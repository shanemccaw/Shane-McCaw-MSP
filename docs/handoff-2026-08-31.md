   prohibited outright. He is sometimes on a capped connection and you cannot tell which.
4. **Prose does not gate the queue — only `blocked_by` edges do.** A comment saying "blocked" is

### 2026-08-30 — pnpm, bandwidth, and dependency edges

**#1987 (`6f8494142`, `d11e157fa`; `CLAUDE.md` +68 and `.claude/settings.json`) — closed and
independently verified.** Four rules plus an override clause:

1. **`pnpm install` is never a remedy for broken module resolution, and is never handed to Shane as
   an instruction.** He has run it hundreds of times. On an unchanged lockfile pnpm compares
   `pnpm-lock.yaml` against `node_modules/.modules.yaml` and exits without walking a single symlink,
   so a link dangling into a deleted worktree survives every run. The real cause is worktree
   dependency isolation — **#1988**.
2. **`--force` is prohibited.**
3. **Never run `pnpm install` from inside a worktree** (the worktree's `node_modules` is a junction
   to main and pnpm wants to purge it).
4. **A blocking conclusion must become a `blocked_by` edge in the GitHub dependency graph, not just
   a comment.** Prose doesn't gate the queue; only edges do. Prompted by #1867 dispatching despite a
   "Blocked" comment. Lives at `CLAUDE.md:320`.

**Agent-self-override clause:** an agent must never grant itself an exception to the
metered-connection gate, must not retry, must not seek an alternate command achieving the same
download, and must not write to settings to clear a block. It fails closed and reports.

**A conflict was resolved rather than papered over.** `CLAUDE.md:668` legitimately instructs one
`pnpm install` at repo root after adding or changing a workspace dependency. The build added a
cross-reference naming that as the one legitimate case rather than deleting it or leaving two rules
in apparent conflict. That was the right call — the prohibition was always about install-as-remedy.

**Bandwidth is a real, hard constraint.** Shane works from two locations: a primary home on fiber and
a second location on capped Verizon wireless. **Agents cannot infer which one he is at.** #1986 is
filed for a Home/Rental title-bar switch modelled on the existing account toggle, gating an env var
on every launched build, a build-prompt header flag, a hard refusal (not a warning) on `--force`
while Rental is selected, and deferral of app-initiated downloads with a visible waiting state.
**Never auto-detect the connection** — a wrong guess that silently enables heavy downloads on the
capped line is the exact failure being prevented.

**Verification of the hook, worth repeating as a method:** the build decoded the `command` field out
of the committed `.claude/settings.json` and executed the literal bytes — exit 0, empty stderr,
stdout parsing as valid JSON with `hookEventName: SessionStart`. A character scan confirmed the only
two `'` in the whole 4,613-character command sit at index 5 and index 4,612, the bash wrapper's own
quotes. That is a stronger check than eyeballing a live `/context`.

## 5. The live blocker as of 2026-08-31 — dual Claude Code logins

**Root cause is not BuildConsole.** `CLAUDE_CODE_OAUTH_TOKEN` is set at the Windows user level and
**outranks `CLAUDE_CONFIG_DIR` for every process that inherits it**, so a per-account config dir
cannot work while it exists. It is also why the usage meter can never read Primary — #2002's rewrite
reads `<configDir>/.credentials.json` and Primary isn't in a file at all.

The sequence, which costs one login instead of two:

```
copy "%USERPROFILE%\.claude\.credentials.json" "%USERPROFILE%\.claude-secondary\.credentials.json"
reg query  "HKCU\Environment" /v CLAUDE_CODE_OAUTH_TOKEN
reg delete "HKCU\Environment" /v CLAUDE_CODE_OAUTH_TOKEN /f
```
Check `ANTHROPIC_API_KEY` the same way. Restart BuildConsole and any open shells, then log Primary in
normally in the default dir. After that both accounts live in files, side by side, and nothing has
to be swapped.

Notes: build journal #1420 says `~/.claude-secondary` had a working login as of 8/27 — verify with
`set CLAUDE_CONFIG_DIR=%USERPROFILE%\.claude-secondary && claude --print "hi"` before re-copying.
Signing a second account in through a browser needs a private window.

**Whether this landed is unverified from this chat.** Confirm before building on it.

## 6. Recorded decisions

**Change control and writes**
- Every tenant write requires an approved CR, including auto-approved standard changes. Standard
  changes are pre-approved catalog items and run unattended forever until revoked.
- Rejection by a customer produces a risk acceptance; rejection by the MSP produces no risk record.
- Runbooks are wholly standard or wholly non-standard — no mixed content.

**Risk**
- An RBD acceptance is a **permanent signed fact** that does not expire. The review clock is separate
  from the acceptance itself.
- Signature required only when accepted scope **expands**, never when it contracts.
- **POA&Ms (#1935)** — a POA&M is a **child of an accepted risk**, not a sibling exit. The risk stays
  covering until the POA&M completes and is verified. Three verification routes: scan (via #1540),
  manual with required pasted evidence, customer attestation with signature. Close authority resolves
  through the RACI workload's A holder. Escalation ladder runs 90/60/30 down to 1 day with severity
  climbing within the three real values.

**Ownership**
- **RACI attaches only to service/workload**; everything else inherits through it (#1523).
- Workload derivation: **service plan enabled in the M365 tenant → RACI row.** No "at least one
  consumer" requirement.
- Multiple holders per RACI letter; ordered A-holders with identical authority; append-only event log.
- **VIP classification is platform-authoritative, not tenant-authoritative.**

**Scope and non-goals**
- **Insider risk / individual attribution is a deliberate non-goal**, recorded explicitly to prevent
  re-proposal. Shane: *"We are not the customer's police."* The platform surfaces organizational
  drift signals without naming individuals.
- **Gov/GCC tenants are excluded from platform scope**, permanently and unrelated to the NASA framing.

**Data lifecycle**
- **Soft Delete (#1944)** — three tiers: 90-day soft delete (customer-recoverable), 30-day semi-hard
  (operator-recoverable only), T-0 hard purge. Post-termination retention 7 years, per-record clocks
  frozen on cancellation and resumed exactly on return. Lock-down is a **subscription gate in
  middleware ahead of routing**, not a per-record check.

**Reporting**
- Status reports are **customer-wide with subscription-driven delivery**, not user-scoped. #1589's
  decision was reversed; **#1923** filed.

**Identity and RBAC — the deepest thread**

`requireAuth.ts:80-93` is not RBAC, it's a **privilege ladder**: a totally ordered `ROLE_ORDER` array
compared by index. Every role is a strict superset of the one below, so **"an engineer can see
remediation but not billing" is a sideways permission and a ladder cannot express sideways.** Adding
a rung never helps. `canManageTeam` and `canApprovePurchases` exist precisely because the ladder
couldn't say it. The enum also conflates four axes: account type (`ServiceAccount`), tenancy,
entitlement (`Free`, `Assessment`), and permission.

Decided:
- **Two separate identity systems** — MSP and customer — for extensibility, one shared mechanism.
- `roles` · `users` · many-to-many `user_roles` · feature→role allow/deny in `jsonb`.
- **Re-point the existing AD-style object UI at the new model; do not rebuild.** Ten shipped phases
  (#61–#69, #90/#91) at `artifacts/admin-panel/src/adminv2/screens/ad/`.
- **One permissions engine** — `can(principal, action, resource)`. One call, two evaluators, with
  **distinct denials**: a tier denial is an upsell moment, an RBAC denial is not.
- 1,626 API endpoints. Two interception points guarantees routes carrying one and not the other —
  that bug already exists between `requireRole` and `requireMspScope`.
- Three architecture flags: **deny wins**; reference roles by **stable id, never name** inside jsonb;
  the capability catalog must be **enumerable** so #1698 can verify coverage mechanically.
- **Strategy is Shane's: build fully featured, then gate.** #1698 exists so the second pass isn't
  forgotten, with a hard "do not start early."
- Issues: **#1696** model · **#1704** engine · **#1697** operator roles · **#1698** deferred gating
  pass · **#1695** white-label identity.

**Other**

- **My Architect (#1569)** — hand-typed advisory ledger, **time only, never money**; 30-minute floor

## 7. Workflow

### Dispatch — Git-as-Build-Queue

1. Write the **fully self-contained** dispatch prompt as a real comment on the GitHub issue, opening
   with `BUILD: model=… effort=… buildSet=…` followed by a `Posted: <UTC ISO8601>` line (Git #2131).
   Shane's system uses DOM injection — **never reference "the rules above" or a shared file, and
   never hand him a copy-paste prompt block.**
2. Move the issue's board Status to **Batter Up** (`09b1927f`) if Shane approved it in chat, or **AI
   Batter Up** (`a0296971`) if it's an agent-discovered finding he hasn't reviewed.
3. BuildConsole auto-queues real Batter Up items on its own refresh.
4. **AI Batter Up items need Shane's explicit Yes (→ Batter Up) or No (→ Backlog).** Never promote one
   yourself.
5. Only bypass this — a literal copy-paste block, or the "Dispatch #___" direct-queue box — when the
   Batter Up path itself is broken or being debugged.

Every prompt also carries: *"Pull #XXX's full issue body AND all comments, in order — later comments
may supersede the original body"*; the logging taxonomy (`logger.child({ channel: … })` from
`engine.*`, `workflow.*`, `billing`, `auth`, `comms.*`, `notification`, `tenant.*`, `admin.*`,
`integration.azure`, `growth.*`, `crm`, `system.core`, `audit`); commit only your own changes and
push immediately; per-issue bookend at `build-journal/{N}.md`, `IN FLIGHT` first and `DONE` with the
real hash last; and query the database directly rather than trusting file exports.

### Header format and model selection

```
--model <full-model-id> --effort <effort> --title <leafIssueNumber> --blocked-by <N> --buildSet <set>
```

Full model IDs only: `claude-sonnet-5`, `claude-opus-4-8`, `claude-fable-5`. Haiku is never used.
Standing buildSet tags: `Marketing`, `Portal`, `MCP`, `BuildConsole`.

| Task type | Model / effort |
|---|---|
| Routine / fan-out | Sonnet 5, Low |
| Everyday well-specified coding | Sonnet 5, Medium/High |
| High-stakes / large-codebase | Opus 4.8, High/xhigh |
| Hardest / most judgment-dependent | Fable 5, High/xhigh |

Always give a specific recommendation matched to risk. Never leave it to default.

### Dependencies

`blocked_by` edges are the source of truth. BuildConsole reads them on every refresh and holds
blocked candidates **fail-closed**. **Depth in the queue costs nothing — never manually hold issues
back; wire the real edge instead.** If the thing being waited on isn't an issue yet, file it first.

```bash
gh api repos/shanemccaw/Shane-McCaw-MSP/issues/<blocking-number> --jq .id
gh api -X POST repos/shanemccaw/Shane-McCaw-MSP/issues/<this>/dependencies/blocked_by -f issue_id=<that-id>
```

### Verification before closing

Never trust a "landed" claim. Chat-pasted summaries are not verification.

```bash
git merge-base --is-ancestor <sha> origin/main      # authoritative
git show origin/main:build-journal/{N}.md           # IN FLIGHT and DONE both present
git ls-remote --heads origin | grep {N}             # branch cleaned up
git status --porcelain                              # clean before DONE
```

Contract pack at `docs/{module-name}-contract-pack.md` where applicable. Close via GraphQL
`closeIssue` with `stateReason: COMPLETED` / `NOT_PLANNED` — REST PATCH cannot set `stateReason`.

**Run the orphan sweep after any batch closure, including your own:** GraphQL `milestone(5)` issues →
`nodes { number parent { number state } }`, flag anything whose `parent.state == CLOSED`.

**BuildConsole's Verifying state is the console working correctly, not a bug.** A build runs → moves
to Verifying → Shane says it landed → you verify → you close → the card moves to Done. **A build
issue closes when the build ran.** Findings become new issues; don't hold build issues open waiting

**GitHub API notes**
- Sub-issues: `POST /issues/{parent}/sub_issues` with `{"sub_issue_id": <integer id>}` — the internal
  numeric `id`, not `node_id`. Single-parent enforced. **Hard cap 100 per issue**; detach closed ones
  with `DELETE` to free capacity without deleting them.
- `dependencies/blocked_by` REST triggers **secondary abuse-detection rate limiting** under rapid
  concurrent calls — HTTP 403 with a scraping/ToS message even when the 5000/hr core quota is full.
  GraphQL quota stays healthy when REST core is exhausted.
- Board pagination: `items(last: 100)` backward is dramatically more efficient than forward — ~1,800
  items across 18 pages, and all real candidates cluster in the last 1–2.
- Milestone on creation takes the integer `number`.
- Label deletion: `DELETE /issues/{n}/labels/{label}`, URL-encode spaces as `%20`.
- Bulk work: clone and grep locally; the Search API rate-limits fast.

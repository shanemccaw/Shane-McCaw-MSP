# Plan — #4576: `identity:ca-policy-count` gate-skipped path has no scalar for the Security pillar CA tile

## Problem Description

The Security pillar's "Conditional Access policies" stat tile
(`PILLAR_STAT_SPECS.security[0]`, `pillar-summary-stats.ts`) reads
`identity:ca-policy-count`'s `caPolicyCount` field via
`statFromCheckObservation`. On a tenant using Security Defaults instead of
Conditional Access (e.g. the McCawSoft testbed tenant, `tenants.id` 2080), the
check's prerequisite gate short-circuits before the CA policy list is ever
fetched (`monitor-executor.ts`, the `gateEndpoint`/`gateExpression` branch),
and the row it persists is the raw Security Defaults policy object —
`{ _gateSkipped: true, id, displayName, isEnabled, description, … }` — with no
`caPolicyCount` field at all. `numericProp` returns `null` for a missing
field, so the tile renders "—" (`unavailableReason: "no_data"`).

That "—" is misleading: this tenant genuinely has zero Conditional Access
policies (it runs Security Defaults instead), which is a real, reportable
fact, not an unmeasured one.

## Root Cause Analysis

`monitor-executor.ts`'s gate branch (~line 3900) is generic — it serves four
checks that share the same Security Defaults gate
(`identity:app-proxy-connector-groups`, `identity:ca-mfa-coverage`,
`identity:ca-legacy-auth-block`, `identity:ca-policy-count`, confirmed via
`select key, gate_endpoint, gate_expression from monitor_checks where
gate_endpoint is not null` against the local DB). It persists
`{ _gateSkipped: true, ...gateData }` for all four uniformly. `gateData` is the
raw `/policies/identitySecurityDefaultsEnforcementPolicy` singleton — it never
carried a scalar count for any of the four, because none of the four names
what to count from it.

Only `identity:ca-policy-count`'s tile spec (`security.caPolicies`) reads a
`caPolicyCount` field from this check's observation. The gate never populated
it, so the field genuinely never existed — not a zero, not a `null` decided
anywhere, just an absent key. `numericProp` correctly treats absence as
`no_data`.

## Decision (confirmed by Shane, dispatch comment)

Stamp the gate-skipped path with an explicit `caPolicyCount: 0` plus a
`securityDefaultsEnabled: true` flag, scoped to `identity:ca-policy-count`
only (the other three checks sharing this gate branch have no such field and
must not gain one that means nothing for them). This turns the tile's "—"
into a real "0 — Security Defaults enabled" state.

## Proposed Changes

1. **`artifacts/api-server/src/lib/monitor-executor.ts`**
   (https://github.com/shanemccaw/Shane-McCaw-MSP/blob/main/artifacts/api-server/src/lib/monitor-executor.ts#L3900-L3949
   — gate-skipped branch, ~line 3900–3949)
   Add a `gateSkippedExtras` object, populated only when
   `check.key === "identity:ca-policy-count"`, carrying
   `{ caPolicyCount: 0, securityDefaultsEnabled: true }`. Spread it into both
   `persistCheckProfile`'s `extractedProperties` and the function's own
   returned `extractedProperties`, alongside the existing `_gateSkipped: true`
   and `...gateData`. The other three gated checks fall through with an empty
   extras object — unaffected.

2. **`artifacts/api-server/src/lib/pillar-summary-stats.ts`**
   (https://github.com/shanemccaw/Shane-McCaw-MSP/blob/main/artifacts/api-server/src/lib/pillar-summary-stats.ts#L738-L788
   — `statFromCheckObservation`, and the `security` tile spec comment ~line 540)
   - Update the `security.caPolicies` spec's comment: it no longer "honestly
     reads unavailable" — it now reads a real, explained 0.
   - In `statFromCheckObservation`, after the existing `subTemplate`/
     `denominatorField` sub-caption logic, check
     `observation.props.securityDefaultsEnabled === true` and, if so, set
     `sub` to a fixed, honest string: "This tenant uses Security Defaults
     instead of Conditional Access". This is a generic read of the flag (not
     hardcoded to the `identity:ca-policy-count` check key), so it applies to
     any future check whose observation legitimately carries the same flag,
     but today only `identity:ca-policy-count` ever sets it.

No schema change, no migration — `extracted_properties` is a JSONB column,
and this only adds keys to an existing row shape.

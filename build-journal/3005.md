## Investigation result — the body's lead is RULED OUT (with real evidence)

The issue's hypothesis was that `RunDeferredStartupAsync`'s `MarkShellReady()` might be
gated behind lazy Git Board initialization, so `StartupConnectivityService.AllSettled`
never fires until the panel is opened. **This is not what happens.** Real activity logs
(`%AppData%\BuildConsole\logs\activity-2026-09-0{4,5}.log`) show, on *every* recorded
startup:

1. `Application shell: connecting…`
2. `Application shell: ok (~2-4s) — ready`  ← `MarkShellReady()` fires in ~2-4s, unconditionally
3. `startup connectivity: all connections settled.`  ← `AllSettled` fires
4. `auto-queue grace period started, 90s before the launch gate lifts (#1884)`
5. ~90s later: `the queue pickup loop's launch gate is now lifted.`  ← `MarkAppReady()`

The whole readiness chain runs on its own, no Git Board open required. `MarkShellReady()`
is in `RunDeferredStartupAsync`'s `finally`, and there's a 20s global-cap watchdog backstop
in `StartupConnectivityService`. So the AllSettled/MarkShellReady chain is not the cause.

## Real cause (confirmed with logs)

After the launch gate lifts, the queue's first claim runs `BuildQueuePostgresClient.GetNextAsync`,
whose Git #1600/#1904 blocker/own-issue re-check reads GitHub's live open-issue set. When the
shared Git #2815 rate-limit circuit is open it holds every blocker-bearing build fail-closed.
Two things make recovery depend on a manual action:

- The Git Board's GitHub open-issue fetch is **manual-only** (Shane, 2026-08-14 — background
  poll removed; `LeftSidebar.xaml.cs:638-645`). Its ONE automatic fetch runs at ~3s — ~87s
  **before** the gate lifts — so its `BoardRefreshCompleted → RequestImmediateReevaluation` was
  gated out and wasted, and nothing re-fetches afterward.
- Real logs (09-05): circuit tripped 11:41-11:44 (backing off ~800s); NO automatic
  `git-board.data loaded N open issue(s)` recoveries followed; the first successful fetch +
  queue recovery came only after a **manual Refresh click at 12:15:50** — ~31 min stuck. Same
  shape at 13:31.

So opening/refreshing the Git Board was the only reliable way to (a) recover the #2815 circuit
with a fresh successful GitHub call and (b) kick an immediate re-evaluation — exactly the
manual workaround the issue describes.

## Fix (72ea25160)

`MainWindow.ResolveAutoQueueGrace` — the moment the launch gate lifts (and the queue is not
being paused), trigger a `LeftSidebar.PopulateGitTrackerBoard(forceFresh: true)`. This
re-fetches GitHub open issues (an HTTP probe that also recovers the #2815 circuit if it had
tripped) and, via the existing `BoardRefreshCompleted → RequestImmediateReevaluation` wiring,
kicks an immediate queue re-evaluation against current data — automating the exact action Shane
did by hand, at exactly the right moment. Fire-and-forget, silent, errors caught; the watcher's
own 10s poll remains the backstop. Preserves Git #1600 fail-closed liveness (no stale-snapshot
claiming introduced). Does NOT re-introduce a background poll (one fetch at gate-lift, not a
cadence).

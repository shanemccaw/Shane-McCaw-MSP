- 2026-08-29 ✅ DONE — **Contamination fixed at source and proven on a real live execution.**

  **Diagnostic first (as instructed).** Added raw-stdout capture on entrypoint.ps1's ConvertFrom-Json failure path (byte length, first 2000 chars, leading-byte hex, child exit code). Deployed it to `ca-ps-execution-dev` (revision `dev1482diag`) via `az acr build` + `az containerapp update` (the #1277 mechanism; driven directly with `az` because the running BuildConsole binary predated #1277's deploy handlers). Ran one live `get-connection-info` and read the container logs.

  **Observed (not inferred).** The child's stdout began with a 6047-byte block: `Error Acquiring Token:\nSystem.Exception: ... AADSTS700027 ... ---> MSAL.NetCore...MsalServiceException...`. This is written by the ExchangeOnlineManagement module's MSAL token wrapper **straight to the process Console stdout** on a token-acquisition failure — bypassing PowerShell streams, `-ErrorAction`, and `| Out-Null` — landing ahead of the child's one-line JSON result. The parent's `ConvertFrom-Json` then failed on `E`(rror) and returned the opaque `script_error` "malformed output". MicrosoftTeams never does this raw write, which is exactly why only the EXO-module (compliance + exchange) checks corrupted.

  **The contamination was masking a real, separate auth failure.** The MSAL error is `AADSTS700027`: the Key Vault cert `mt-app-cert` (thumbprint `251BDCD5895FB127F44648F29999F3B1820CA2D3`) is **not** registered on app `9ea2e409-d1b9-422a-8451-02fa0b98d1c3`. That app has exactly one registered cert — thumbprint `BC8F5C26BA1FA641C15264278EDCDA8F0F481906` (CN=ShaneMcCawMSP-MT-App-2026, valid to 2028-08-17). Key Vault and the app registration hold **different certs**. This is a credential-sync gap only Shane can safely fix (production multi-tenant app registration) — flagged as **Shane To-Do**.

  **The fix (source-side).** `child-worker.ps1` now keeps a private handle to the real stdout writer for its one result line and diverts `[Console]::Out` to an in-memory `StringWriter` for the process's whole life, so any stray Console write (module import output, the MSAL "Error Acquiring Token:" dump, a connect banner) is captured and surfaced once as a `warn` log on `integration.ps-execution` instead of corrupting stdout. Added `-ShowBanner:$false` to `Connect-IPPSSession` for parity with `Connect-ExchangeOnline`. `entrypoint.ps1` gained a last-JSON-line recovery **safety net** (explicitly not the fix) plus the raw-stdout capture logging kept in place so any future contaminant is observable. Locally proved the `[Console]::SetOut` diversion keeps stdout pristine before deploying.

  **Proven live** on revision `dev1482fix3` (confirmed serving via `/healthz` self-report + `az revision list` at 100% traffic), direct authenticated calls to the container (dev api-server on :8080 was down, so bearer fetched transiently from Key Vault for the verification POST):
  - compliance `get-connection-info` (`Connect-IPPSSession`): before → HTTP 500 `{"error":"script_error","message":"...produced malformed output."}`; after → **HTTP 502 `{"error":"auth_failed","message":"Could not establish a Security & Compliance session for the target tenant."}`**.
  - exchange `get-transport-rules` (`Connect-ExchangeOnline`): after → **HTTP 502 `{"error":"auth_failed","message":"Could not establish an Exchange Online session for the target tenant."}`**.
  - Container logs for both show `suppressed stray stdout write from a module/connect path (#1482 contract guard)` with `strayByteLen: 5909` capturing the `Error Acquiring Token:` dump, and **no** "unparseable/malformed output" and **no** "recovered from last JSON line" — i.e. the parent parsed clean stdout on the first try; the child-side guard did all the work.

  **Honest outcome vs "prove the count drops".** The 14 EXO-module checks no longer fail with the opaque `script_error`/"malformed output" contamination bug — that failure mode is eliminated; they now return the correct, actionable `auth_failed`. They are still not `ok:true` because of the separate `AADSTS700027` cert-registration gap the contamination had been hiding — that is a real infra blocker (Shane To-Do), not something code can or should fake (fixture/real-data rule). Once Shane syncs the Key Vault cert with the cert registered on app `9ea2e409`, these checks will connect and return real data. No test manifest written — the change is in `services/ps-execution`, outside the `artifacts/msp-portal` / `artifacts/shane-mccaw-consulting` manifest scope.

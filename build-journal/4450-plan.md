# #4450 — Plan: remove the Diagnostics rail "Add Comment" box and settle the floating-card focus question

Permalinks below are pinned to `d39473bb17c1dc1367df217aba7805379e5ba41b` (origin/main when this plan was written).

## Problem Description

Shane's confirmed scope (issue comment, 2026-09-18): the Diagnostics rail's "Add Comment" card
(`TxtDomComment`, inside the collapsed "DOM Inspector" accordion) is a submission path he has never
intentionally used. Remove it. The in-page floating note card and the composer's Bug Entry section
stay as they are. His expectation is that after a DOM Inspector click the floating card already has
real keyboard focus, so he does not have to click into it before typing.

## Root Cause Analysis

Traced the focus handoff on a DOM Inspector click, in order:

1. **Page, mousedown.** The in-page listener is `document.addEventListener('click', onClick, true)`
   ([VisualTestTrackerTelemetry.cs#L1069](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/d39473bb17c1dc1367df217aba7805379e5ba41b/desktop/BuildConsole/Services/VisualTestTrackerTelemetry.cs#L1069)).
   There is no `mousedown` handler on the page that prevents default, so the native mouse-down has
   already given the WebView2 HWND real OS keyboard focus before `click` fires.
2. **Page, click.** `onClick` locks the element, shows `noteCard`, then posts `VTT_DOM_INSPECT`
   ([L921-L1017](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/d39473bb17c1dc1367df217aba7805379e5ba41b/desktop/BuildConsole/Services/VisualTestTrackerTelemetry.cs#L921-L1017)).
   **It does not focus `__vtt_card_input`.** #4447 (`71575585d`) deleted the only
   `setTimeout(() => cardInput.focus(), 30)`; the comment left at L1000-1009 records that.
3. **Host, on the message.** `TestModeDiagnosticsPanel.HandleDomElementInspected` queues
   `TxtDomComment.Focus(); Keyboard.Focus(TxtDomComment);` at `DispatcherPriority.Input`
   ([xaml.cs#L466-L473](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/d39473bb17c1dc1367df217aba7805379e5ba41b/desktop/BuildConsole/Controls/TestModeDiagnosticsPanel.xaml.cs#L466-L473)).
   That is the only `Focus(` call reachable from a docked-Test-Mode inspect click
   (`grep "Focus(" MainWindow.TestMode*.cs Controls/TestModeComposerPanel.xaml.cs Controls/TestModeDiagnosticsPanel.xaml.cs`
   returns just these two lines).

**What #4447 did and did not change.** It removed the JS half of a two-sided focus grab. Since then
the C# call is not racing anything: it wins every click, and it moves real OS focus out of the
WebView2 into a rail box that is collapsed inside an accordion and that Shane did not know existed.

**Consequence for Shane's hypothesis (scope item 3).** The hypothesis was that removing the C# call
lets the card's own `cardInput.focus()` win. That call no longer exists, so removing
`TxtDomComment.Focus()` alone cannot give the card focus. After the removal the WebView2 keeps OS
focus (step 1), but `document.activeElement` is the page body, not the card's textarea, so typing
still goes nowhere until he clicks into the card. **Removal is necessary but not sufficient.**

## User Review Required

None blocking. One judgment call for Shane: to meet the stated goal (card usable without a click)
this build also restores a page-side `cardInput.focus()` as a separate commit. That touches the
in-page card, which the scope comment says to leave alone, so it is isolated and trivially
revertible. The race that made #4447 remove it needs a second focus claimant, and the rail box was
that claimant; it is gone after this change.

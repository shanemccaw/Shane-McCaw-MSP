- 2026-09-08T20:10:00Z ✅ DONE — Root cause found by full-code audit (no live browser available in
  this environment; see honest verification note below): `web/shanes-life/public/app.css`'s
  `body { overflow-x: hidden; }` (added by Git #3128 to fix a Chromium scroll bug) is a genuine
  ancestor of `#capture` (`body > #app-view > #capture`, confirmed in index.html). Giving an
  ancestor of a `position: fixed` element a non-`visible` overflow axis is the real WebKit/
  Chromium containing-block trap the issue's own hypothesis named -- on iOS Safari it makes the
  fixed element track that ancestor's box instead of the true viewport, which explains
  "docks fine on short rooms, sticks mid-page once a room actually scrolls" (route-dependent
  because only rooms with enough content to scroll reveal it). The `overflow-x: hidden` was only
  ever needed to clip the room watermark's real horizontal bleed (Git #3119, `attachRoomWatermark()`
  in `critters.js`: `right: -44px` on a `position: absolute` SVG) -- every watermark paints onto
  `#view` (confirmed via every `render()` room-dispatch call site in `app.js`), which is a SIBLING
  of `#capture`, not an ancestor. Fix: moved `overflow-x: hidden` off `body` onto `.view` instead
  -- same bleed clipped at its actual source, `html`'s real scroll node stays untouched (Git #3128
  unaffected, confirmed no `overflow` was ever set on `html`), and `#capture`'s ancestor chain
  (`html`/`body`/`#app-view`) now carries no transform/filter/will-change/overflow of any kind.
  Verification: local server (`node src/server.mjs` against the real local `finances` Postgres)

  **Found the fix above was real but incomplete.** `.view`'s `overflow-x: hidden` (298bd12c5) does
  stop unclipped descendant overflow from inflating `document.documentElement.scrollWidth` (which
  is what real mobile browsers use to zoom the page out and break `.capture`'s `position: fixed`)
  -- confirmed live, `window.innerWidth`/`innerHeight` correctly 402x874 on every route now. But
  `.view` itself has `display: grid` with no explicit `grid-template-columns`, so its one implicit
  `auto` column still internally grows to fit the max-content of its widest child -- `.money-tabs`
  (Money's own Now/Bills/Banks/Bankruptcy/Accounts/Cars/Vault/Documents tab bar) wanting ~1015px to
  lay out 8 real tabs. `overflow-x: hidden` clips that blowout from *painting* past `.view`'s real
  402px box and from leaking into page-level metrics, but doesn't shrink it: `.money-tabs` itself
  still measured 1015px wide (confirmed via `getBoundingClientRect` on the live grid, not just the
  page-level numbers the prior fix's own verification checked), leaving 4 of its 8 real tabs
  (Accounts/Cars/Vault/Documents) genuinely off-screen and unreachable by a real user -- a second,
  separate real bug on the same element, not the #3264 symptom itself but found and fixed in the
  same pass rather than left for later. Root of that: `.money-tabs`' own
  `grid-template-columns: repeat(5, 1fr)` was stale from when `MONEY_TABS` (app.js) had 5 entries;
  Banks/Bankruptcy/Accounts/Documents were added later (Git #3241 era and after) without updating
  this count, and bare `1fr` still respects each column's own min-content floor, so even correcting
  the count to `repeat(8, 1fr)` alone left 4 tabs clipped by "Bankruptcy"/"Documents" being
  single unbreakable words wider than an even 1/8th share.
  **Fix:** `.view { grid-template-columns: minmax(0, 1fr); }` (caps the implicit column to the
  real available width) plus `.money-tabs { grid-template-columns: repeat(8, minmax(0, 1fr)); }`
  (matches the real tab count and removes the per-column content floor). Full diff in commit
  `d72445865`.

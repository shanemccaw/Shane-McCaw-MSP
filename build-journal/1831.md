## Log
- 2026-08-30 ⏳ IN FLIGHT — reading Themes/DarkTheme.xaml ScrollBar style (~744-786), then live-testing mouse-wheel behavior over general content (not thumb) before touching code.
- 2026-08-30 ✅ DONE — Widened the global `ScrollBar` style (`Themes/DarkTheme.xaml`) from
  8px to 14px (both vertical Width and horizontal Height triggers), keeping the visible
  color pill the same slim 8px width but wrapping it in an outer `Background="Transparent"`
  Border that fills the full 14px track — WPF hit-tests any Border with a non-null
  Background (Transparent included), so the real grab/hover area is now the whole 14px
  column, not just the visible pill. Added a horizontal counterpart style
  (`SbThumbHorizontalStyle`) since the old shared `SbThumbStyle` hardcoded a vertical
  layout that would have mis-rendered horizontal scrollbars once specialized. Added
  `Margin="0,0,8,0"` to the Build Queue column's outer `DockPanel` (`MainWindow.xaml`,
  Grid.Column=5) so its scrollbar sits 8px in from the real window edge instead of flush
  against it.
  **Wheel-scroll investigation (real, not assumed):** grepped the whole app for
  `MouseWheel`/`PreviewMouseWheel` handlers — none exist anywhere near `BuildQueuePanel`
  or its ancestor chain (MainWindow, DockPanel, Grid). Grepped for any
  `TargetType="{x:Type ScrollViewer}"` style/template — none exists in the app; the
  `ScrollViewer` itself is 100% framework-default everywhere, only the `ScrollBar`
  chrome is themed. That means wheel-over-content routing is unmodified default WPF
  `ScrollViewer` behavior (scrolls anywhere within its bounds, not just over the thumb).
  Confirmed live via UIAutomation against a real running second instance of the built
  app: the Build Queue's outer `ScrollViewer` (`ClassName=ScrollViewer`,
  `AutomationId` none) had `BoundingRectangle` X=1621..1920 against a window rect of
  0..1920 — i.e. its right edge landed **exactly** on the window's right edge, 0px of
  buffer, directly confirming the "flush against the literal window edge" half of the
  bug. Could not get a live wheel-delta-changes-VerticalScrollPercent reading on that
  exact ScrollViewer because the live queue had no overflow at the moment I tested
  (`VerticalScrollPercent=-1`, `ViewSize=100%` — nothing to scroll right then); I
  verified the identical unmodified-ScrollViewer/unmodified-ScrollBar-style plumbing on
  the Editor pane's ScrollViewer instead (`ViewSize=74.8%`, genuinely scrollable) to
  establish the mechanism is shared and standard. I stopped short of a physical
  mouse-wheel-gesture simulation once it became clear my raw `SendCursorPos`/`mouse_event`
  screen coordinates (uncorrected for DPI) were landing on unrelated desktop windows, not
  reliably on the target app — continuing would have risked moving the real cursor over
  other things on a shared machine, so I stopped rather than push through it. Net
  conclusion, stated plainly: **no code fix was needed for wheel-scroll** — it already
  works by ordinary WPF default behavior, confirmed by the complete absence of any
  interception code and the shared, unmodified `ScrollViewer` plumbing across the app;
  the real, confirmed bug was the 8px width and the 0px edge margin, both now fixed.
  **Side-effect check:** built Release, launched a second live instance, screenshotted
  the full window — dark theme intact, no layout breakage, editor-pane scrollbar (uses
  the same widened global style) renders as a normal, slightly more visible thin thumb,

  warnings, 0 errors) both before and after the change.

- 2026-08-30 ✅ DONE — **Decision:** `status_reports` STAYS user-scoped (`clientUserId` remains a `users.id`). It targets a specific person; every notification, email, audit row and project link in `admin-status-reports.ts` depends on that users.id. Realigning it to `tenants.id` would be a destructive re-architecture of a working CRM table with **no customer-visible difference** (both models surface the same reports to the same customer), so it is not a product decision requiring Shane. **Fix:** eliminated the DUAL tenant resolution in `portal-retainer.ts` — the route now resolves the caller's tenant EXACTLY ONCE (`customerId = resolveCustomerId(req)`, the JWT's tenants.id) and sources the `status_reports` users.id set from THAT tenants.id via `resolveCustomerUserIds(customerId)` instead of a second independent resolution off `req.user!.id`'s own `users.tenantId`. Removes the divergence hazard where a page could show one tenant's retainer ledger beside another's status reports. Added a fail-closed empty-set path (unclaimed customer → no status_reports DB read → `[]`). **No schema change** (additive-in-spirit source swap; both tables confirmed empty via psql — 0/0/0 rows, mismatch never exercised). **Verification:** api-server `tsc --noEmit` clean on both touched files; `vitest run portal-retainer.test.ts` → 7/7 passed (test updated to mock `resolveCustomerUserIds` + assert scoping on customerId=42, plus a new unclaimed-customer fail-closed test).

  actually fires a runnable SOP's automated (write-verb `graphEndpoint`) steps through the
  SAME production machinery `runConfigPackForCustomer` uses — the CR authorization gate
  (#1497's `claimChangeRequestForWrite`/`bindChangeRequestToRun`) and the Workflow Engine's

  `settleAuthorizedChangeRequests`) advances `currentStepIndex`/`passedStepsCount`/`status`

  is MSP-operator-triggered, the same posture `execute_write_pack`/`execute_action` already
  use for config packs and micro-remediations).

## What shipped

- **`lib/db/src/schema/msp.ts`** — `mspSopRunsTable.wfRunId` (plain nullable int, no FK —
  same convention `msp_change_requests.executor_run_id` follows) and `.automatedStepMap`
  (jsonb, the run's own node-id → step-index snapshot; `SopRunAutomatedStep` type exported).
- **`artifacts/api-server/src/lib/sop-workflow-graph.ts`** (new, pure) — `buildSopWorkflowGraph`
  materializes only write-verb (`POST`/`PATCH`/`PUT`/`DELETE`) `graphEndpoint` steps into a
  linear `start → graph_write_operation → … → end` `WfGraph`. A small non-`eval` parser
  (`parseLooseObjectBody`) reads the stored steps' loose-object bodies (`{ accountEnabled:
  false }`); single-brace author-time placeholders (`{id}`) are rewritten to the engine's own
  `{{id}}` `interp()` syntax. GET steps and anything unparseable are left unmaterialized for a
  human rather than guessed. 19 unit tests (registered in `vitest.config.ts`), **19/19 pass**.
- **`artifacts/api-server/src/lib/sop-execution.ts`** (new, IO) — `runSopForCustomer` mirrors
  `runConfigPackForCustomer`'s authorization posture exactly (approved+unconsumed CR via the
  reused `claimChangeRequestForWrite`/`bindChangeRequestToRun`/`releaseChangeRequestClaim`, or
  a testbed customer; fail-closed otherwise), fires via the reused `fireWorkflowForDefinition`,
  and writes the `msp_sop_runs` row (CR reference in `psaTicketId` via the existing
  `formatChangeRequestCode`, matching the row's own documented `/^CR-/` read-side test).
  `settleSopRuns` is the 60s reconciliation sweep (wired in `index.ts` next to
  `settleAuthorizedChangeRequests`), reading each run's own `automated_step_map` snapshot
  against real `wf_runs`/`wf_run_node_outputs` rows — never the SOP's live (possibly
  since-edited) steps.
- **`artifacts/api-server/src/lib/config-pack-orchestrator.ts`** — extracted
  `persistMaterializedWorkflow` (generic over definition name/description/metadata) out of
  `persistConfigPackWorkflow` (now a thin wrapper, unchanged external behavior/signature) so
  both the config-pack path and the SOP path share one definition/version-persistence
  implementation — the concrete form of "never a second execution path."
- **`artifacts/api-server/src/routes/msp-sops.ts`** — `POST /api/msp/sops/:sopId/run`
  (`MSPOperator`), same trigger-surface posture as `admin-config-pack-run.ts`. Verifies the
  target customer belongs to the caller's own MSP (a check `runConfigPackForCustomer` doesn't
  need since its own route is `PlatformAdmin`-scoped) before ever touching the CR gate.

- **Real data check found a third thing to fix mid-build:** `bt_chat_mentioned_issues` has no expiry
  on an open issue (only a closed one gets pruned) — one real production `chat_url` has **449** tracked
  mentions. The issue's own filter definition names "not stale" as a criterion alongside open/not-
  resolved, but a naive implementation would (a) never actually filter on staleness and (b) fire up to
  ~8 sequential GitHub calls (title + board status + 2-direction chain walk) per mentioned number —
  for 449 numbers that's thousands of network round trips per dock refresh. Added a real 14-day
  staleness window on `last_seen_at` plus a 40-item hard cap (most-recently-mentioned first) as a
  backstop. Verified against the real 449-mention chat: every single one fell inside the 14-day window
  (it's a currently-active chat), which confirms the cap — not the staleness window — is what actually
  bounds this chat's dock refresh; both are real and load-bearing, not redundant.

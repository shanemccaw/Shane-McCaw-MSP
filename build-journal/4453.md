## Root cause — NEITHER a per-login re-execution NOR a pure widget bug: an orphaned run row
Evidence, local Postgres + platform_log_stream:
- **Not re-execution:** exactly 1 msp_diagnostic_runs row for customer 2080 (43cc492d…, created 21:22:32 -04 at account creation), against 2 real logins (user_sessions 1324 at 21:23:31, 1325 at 21:43:42). No monitor-executor check activity after 21:40:11, so no Graph calls on login.
- **What actually happened:** the run executed checks 21:22:32 → 21:40:11, then the api-server restarted at 21:41:23 ("Server listening"; 6 restarts 21:41–22:06). runDiagnostics is fire-and-forget in-process, so the scan died with the process. The row stayed status=running, checks_*=0, updated_at=21:22:32, and no reaper existed.
- **Why "Check 1 of 198":** /portal/scan-status reported active (pending/running). The dead process never sent SSE events, so useScanState fell back to max(1, checksOk+checksError+checksLicenseGap) = max(1, 0) = 1. The total came from /portal/scan-plan (198 core:premier checks). Every login or page load re-read the same dead row.

## Fix (54ea42f69)
- diagnostics-runner.ts: 60s liveness heartbeat on updated_at while a run executes (cleared in finally, unref'd).
- failInterruptedDiagnosticRuns(): fails pending/running rows with no heartbeat for 10+ min, using a real error message, and raises the same operator task an in-process failure does. Heartbeat-based rather than "fail all running at boot", so a sweep in one api-server process can't fail a run another process sharing the DB is still executing.
- index.ts: sweep at boot + every 2 min.
- The portal needed no change: a failed lastRunSummary already renders the existing "Scan failed" phase with the errorMessage.

  (`%AppData%\BuildConsole\logs\activity-2026-08-30.log`) around the 1882/q995 window.

  **#1971 vs #1965 — one root failure, two compounding defects (not the hypothesis #1971's
  body stated).** #1971's body hypothesised "a real build call site fails to pass the stable
  build pid, so the sweep sees a dead owner and reclaims a live worktree." **That hypothesis
  does not hold up** (observed): the only real build call site — `QueueWatcherService.LaunchItem`
  — provisions with the launcher (BuildConsole) pid and then re-stamps to the launched build
  pid, and the activity log confirms it every time (`Re-stamp worktree owner '1882-q995' ->
  pid 32076: ok`). The 07:02:19 sweep correctly retained all 12 live worktrees (`removed=0`).
  The owner-pid liveness gate works for a LIVE process.

  The real failure is what happens once a build process legitimately EXITS with unpublished
  work still in its worktree — specifically the session-limit park path:
  1. (#1965, the trigger) A build that hit the Claude session limit is parked "limit-paused"
     and its process exits (observed: `Parked queue #995 ... (exit 1)`). It was NOT idle/done;
     it was blocked on the limit with uncommitted work in `C:\wt\1882-q995`.
  2. (`QueueWatcherService.cs:945`) For a `limitParked` build the reap loop SKIPS both merge-back
     and mark-stale — leaving the worktree record `status:"active"`, `creatorPid` = the now-dead
     build pid, `keepForDebug:false`.
  3. (#1971, the amplifier) `MaybeSweepWorktrees()` runs every 5 min. The worktree now fails the
     liveness gate (dead pid), the 30-min grace keys off `createdAt` (a long build is already
     past it), and nothing marks it keep-for-debug — so it becomes a removal candidate.
  4. `removeWorktreeSafe` then force-removes the directory AND force-deletes the `agent/*` branch
     with **no preservation** — wiping uncommitted work and orphaning even committed bookends
     (recoverable only via `git fsck`), exactly as 1882/1548 reported. (The exact command that
     emitted the observed `reset: moving to HEAD` reflog line is INFERRED — the session-limit
     auto-restart re-provisioning the just-removed name recreates a fresh worktree at
     `origin/main`, which presents as a clean tree + a reset reflog; the log did not capture the
     precise plumbing, so this last link is labelled inferred, not observed.)

  **Fix (root cause once, defense in depth), all additive/low-risk:**
  - `worktree-lifecycle.mjs removeWorktreeSafe`: before destroying, PRESERVE — WIP-commit any
    dirty tree onto the branch, then stamp a durable `refs/rescued/<name>-<ts>` ref at the branch
    tip so removal/branch-delete can never silently discard work (a recoverable named ref, no
    `git fsck`). Single choke point for both the sweep and explicit cleanup.
  - `worktree-lifecycle.mjs sweepWorktrees`: keep the existing `pidAlive` liveness gate (never a
    second one); also honour `lastActiveAt` in the grace window so a freshly re-stamped/resumed
    worktree is retained.
  - `QueueWatcherService.cs`: a `limitParked` build now RETAINS its worktree (keep-for-debug,
    "session-limit paused — resume pending") instead of leaving it exposed, so the sweep can't
    reclaim it before the auto-restart resumes the session in that same worktree.

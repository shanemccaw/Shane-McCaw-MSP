  **A real correctness bug found live and fixed in-build (`63e210f5f`).** #1961's
  `selectReadCmdlet()` prefers the mapped cmdlet whose noun is a suffix of the resource's DSC
  name. Teams cmdlet nouns carry a `Cs`/`CsOnline`/`CsTeams`/`CsTenant` module prefix the DSC name
  never has, so `teamsvoiceroute`.endsWith(`csonlinevoiceroute`) is false for **every** Teams
  resource — the rule never fired and each multi-cmdlet Teams resource fell back to whichever
  cmdlet Microsoft365DSC listed first. Observed in the live run, not hypothesised:
  `m365dsc:TeamsVoiceRoutingPolicy` resolved to `Get-CsOnlinePstnUsage` and **stored a PSTN usage
  under a resource type named "…VoiceRoutingPolicy"**, `m365dsc:TeamsVoiceRoute` resolved to
  `Get-CsOnlinePSTNGateway`, and `m365dsc:TeamsComplianceRecordingPolicy` to the …Application
  cmdlet. `comparableNounForms()` strips the module prefix so the noun is comparable again; no
  Exchange/Purview noun in the catalog starts with `cs`, so pass 1's behaviour is unchanged.
  6 new tests on verbatim real `read_cmdlets` arrays; `config-snapshot-collector.test.ts` 26/26
  green. Not filed as a finding — fixed in this build.

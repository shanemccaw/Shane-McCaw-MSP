- 2026-08-31 ⏳ IN FLIGHT — auditing `LinkChatToIssueAsync`/`UnlinkChatFromIssueAsync` in
  `desktop/BuildConsole/Services/BuildQueuePostgresClient.cs`, the milestone-assign path in

- 2026-08-31 ✅ DONE — confirmed the root cause by direct code read: Step 4 of
  `LinkChatToIssueAsync` looked ONLY at local `bt_epics`/`bt_issues`; a not-yet-synced target
  fell through silently (`bt_chat_issues` still got its row, `bt_chats.epic_id`/`issue_id`
  never set, no error). Fixed:
  - `LinkChatToIssueAsync`/`UnlinkChatFromIssueAsync` (`BuildQueuePostgresClient.cs`) now take
    an optional `resolveLive` delegate; `LeftSidebar.ResolveLiveBoardIssue` (new) resolves it
    from the already-fetched `_lastBoardIssues` (same source `BackfillSyntheticEpicsFromBoard`
    reads for #1362's read-side fix) and a shared `ResolveAndPersistChatLinkAsync` helper
    upserts a minimal `bt_epics`/`bt_issues` row when the local lookup misses but the live
    board resolves it. `LinkChatToIssueAsync` now returns whether resolution actually
    succeeded; the 3 genuine issue/epic call sites in `LeftSidebar.xaml.cs` (chat-card "Link to
    Issue/Milestone...", tab-level `AssignChatToIssueInteractiveAsync`, issue-node "Assign Chat
    to Issue...") show a real warning toast instead of a false-success one when it didn't.
    `UnlinkChatFromIssueAsync`'s remaining-link recalculation gets the same fallback, which
    also fixes a related bug: an unresolvable remaining link used to leave `bt_chats` pointing
    at the epic/issue that was JUST unlinked (stale, not just unset). `MainWindow.xaml.cs`'s
    `AssociateChatWithIssueAsync` passes `LeftSidebar.ResolveLiveBoardIssue` too and logs the
    resolved flag.
  - Audited the milestone-assign path (`LeftSidebar.xaml.cs` ~4459, "Assign Chat to
    Milestone..."): does NOT share the bug. A GitHub Milestone number is a different number
    namespace than `_lastBoardIssues` (real issues/epics) — `bt_chat_issues` (unconditional)
    is the sole intended persistence there and already worked; deliberately left without
    `resolveLive` (documented in-code) to avoid a collision risk (a milestone number
    accidentally matching an unrelated real issue number).
  - Audited `_api.LinkChatToIssueAsync`/`UnlinkChatFromIssueAsync` (HTTP path,
    `POST /admin/build-tracker/chats/assign-issue` + `.../unassign-issue` in
    `artifacts/api-server/src/routes/admin-build-tracker.ts`): confirmed the identical
    local-table-only gap. Added a `resolved: boolean` field to both responses (honest
    reporting) but deliberately did NOT add a live-GitHub-fetch fallback there — that
    endpoint's own doc comment says the number can be "a real GitHub issue/epic/milestone
    number" (three namespaces, one wire parameter), so a blind fetch risks linking to the
    wrong target. Filed as follow-up **#2075** (parented to #1787, board status "AI Batter
    Up") — needs an explicit signal from the caller before it's safe to add.
  - Verified: `dotnet build -c Release` clean (0 errors, 0 warnings). `tsc --noEmit` on
    `artifacts/api-server` shows pre-existing unrelated baseline errors only — none on the

    `ResolveAndPersistChatLinkAsync` was run transactionally against the real local Postgres

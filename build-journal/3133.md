## Log
- 2026-09-07T23:00:00Z — Started. Root cause already confirmed in issue correction comment:
  `whenDate()` in `web/shanes-life/public/app.js` assumed `isoDate` was a bare
  `"YYYY-MM-DD"` string and appended `T00:00:00` to it. The real value passed in
  (`item.lastPrice.observedOn`, from `item_prices.observed_on`) comes back as a full ISO
  timestamp (`"2026-09-07T04:00:00.000Z"`) because `item_prices.observed_on` is a SQL
  `date` column (confirmed in `migrations/021_item_prices.sql:35` — already the right
  column type, no schema change needed) but node-postgres parses `date` into a JS `Date`
  object, and the API layer's JSON serialization emits that as a full ISO timestamp, not
  a bare date string. Concatenating `T00:00:00` onto that produced the malformed
  `"...ZT00:00:00"` string, hence `Invalid Date`.
- 2026-09-07T23:10:00Z — ✅ DONE — Fixed `whenDate()` in `web/shanes-life/public/app.js`
  (commit `2a...` see git log) to slice the input down to its first 10 chars
  (`YYYY-MM-DD`) before reconstructing the local-midnight `Date`, so it handles both a
  bare date string and a full ISO timestamp identically. No schema/migration change
  needed — `item_prices.observed_on` is already the correct `date` column type
  (`migrations/021_item_prices.sql:35`); the mismatch was purely in front-end parsing of
  the API's serialized value. `push_deals`'s `validOn` default (`COALESCE($6,
  current_date)` in `src/core/prices.mjs:88`) is already correct — no change needed there.
  Verified with a standalone node repro: `whenDate("2026-09-07T04:00:00.000Z")` → `"today"`,
  `whenDate("2026-09-06")` → `"yesterday"` — both shapes now parse correctly. Branch
  `agent/3133-q1892` merged into `origin/main` (fast-forward, verified via

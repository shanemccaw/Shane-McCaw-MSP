### Finding 1 — `severity_matched` is the right tier source, but only for 87 of the 155 card checks (confirmed against real data)

The dispatch called `tenant_monitor_profiles.severity_matched` / `severity_label` "very likely correct". Checked against the local DB (testbed tenant `c4c814d4-…`, latest row per check; 199 checks observed):

- Real vocabulary of `severity_matched`: `critical`, `high`, `warning`, `info`, `low`, or **NULL**. (Rule vocabulary in `monitor_checks.severity_rules` additionally uses `medium`.)
- **NULL means two different things**: "rules exist and none fired" (a genuine *good*) and "this check has no severity rules at all". Of the 155 design card keys, **68 have `severity_rules = []`** (e.g. `governance:guest-count`, `teams:meeting-policy-coverage`, `cost:group-based-licensing-adoption`).
- Consequence: for those 68, nothing in the platform judges the value, so painting them `good` ("Fully covered", as the design does for e.g. Guest accounts) would be a fabricated verdict. They render as a fifth, neutral state — **"Measured — nothing grades this"** — a deliberate, documented departure from the design's four tiers, and reported as a design gap (finding filed at DONE).
- Tier mapping (one pure, unit-tested function): non-`ok` statuses → `na` (with the real reason); `ok` + `critical|high` → `bad`; `ok` + `warning|medium` → `meh`; `ok` + `info|low` → `meh`; `ok` + NULL + check has rules → `good`; `ok` + NULL + no rules → *ungraded*. The `info|low → meh` choice is the one judgement call; it lives in one place so Shane can flip it.
- Real status distribution for context: 1298 ok / 598 error / 259 license_gap / 110 service_not_configured / 9 partial rows.

### Finding 2 — `resolveDriftEvents` reads "clean" for a domain the collector says is not comparable

Live: tenant `c4c814d4-…` domain `ca-policy` has a baseline snapshot (2026-09-16) **and** `drift_collection_status.status = 'not_comparable'`, reason `gate_not_satisfied`. `resolveDriftEvents` only consults `drift_collection_status` when *no baseline exists* ([L750–L766](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/e2cd630a8d9deedcf3c72bcc3fe4c91da80bfc6b/artifacts/api-server/src/lib/dashboard-resolvers.ts#L750)), so it returns `ok, events: []` — a fabricated "no drift". The new panel therefore reads the **collection status first** and the baseline/event counts second. The resolver itself is left untouched (other dashboards depend on it) and filed as a finding.

## User Review Required

**The group-curation home is resolved from existing precedent — no Ask-Shane sibling filed.** Decision: a static module **`artifacts/api-server/src/lib/pillar-signal-specs.ts`**, sibling to and modelled exactly on [`PILLAR_STAT_SPECS`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/e2cd630a8d9deedcf3c72bcc3fe4c91da80bfc6b/artifacts/api-server/src/lib/pillar-summary-stats.ts#L409). Why, and why not the alternatives:

- **Precedent, not a fork in the road.** #4560 already established that a customer-facing tile names its check key *and* value field explicitly, in a static per-pillar spec table in api-server, checked by a contract test against the live catalog. A signal card is the same idea one level down; anywhere else would split "which field is this number" across two homes.
- **Not `lib/dashboard-registry`** (the dispatch's "e.g."): that package is the *metric* registry whose `sourceKey` indirection is exactly what #4560 documented as rotting three times (#441, #1103, #4560), and it has no notion of a per-card value field. It is also consumed by the admin dashboards, which have no use for pillar-page grid curation.
- **Not a DB table**: nothing concrete argues for one — no operator edits it, there is no per-tenant variation, and it is design copy that should be code-reviewed like the design it comes from. `monitor_checks` has no pillar or group column, and inventing one would put design metadata in an admin-editable catalog.
- The design's group *titles*, card *labels*, *icons* and *spans* are carried verbatim. Sub-captions that assert a demo tenant's state (e.g. "legacy auth is not blocked — MFA can be bypassed") are **not** carried — they would be false for other tenants; a definitional caption ("of 18 teams", "no activity in 90 days") is kept, otherwise none.

Two smaller departures, flagged so they are not discovered later:

1. **Delta source.** The dispatch names `monitorHistoryForTenant`. It is a private function ([L607](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/e2cd630a8d9deedcf3c72bcc3fe4c91da80bfc6b/artifacts/api-server/src/lib/dashboard-resolvers.ts#L607)) that issues one query per check (~60 per pillar) and picks the value field with `pickMappedValueField`'s token heuristic — the exact behaviour #4560 removed for tiles because it can put the wrong number under a caption. The delta instead comes from **one windowed read** (last 5 stored rows per check for the tenant) resolved with the *same explicit `valueField`* as the current value, so a delta can never disagree with its own value. Same table, same shape, no heuristic.
2. **Neutral "ungraded" state** (Finding 1).

## What was actually happening (diagnosis)
Queried the live `bt_issue_mirror_sync_state` against the real local DATABASE_URL:
- `last_full_sync_at = 2026-09-07T22:08:13.680Z` (**non-null → a successful sync DID set it**)
- `last_sync_ok = false`, `last_sync_note = "issues walk failed: 403 (Forbidden)"`
- `bt_issue_mirror` = 527 rows (470 open), all `last_synced_at ≈ 22:08:13`.

Grepped the real durable ActivityLog (`%AppData%\BuildConsole\logs\activity-2026-09-07.log`):
**111 `issue-mirror` lines**, showing successful syncs on a clean ~5-6 min cadence
(17:37, 17:43, 17:49, 17:55, 18:01, 18:08 all "sync ok — 463..470 open issues, 3104..3112
board statuses"), interleaved with intermittent `sync ABORTED ... 403 (rate-limit circuit
open (Git #2815))` and one `403 (Forbidden)`.

**Conclusion:** The sync is NOT broken and is NOT failing to run — it runs successfully every
~5 minutes and the mirror is genuinely populated (527 rows). Of the 4 candidate scenarios in
the body, the real one is: the **observability gap** the issue itself predicted (scenario 1).
The 403s are the already-tracked #2815 rate-limit circuit (transient, self-heals ~60s), not a
new failure. The "ZERO matches" observation is explained by the two SILENT early-returns in
`MaybeSyncAsync`: on a fresh cold start where `last_full_sync_at` is still recent from a prior
session, the very first call silently no-ops and keeps silently no-op'ing for the whole 5-min
window — indistinguishable from "never wired." (A grep of the in-app Activity Log panel, which
drops pre-subscribe startup lines per #815/#911, would also read empty in that window; the
durable on-disk file is authoritative and had 111 lines.)

## What shipped
`desktop/BuildConsole/Services/GitHubIssueMirror.cs` — `MaybeSyncAsync` now logs a throttled
`issue-mirror` line on every path that used to return `null` silently:
- **still-fresh skip** — "skip: mirror still fresh (last successful sync Xm ago …)", and when
  the last recorded attempt failed it appends the real note (so an intermittent #2815 403 is
  visible here without a DB query).
- **failed-attempt backoff skip** — "skip: backing off after a recent failed attempt …".
- **single-flight in-flight** — "skip: a full sync is already in flight …" (proves the sync IS
  working when a slow ~40s sync spans ticks).
New `MaybeLogSkip` helper throttles these to ≤1 line / 60s (reset when a real attempt starts)
so a no-op is grep-visible without per-30s-tick spam.

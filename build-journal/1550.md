  CR from the policy's pre-approved catalog item (#1550)".
- 2026-08-30 ✅ DONE — Built exactly that missing piece, integrated additively on top of
  the already-landed work rather than duplicating or fighting it:
  - **`lib/policy-enactment.ts`** (new) — `raisePolicyEnactmentChangeRequest`: raises a
    real, auto-approved `changeClass: "standard"` change request from a standing
    policy's bound `change_catalog_items` row, inheriting that item's real signed
    approver into both `msp_change_requests.approved_by` and the `cr_approvals` ledger
    (`approver_role: "catalog_inherited"`) via the existing
    `materializeApprovalsForChange` — same machinery `portal-change-catalog.ts`'s
    customer-facing "execute" already uses, applied to the policy-enacted path.
    Live-checked every call, never cached (#1555's discipline reused): the policy must
    be `isActive` and its bound catalog item must be `approved` AT THE MOMENT of
    enactment.
  - **`lib/standing-policies.ts`** — added `evaluatePolicyEnactmentGate`, the pure,
    DB-free verdict rule both the CR-raise function and its tests share (same pattern
    as `change-control-write-gate.ts`'s `evaluateChangeRequestAuthorization`).
  - **`lib/sop-execution.ts`** — in `runSopForCustomer`'s Authorization step, a
    `standingPolicyId` run with NO explicit `changeRequestAuthorization` now
    auto-raises one via `raisePolicyEnactmentChangeRequest` instead of falling through
    to the testbed-only fallback — "approve once, execute many" applied to policy
    enactments. New error code `standing_policy_catalog_item_not_approved` (409) for
    when the bound catalog item is missing/draft/revoked at enactment time.
  - **`routes/msp-sops.ts`** — registered the new error code in `SOP_RUN_ERROR_STATUS`.
  - No schema/migration needed — `standing_policies.catalog_item_id`,
    `change_catalog_items`, and `msp_sop_runs.standing_policy_id` already exist on main.
  - Deliberately did NOT add a governed activate/deactivate lifecycle to
    `msp-standing-policies.ts` (an earlier draft of this build did) — `isActive` is
    already read directly and gated correctly by the concurrently-landed continuous-
    evaluation loop and enactment-route resolver; adding a second governance layer on
    top would have duplicated, not completed, that already-converged design.

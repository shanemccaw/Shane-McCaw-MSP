  **Four tables** (`lib/db/src/schema/config-snapshots.ts`, its own module — `config-state.ts`
  is the *model*, this is the *store*):

  | Table | Role |
  |---|---|
  | `config_snapshot_resource_types` | The curated, STABLE registry of what is collectable. Not a duplicate of `config_resources`: it holds the identity strategy no published source states, and the operational collect/don't-collect decision |
  | `tenant_config_snapshots` | Immutable point-in-time header, with an honest completeness summary |
  | `tenant_config_snapshot_objects` | One row per object, holding `object_json` — the real object, verbatim |
  | `tenant_config_snapshot_resource_status` | ONE row per targeted resource per snapshot, always, including skips and failures |

  **The four constraints the issue set, and how each is actually enforced:**
  - *Full fidelity* — `object_json` is the verbatim response, never a projection onto the derived
    property model. Per #1846 Graph returns properties its own `$metadata` does not declare
    (`createdDateTime`, `externalSourceName`, `sourceType` on `/devices` are in neither v1.0 nor
    beta CSDL), and a differ cannot see a property change it never stored.
  - *Immutable and point-in-time* — enforced by database triggers, not convention.
    `config_snapshot_reject_mutation_on_sealed` rejects UPDATE/DELETE on a sealed snapshot's
    objects and completeness rows; `tenant_config_snapshots_guard_immutable` refuses to rewrite
    `snapshot_id` / `tenant_id` / `entra_tenant_id` / `captured_at` or to re-open a sealed
    snapshot. Whole-snapshot retention deletion still cascades, which is the one legitimate case.
  - *Stable identity* — `identity_strategy` is declared per resource type, `unresolved` is a real
    state meaning "not collectable", and a CHECK constraint refuses to mark such a type
    collectable. Diff pairs on (`resource_key`, `object_identity`), unique within a snapshot.
  - *Honest completeness* — the `collected` / `empty` / `partial` / `skipped` / `failed` split
    makes "we could not read it" structurally distinct from "you do not have any", which is the
    exact conflation #1847 found in the `devices:*` checks. A CHECK constraint makes it
    impossible to write an incomplete outcome without its reason, or to mark a snapshot
    `is_complete` while anything was skipped or failed.

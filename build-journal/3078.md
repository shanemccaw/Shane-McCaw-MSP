- ✅ DONE 2026-09-07T17:22:00Z — Shipped, verified against the real database.

  **Live scope, re-measured.** #3078's body reported 21 duplicate groups, counted
  before its own #2983 migration ran and via a join through `users`. Counted directly
  on `customer_id` today: **45 `(customer_id, signal_key)` pairs holding 2-3 open rows
  apiece, 45 surplus rows**, across tenants 1 and 3, out of 168 open rows. Every
  duplicate pair's `fired_at` values sit milliseconds apart — the race, not a re-fire.

  A concurrent session purged the 103 NULL-scope orphan rows (#3077) between two of my
  queries; the 45 real-tenant duplicates above are the post-purge count and are what
  this issue is actually about.

  **Migration**, run in-session against the local `DATABASE_URL` (`UPDATE 45`,
  `CREATE INDEX`, one transaction so the constraint can never be built against
  violating data):
  1. Resolves the surplus rows, keeping the earliest `fired_at` per pair — the
     disposition recorded on #3078 itself. `resolved_at` is stamped with the duplicate
     row's *own* `fired_at`, not `now()`: a duplicate never represented a distinct open
     period, so a zero-length interval is the honest record, where `now()` would inject
     a phantom "just resolved" event weeks late into resolution history and into every
     duration-based read (SLA timers, Signal Policy Engine).
  2. Creates `tenant_signal_history_one_open_per_signal` — UNIQUE on
     `(customer_id, signal_key) WHERE resolved_at IS NULL`. Partial, because a signal
     legitimately re-fires once resolved. Non-`CONCURRENTLY` on purpose despite the
     issue body's suggestion: `CONCURRENTLY` cannot run inside a transaction, and
     splitting dedupe from constraint leaves a window in which the very writer being
     fixed re-introduces a duplicate and fails the index build. Table is ~6.5k rows.

  Rows with a NULL `customer_id` are deliberately untouched — #3077's territory, no
  live writer produces them, and a btree unique index treats their NULLs as distinct.

  **Code.** `recordSignalTransitions`'s INSERT is now
  `ON CONFLICT (customer_id, signal_key) WHERE resolved_at IS NULL DO NOTHING
  RETURNING id`; zero rows back means a concurrent evaluation won, logged at `info`
  (`engine.signals`) since that is the only place the race is observable. The Drizzle
  schema carries the index so the TS definition and the database agree.

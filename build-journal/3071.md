## Log
- 2026-09-07T02:10:00Z — Session started. Read #3071 body + comment. Root cause confirmed:
  `StartupGitHubCoordinator.RunAsync` (Services/StartupGitHubCoordinator.cs, landed via #3022)
  uses `ConfigureAwait(false)` on its internal awaits (`_gate.WaitAsync`, `await work()`,
  `Task.Delay` settle gap, and the generic `RunAsync<T>` overload). The critical one is the
  `_gate.WaitAsync(...).ConfigureAwait(false)` at line 106: after acquiring the semaphore, the
  continuation (which then calls `work()`) resumes on a ThreadPool thread instead of the
  original UI thread, so `work()` — and any UI-touching code before its own first await
  (e.g. `RenderIssuesTreeAsync`'s `ItemCollection.Clear()`) — silently runs off-thread and
  crashes with `InvalidOperationException: The calling thread cannot access this object
  because a different thread owns it.`
- Fix: remove `ConfigureAwait(false)` from every await inside `StartupGitHubCoordinator`
  (both `RunAsync` overloads) so execution resumes on the original (UI) SynchronizationContext
  throughout, matching the rest of the WPF codebase's convention for UI-adjacent async work.
- Audited all 5 wrapped subsystems (Home reconciliation, In-Flight tile, orphan recovery,
  blocked-by sweep, title warm-up) per #3022 — none has a genuine reason to run its portion off
  the UI context; they're all startup GitHub-call operations that report back into UI-bound
  state (Activity Log entries, tree/tile rendering). No subsystem-specific override needed;
  default to preserving context everywhere in this file.

## Log
- 2026-08-30 ⏳ IN FLIGHT — reading LeftSidebar.xaml.cs PopulateGitGraph/RefreshGitStatus/SetupGitWatcher/OnWorkspaceFileSystemEvent and all RefreshGitStatus callers; instrumenting OnWorkspaceFileSystemEvent to find the real churn source before fixing anything.
- 2026-08-30 ✅ DONE — **Diagnosis (evidence, not the issue's guess):** a live BuildConsole.exe (PID 6016) was running and actively logging the exact reported pattern (`[git-panel.graph] rendered 40 commit(s) across N lane(s)` every ~1.5-3s). Rather than editing+relaunching that live GUI process (which would have disrupted it), I ran an external `System.IO.FileSystemWatcher` probe (identical `Path`/`IncludeSubdirectories=true`/`NotifyFilter` to `SetupGitWatcher`) directly against the live `RootWorkspacePath` while that session was active. Result: 217 real filesystem events captured in one 30s sample, and the dominant, continuous churn was almost entirely `Changed` events on `<root>/.logs/activity-2026-08-30.log` and `<root>/.logs/activity-latest.log`. Traced to `ActivityLog.cs`'s `AppendToFile()`: every single `ActivityLog.Log()` call anywhere in the app (queue polling, version checks, and — critically — `PopulateGitGraph()`'s own `"rendered N commit(s)..."` line) unconditionally appends to those two files, which live INSIDE the watched tree. `IsIgnorableGitInternalPath` only filtered `.git/` internals, nothing under `.logs/`. This is a **self-sustaining feedback loop**, not "build output/node_modules churn" as the issue's own hypothesis guessed (though it did name "log files" as one candidate): the graph's own render writes a log line → refires the watcher → re-arms the 750ms debounce → triggers the next render → writes another log line, forever, even in an otherwise genuinely idle session. Re-ran the same probe with the new filter logic applied client-side and confirmed the `.logs/*` churn is fully eliminated from the captured event stream (one incidental unrelated burst was captured instead — a concurrent build session's `node_modules`/worktree-merge activity, real and expected, not a loop).
  **Fixes implemented** (`desktop/BuildConsole/Controls/LeftSidebar.xaml.cs`):
  1. `IsIgnorableGitInternalPath` now also ignores anything under `/.logs/` (mirrors the existing `.git/objects`, `.git/logs` reasoning — the app's own bookkeeping, not a real workspace change).
  2. `PopulateGitGraph()` returns immediately while `GitGraphHost.Visibility != Visible` (collapsed by default per #1898); `BtnGitGraphToggle_Click` now calls `PopulateGitGraph()` on expand so "current data the moment it's shown" still holds, just via a fresh fetch on expand instead of a fetch that silently already ran while hidden.
  3. Added `ComputeGitGraphSignature()` — a process-free cheap check (max mtime across `.git/HEAD`, `.git/packed-refs`, `.git/logs/HEAD`, `.git/refs/heads/**`) that gates `PopulateGitGraph()`: if nothing graph-relevant moved since the last real render, it returns without spawning `git log` or touching the visual tree at all. Verified empirically against a real scratch repo: signature is stable across an idle 2s window, and changes on both a real `git commit` and a real `git checkout -b`. Independently, `RefreshGitStatus()` now also compares the raw `git status --porcelain -b` text against the last call and skips the `GitChangesTree` visual-tree rebuild (Clear + re-add TreeViewItems) when byte-identical — `git status` itself still has to run since it's the cheapest available signal for working-tree-visible changes, but the expensive rebuild is skipped.
  4. `GitWatcherDebounceDelay` raised 750ms → 1500ms as a documented supplement only, not the fix — commented plainly that a longer debounce on a watcher that never goes quiet only slows a broken loop down, it doesn't stop one.
  Temporary instrumentation was never merged into the app itself (the external probe was the diagnostic instrument); no cleanup needed there.

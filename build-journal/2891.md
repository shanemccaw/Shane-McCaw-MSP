- 2026-09-04T20:45:00Z ✅ DONE — Root-caused and fixed. The reap loop (`TickAsync`) only reaps builds tracked in the in-memory `_running` dict via the authoritative `BuildProcessHandle.HasExited` on a real handle. A `bt_build_queue` row left `running` that this instance is NOT tracking — a `LaunchItem` that threw after the `GetNextAsync` claim (which flips the row to `running`) but before reaching `_running[item.Id] = entry`, or any other launch-path desync — was only ever reconciled by the STARTUP adoption sweep (`RecoverOrphanedRunningItemsAsync`), never during normal operation. So such a row sat `running` forever with no real `claude.exe` (exactly the #2888 incident: 19m27s "thinking...", zero output, no process in Task Manager, no branch/bookend/comment). Distinct from #1839, which only covers the restart-survivor case at startup.

  **Fix (commit 92f6d0bb6, `desktop/BuildConsole/Services/QueueWatcherService.cs`):** added a throttled (60s) in-tick phantom-running liveness sweep (`MaybeSweepStuckRunningRowsAsync` → `SweepStuckRunningRowsAsync`), placed in the reap section before the `_appReady`/`_paused` gates so a phantom is cleared even while paused. For every `running` DB row this instance is neither tracking (`_running`) nor actively launching (new `_launching` set):
  - **build_pid alive + creation-time fingerprint matches** (same #1839 `TryOpenExisting` + `GetProcessTimes` 1s-tolerance check, factored into `ProcessLivenessFor`) → leave it (never fail a live process).
  - **build_pid gone / already-exited / pid reused by a stranger** → mark failed -2 (`MarkOrphanedFailedAsync`), mirror to Crashed board column, free the slot automatically. No `BuildFinished` fired (matches the startup orphan path — a phantom produced no committed work to deploy).
  - **no build_pid ever stamped + row aged past a 5-minute grace on `updated_at`** → same failed -2 treatment (a launch that died before ever spawning).
  Guards: gated on the direct-DB path (`_db != null`), the #943 second-console guard is reused (never fail a row another instance may legitimately own), and the new `_launching` set brackets the WHOLE `LaunchItem` (via a thin wrapper around the renamed `LaunchItemCore`) in a try/finally — so a build mid-provision (worktree checkout can take minutes, no pid, not yet in `_running`) is never mistaken for a phantom, while a `LaunchItem` that THROWS correctly leaves the set and becomes visible to the sweep.

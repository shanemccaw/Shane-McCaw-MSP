- 2026-08-28 ✅ DONE — Root cause found and fixed. This was NOT the Build Watch
  `reportProgress`/checklist-bridge panel (#1206/#1251's subject) — it's the
  separate claude.ai-tab **context meter** (`ChatContextMeterScript` /
  `UpdateContextMeter` in `MainWindow.xaml.cs`), the progress bar Shane watches
  while chatting directly in the embedded claude.ai WebView2 tab. Confirmed via
  `claude_chat_temp.txt`: claude.ai virtualizes its chat transcript — only a tail
  window of `data-testid="transcript-row"` elements stays mounted in the DOM (a
  real 1238-message conversation had just 11 rows mounted, flanked by a
  `transcript-spacer` placeholder and a "Load earlier messages" button that never
  gets clicked). `ChatContextMeterScript` counted
  `document.querySelectorAll(selectors).length` directly, which plateaus at the
  virtualization window size the moment a conversation outgrows it — exactly the
  "starts working, then stops updating" symptom, not a report-count/rate-limit
  issue on the agent-protocol side at all.

  Fix: every mounted message article carries a real `aria-setsize`/`aria-posinset`
  attribute (e.g. `aria-setsize="1238"`) reflecting the conversation's TRUE total
  regardless of what's mounted (with an `aria-label` "Message X of Y" fallback for
  markup that only carries it there). `ChatContextMeterScript.cs` now reads that
  for `turnCount`, and extrapolates `charCount`/`heavyTurnCount` from the mounted
  turns' average when the true total exceeds what's mounted, instead of silently
  freezing. The Git #1436 "selectors likely stale" self-diagnostic is kept keyed
  off `mountedTurnCount` (the content selectors), independent of the new
  aria-setsize signal, so a genuine markup rename still surfaces correctly.

  Verified with a live regex-based extraction against the real captured page
  source (`claude_chat_temp.txt`): old logic reports a frozen `turnCount` of 11;
  new logic correctly reports 1238, matching the real conversation length. No
  WebView2/browser available headlessly here, so this real-fixture extraction is
  the closest available live verification — the same DOM attributes and structure
  drive the actual injected script.

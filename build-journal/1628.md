# #1628 — Chat context meter is stateless — accumulate, latch, persist

- **Status:** ✅ DONE
- **Scope:** buildconsole
- **Started:** 2026-08-29
- **Commit(s):** 4a80a6853 (on `origin/main`)

## Log
- 2026-08-29 ⏳ IN FLIGHT — successor to #1468 (virtualization plateau, fixed) on the same
  claude.ai context bar. Second root cause: the whole scrape→UI pipeline is stateless — every
  2s poll recomputes the total from whatever is currently mounted and `UpdateContextMeter`
  overwrites state unconditionally, so DOM churn (a heavy turn unmounting, a mid-render/streaming
  poll) drops the bar even though the real conversation only grew. Fix per #1628 body: an in-page
  accumulator keyed by stable per-message identity (`aria-posinset`, fallback transcript-row
  index) and by conversation id, that never deletes an unmounted row and reports the accumulated
  sum; aria-setsize extrapolation only for turns evicted before ever observed; a per-conversation
  monotonic high-water clamp in-script; host-side persistence of `{conversationId → estTokens,
  turnCount, heavyTurnCount}` (new `ChatContextMeterStore`, mirroring `ChatUrlStore`) that clamps
  incoming values to the persisted high-water and restores a reopened chat; plus removing the
  `_contextMeters` entry when its WebView unloads (the pre-existing leak).
- 2026-08-29 ✅ DONE — `4a80a6853` on `origin/main` (HEAD verified an ancestor of
  `origin/main`; `git status --porcelain` clean). What shipped:
  - `ChatContextMeterScript.cs` — rewritten around a persistent in-page accumulator
    (`window.__bcCtxStore`) keyed by conversation id and by stable per-message identity
    (`aria-posinset`, falling back to the mounted `transcript-row` index only when no
    article carries posinset). Each mounted row's length is recorded monotonic-per-key
    and **never deleted when the row unmounts**; the meter reports the accumulator sum,
    not the mounted sum. aria-setsize extrapolation now covers **only** turns evicted
    before ever observed (`observedSum + avg × (trueTotal − observedCount)`), not the
    whole conversation. Per-conversation monotonic high-water clamp in-script;
    `conversationId` emitted on `BT_CHAT_STATS`. The #1436 stale-selector diagnostic is
    preserved, still keyed off the mounted content-selector count.
  - `ChatContextMeterStore.cs` (new) — persists high-water `{conversationId → estTokens,
    turnCount, heavyTurnCount}` to `%APPDATA%/BuildConsole/context-meter-highwater.json`,
    mirroring `ChatUrlStore` (static store, load in cctor, save on write). `Merge` clamps
    incoming to the stored max per field and writes back on a new maximum.
  - `MainWindow.xaml.cs` — `UpdateContextMeter` takes `conversationId`, clamps/persists
    via `ChatContextMeterStore.Merge` before touching the bar (recomputing cost/buffer
    from the clamped total), so a reopened chat restores its level on the first post-load
    poll and a brand-new chat (no `/chat/<uuid>` id yet) starts at zero. `BT_CHAT_STATS`
    handler parses `conversationId`. `ChatContextMeterState` gained a `ConversationId`
    field. `DisposeWebView2Descendants` (now an instance method) removes the
    `_contextMeters` entry when a chat WebView is disposed — the leak fix (#4).
  - **Verification:** `dotnet build desktop/BuildConsole/BuildConsole.csproj -c Release`
    clean — 0 errors, 46 pre-existing warnings, none in the touched files. A standalone
    unit test of the accumulator algorithm (run from `%TEMP%`, then deleted — not
    committed) simulated the exact reported symptom: a heavy 20k-char turn observed while
    mounted, then scrolled out of a 6-row virtualization window as the chat grew to 30
    turns. The reported char total rose to 24000 when the heavy turn was seen and kept
    climbing to the true accumulated 49000 as it unmounted — **monotonic non-decreasing
    across every poll**, turn count reaching the real 30. Old stateless code dropped here.

# #4556 — Plan: AND-of-OR support for `monitor_checks.required_service_plans`

## Problem Description

`monitor_checks.required_service_plans` (added #4512, `lib/db/src/schema/msp.ts:2389`) is
evaluated by `tenantHasRequiredLicense()`
(`artifacts/api-server/src/lib/license-gate.ts:138-144`):

```ts
export function tenantHasRequiredLicense(
  requiredSkus: readonly string[] | null | undefined,
  tenantServicePlanNames: ReadonlySet<string>,
): boolean {
  if (!requiredSkus || requiredSkus.length === 0) return true;
  return requiredSkus.some((sku) => tenantServicePlanNames.has(sku));
}
```

This is **ANY-OF only** (`.some()`). `identity:ca-device-compliance`
(`lib/db/migrations/manual/2026-09-17-ca-device-compliance-real-state-4534.sql`) needs the
CA grant `compliantDevice` to ever be satisfiable, which requires **both**:
- Entra ID P1 or P2 (`AAD_PREMIUM` / `AAD_PREMIUM_P2`) — to create/enforce the CA policy, and
- Intune (`INTUNE_A`) — to actually mark a device compliant.

Today the check's `required_service_plans` is `["AAD_PREMIUM","AAD_PREMIUM_P2"]` — a tenant
with P1 but no Intune passes the license gate and runs the real policy read, even though
`compliantDevice` can structurally never be satisfied for that tenant.

## Root Cause Analysis

`tenantHasRequiredLicense`/`required_service_plans` was built for the #4512 three-CA-criticals
case, where a single ANY-OF group (P1 or P2) is the whole requirement. #4534 reused the same
column/shape for `ca-device-compliance` and explicitly deferred the AND gap as a documented,
not-built-in-that-pass limitation (see the migration's own `NO ENTRA ID P1` comment block).

Confirmed via direct query against local Postgres (`monitor_checks`,
`write_action_catalog`) that **only** `identity:ca-device-compliance` has a real unmet AND
requirement:
- `identity:ca-mfa-coverage`, `identity:ca-legacy-auth-block`, `identity:ca-policy-count`
  (all `required_service_plans = ["AAD_PREMIUM","AAD_PREMIUM_P2"]`) only need P1/P2 — MFA,
  legacy-auth-block and policy-count grants don't touch device state, so no Intune requirement.
- All 12 `write_action_catalog` rows with `required_license_skus` set (Conditional Access
  domain, ids 133-141, 214-216) are generic "Create/Update/Delete CA policy" actions that can
  create any kind of CA policy — none is scoped specifically to a device-compliance grant, so
  none has an unmet AND requirement either.

`config-pack-preconditions.ts:64-70,126-131` already has a real, working AND-of-OR pattern one
layer up — `requiredLicenseSkuLists: string[][]`, each inner array an ANY-OF group, evaluated
with `.every((skus) => tenantHasRequiredLicense(skus, ...))` across multiple catalog rows. This
build reuses that same array-of-arrays shape *inside* `tenantHasRequiredLicense` itself, so
every current and future caller (monitor-executor, Launch Control, Config Pack) gets AND-of-OR
for free from one shared implementation instead of each caller re-deriving it.

## User Review Required

**Schema-shape decision (flagged per dispatch note):** extending `tenantHasRequiredLicense`
to accept **either** a flat `string[]` (existing ANY-OF meaning, unchanged — all 4 existing
`monitor_checks` rows and all 12 `write_action_catalog` rows keep their current flat-array
shape and behavior with zero data migration) **or** a nested `string[][]` (new: AND across
groups, ANY-OF within each group — detected by `Array.isArray(requiredSkus[0])`).

This was chosen over (a) a second `required_service_plans_all_of` column, because it needs no
new column and no caller has to read two columns and combine them, and (b) an explicit
`{anyOf: [...]}` discriminator object, because the array-of-arrays shape is already a proven,
shipped pattern in this exact codebase (`config-pack-preconditions.ts`'s
`requiredLicenseSkuLists`), so this reuses an established convention rather than inventing a
third shape. Flagging in case a discriminator column is preferred for future readability —
happy to swap if so, but proceeding with array-of-arrays as the lower-disruption default.

## Proposed Changes

1. **`lib/db/src/schema/msp.ts`** — widen `requiredServicePlans`'s `$type` from `string[] |
   null` to `string[] | string[][] | null`, update the doc comment.
   https://github.com/shanemccaw/Shane-McCaw-MSP/blob/main/lib/db/src/schema/msp.ts#L2389
   (line number as of `3b83f0f02`, pre-this-build)

2. **`artifacts/api-server/src/lib/license-gate.ts`**
   - `tenantHasRequiredLicense`: detect a nested `string[][]` (first element is an array) and
     evaluate `.every(group => group.some(sku => tenantPlans.has(sku)))`; flat `string[]`
     behavior unchanged.
   - `licenseFeatureName`/`describeRequiredLicense`: produce readable text for the nested case
     — e.g. `"Microsoft Entra ID P1 or P2 and Microsoft Intune"` (groups joined with `" and "`,
     each group's SKUs joined with `" or "` as today).
   - Add `INTUNE_A: { family: "Microsoft Intune", label: "" }` to `LICENSE_SKU_DISPLAY` so
     Intune gets a real display name instead of falling back to the raw SKU string.
   https://github.com/shanemccaw/Shane-McCaw-MSP/blob/main/artifacts/api-server/src/lib/license-gate.ts

3. **`monitor-executor.ts`** — no code change needed. The existing `Array.isArray(...) &&
   .length > 0` guard and the calls into `tenantHasRequiredLicense`/`licenseFeatureName`
   already pass the raw column value through; both functions now handle the nested shape
   transparently.

4. **New migration** `lib/db/migrations/manual/2026-09-17-ca-device-compliance-all-of-intune-4556.sql`
   — additive, idempotent UPDATE of the one `identity:ca-device-compliance` row:
   `required_service_plans = '[["AAD_PREMIUM","AAD_PREMIUM_P2"],["INTUNE_A"]]'::jsonb`, updated
   description, `schema_version = schema_version + 1`. Guarded on the current flat-array value
   so a re-run is a no-op. Run locally in-session against `DATABASE_URL` (additive DDL/DML per
   CLAUDE.md); Replit/Staging carries it via the #1630 release checklist.

5. **Tests** — extend `license-gate.test.ts` (`tenantHasRequiredLicense`, `licenseFeatureName`,
   `describeRequiredLicense`) with nested-group cases, and extend
   `monitor-executor.test.ts`'s `identity:ca-device-compliance` `describe` block with a
   "P1 present, Intune absent → still a license gap" case alongside the existing "no P1"
   and "P1 + policy" cases.

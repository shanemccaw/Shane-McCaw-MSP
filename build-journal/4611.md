## Changes Made

`desktop/BuildConsole/Services/QueueWatcherService.cs` — `LaunchItemCore`, immediately before the
existing `if (!string.IsNullOrWhiteSpace(item.ResumeSessionId))` branch that adds `--resume` to the
launch args (previously unguarded, ~line 3002): when `item.ResumeSessionId` is set, call the
already-existing `LiveQueueIdsForSession(item.Id, item.ResumeSessionId)` (the same helper
`LaunchContinuationAsync` already trusts for its own click-time refusal). If it returns any live
queue id(s), the launch is refused — log a clear `ActivityLog` line naming the colliding queue
id(s)/session, call `MarkLaunchFailedAsync(item.Id, reason)`, and `return` — matching the existing
fail-closed pattern every other pre-flight guard in this same method already uses (worktree
provisioning failure, exe not found, unusable secondary/primary account).

This is a real backstop, not a duplicate UI check: `LaunchItemCore` is the one call site every real
launcher funnels through (the periodic pickup loop, `ForceLaunch`, `LaunchItemExplicit`,
`SessionLimitAutoRestartService`'s resume-from-limit-pause, and `LaunchContinuationAsync`'s own
`SafeLaunch`), so it now covers the two dispatcher paths the issue identified as reaching this
point with no upstream UI click to have guarded them (a continuation left `queued` at the hard cap,
and a `limit-paused` row flipped back to `queued` with `resume_session_id` preserved).
`LaunchContinuationAsync`'s own legitimate resume path is unaffected — it always stops and confirms
the old process's exit via `StopForContinuationAsync` before its `SafeLaunch` call reaches
`LaunchItemCore`, so `LiveQueueIdsForSession` correctly returns empty for it.

No new schema/endpoint/UI work — this issue is a pure backend liveness-guard bugfix in the WPF app,
out of scope for the portal/marketing `*Data.ts` and test-manifest rules.

  **The auth answer** (from `MSCloudLoginAssistant/WorkloadEndpoints.psd1`,
  `Workloads/PowerPlatformREST.ps1` and `MSFT_PPAdminDLPPolicy.psm1`, Dev branch,
  read 2026-08-30 — then proven with real calls):
  - scope `https://service.powerapps.com/.default`, audience
    `https://service.powerapps.com/`, host `api.bap.microsoft.com`
  - **a client SECRET is sufficient** — the opposite of `sharepoint-admin`, which mandates
    a certificate. No cert is needed and the module deliberately does not require one.
  - **the EXISTING multi-tenant app registration carries it.** No separate app
    registration and no new credential is required — token acquisition returned HTTP 200
    with `aud = https://service.powerapps.com`, `appid = 4743b130-…`, `tid = c4c814d4-…`.

  **The real blocker, proven not assumed:** every BAP admin read then returns HTTP 403 —
  *"The service principal with id … does not have permission to access the path … in
  tenant …"*. That is the unregistered-management-app signature. The BAP admin API does
  not authorise by Entra permission at all; the SP must be enrolled once per tenant via
  `New-PowerAppManagementApp`, and Microsoft documents that **a service principal cannot
  register itself**. The write app returns the identical 403, confirming it is not
  app-specific. Filed as #1906 with the exact commands; #1869 and #1906 both labelled
  `Shane To-Do`. Not attempted here — production tenant, and #1869 was scoped read-only.

  **Honest limit:** the tenant's real DLP posture is therefore **not yet observable**. This
  session does not claim the tenant has no DLP policy — "no policy exists" and "we cannot
  see the policies" are different statements and only the second is evidenced. The
  `PowerPlatformDlpPolicy` interface is sourced from Microsoft365DSC's own reads and is
  labelled as such, not presented as a captured payload.

  **Built:**
  - `artifacts/api-server/src/lib/power-platform-admin.ts` — new transport, read-only by
    construction (every call a GET; no write helper exists). `PowerPlatformNotRegisteredError`
    carries the enrolment gap as its own state so it is never conflated with revoked
    consent, a licence gap or an empty result, and never flips Graph consent.
    Channel `integration.powerplatform`.
  - `MONITOR_CHECK_EXECUTOR_TYPES` gains `power-platform` (fifth transport); dispatched
    from `monitor-executor.ts` like any other, via a code-owned `POWER_PLATFORM_OPERATIONS`
    registry (`dlp-policies`, `environments`, `tenant-settings`) keyed by the new
    `monitor_checks.pp_operation` column — identifier only, never a URL or script.
  - **"No executor exists" as a distinct coverage state** (#1849 point 3):
    `coverageStateFor()` / `transportHasExecutor()` / `EXECUTOR_BACKED_TRANSPORTS` in
    `config-state.ts`, derived from `MONITOR_CHECK_EXECUTOR_TYPES` so the two cannot drift.
    Wired through `/api/admin/config-resources` (summary totals, `coverage=no_executor`
    filter, per-row `coverageState`) and the operator page (fifth stat tile, red
    "no executor" badge, coverage % measured against the *reachable* model).
    Applied to `azure-rm` too, whose scope question stays open and unanswered.
  - No customer-facing checks written — explicitly out of scope for this issue.

# #4476 — plan

## Problem Description

`POST /api/public/purchase/payment-intent`
(https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157/artifacts/api-server/src/routes/public-purchase-payment.ts#L595)
computes `alreadyPaid` directly off the object returned by
`stripe.paymentIntents.create(..., { idempotencyKey })`:

```ts
alreadyPaid: intent.status === "succeeded",
```

When the same idempotency key is replayed (buyer paid, lost the page before
`payment-confirmed` landed, reloads and re-submits), Stripe does not return the
intent's live state on a replayed create — it returns the **saved response of the
first create call**, which is always `requires_payment_method`. `alreadyPaid` can
therefore never be `true` on the one path it exists to serve, and `Buy.tsx`'s
`intentData.alreadyPaid && intentData.paymentIntentId` recovery branch never fires.
Confirmed against real Stripe test mode in the issue body's probe script.

## Root Cause Analysis

`stripe.paymentIntents.create()` with an idempotency key that has already been used
returns Stripe's cached response body from the ORIGINAL call, not a fresh read of
the resource. The route trusted that cached body as if it reflected current intent
state. The correct live state requires a separate read
(`stripe.paymentIntents.retrieve(intent.id)`), which is not subject to idempotent
replay.

Doing that retrieve unconditionally on every `payment-intent` call would double the
Stripe API calls for the normal (non-replay) path, which is the common case. Stripe
node SDK exposes whether a response was a replay via the raw response headers on
`Response<T>.lastResponse.headers` — Stripe sets `Idempotent-Replayed: true` on a
replayed request. That lets the extra `retrieve` be scoped to only the recovery
path, matching the issue's explicit ask ("don't add it to the normal non-replay
path if that's a meaningfully hot path").

## Proposed Changes

In `artifacts/api-server/src/routes/public-purchase-payment.ts`
(https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157/artifacts/api-server/src/routes/public-purchase-payment.ts#L543-L596),
after `stripe.paymentIntents.create(...)`:

1. Read whether the response was a replay off
   `intent.lastResponse?.headers?.["idempotent-replayed"] === "true"`.
2. If it was a replay, call `stripe.paymentIntents.retrieve(intent.id)` and compute
   `alreadyPaid` from the retrieved intent's `status`. Otherwise keep the existing
   `intent.status === "succeeded"` check (fresh create — practically never
   succeeded synchronously, but harmless to keep for parity).
3. No other behavior changes; the response shape (`alreadyPaid: boolean`) is
   unchanged, so `Buy.tsx` needs no edit.

## Verification Plan

Local probe script against Stripe test mode (`STRIPE_SECRET_KEY` test key from
`.env.local`), for at least two of the three product categories (Monitoring and
Retainer, and ideally Packs):

1. Create a real checkout session for the product (via the existing purchase-flow
   tables/routes or direct DB insert matching `resolvePurchaseOrder`'s
   expectations).
2. `POST /api/public/purchase/payment-intent` → get `clientSecret` /
   `paymentIntentId`.
3. Confirm the intent directly via the Stripe SDK with `pm_card_visa` (test
   payment method), simulating what `Buy.tsx`'s Payment Element confirm would do.
4. Replay `POST /api/public/purchase/payment-intent` with the same `sessionId` (and
   same `packSlugs` for packs) so the same idempotency key is reused.
5. Assert the response now has `alreadyPaid: true` and the same `paymentIntentId`.
6. Confirm `Buy.tsx`'s existing `intentData.alreadyPaid && intentData.paymentIntentId`
   branch (unchanged) receives what it needs to complete the flow: it calls
   `payment-confirmed` directly with that intent id.

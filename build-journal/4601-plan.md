# Plan — #4601: `identity:mfa-method-breakdown` countWhere + severity_rules

- **Posted:** 2026-09-18T04:49:04Z

## Problem Description

`identity:mfa-method-breakdown` (endpoint `/reports/authenticationMethods/userRegistrationDetails`)
has two real, live-confirmed defects:

```
key                            | mapping                                                                                              | severity_rules
identity:mfa-method-breakdown  | [{"transform": "count", "sourceField": "methodsRegistered", "targetField": "legacyMfaMethodCount"}] | []
```

1. **Wrong semantics.** `methodsRegistered` is a real per-user array (Graph:
   `userRegistrationDetails.methodsRegistered`, `String collection`). Even after
   #4537's fix to the `count` transform (empty-array-aware), a plain `count`
   still counts every user with *any* registered method — it cannot distinguish
   legacy (SMS/voice) methods from phishing-resistant ones (FIDO2, Windows
   Hello), despite `targetField: legacyMfaMethodCount` and the check's own
   `description` ("Phishing-resistant (FIDO2/Windows Hello) vs SMS/legacy MFA
   methods in use") both promising exactly that distinction.
2. **Dead check.** `severity_rules: []` — the field can never produce a finding
   no matter what value it holds.

## Root Cause Analysis

The check was authored with a transform (`count`) that cannot express a
predicate, and no severity rule was ever attached. Not a regression from
#4537 — a pre-existing, separate gap filed against it directly (see #4601's
own body, filed while auditing all `count`-transform checks per #4537's own
follow-up instruction).

### Why `countWhere` can't filter `methodsRegistered` *entries* directly

Read `monitor-executor.ts`'s `countWhere` case
(https://github.com/shanemccaw/Shane-McCaw-MSP/blob/75710823099dc62287c0611e88c6b78828431072/artifacts/api-server/src/lib/monitor-executor.ts#L1847-L1928):
when `sourceField` resolves to an array on any item, `countWhere` walks the
array's own **entries** as the predicate's scope
(https://github.com/shanemccaw/Shane-McCaw-MSP/blob/75710823099dc62287c0611e88c6b78828431072/artifacts/api-server/src/lib/monitor-executor.ts#L1873-L1889),
but only accepts **object-shaped** entries — a scalar (string) entry is
explicitly skipped as non-object
(https://github.com/shanemccaw/Shane-McCaw-MSP/blob/75710823099dc62287c0611e88c6b78828431072/artifacts/api-server/src/lib/monitor-executor.ts#L1878).
`methodsRegistered` entries are plain strings (`"sms"`, `"fido2"`, …), so
`sourceField: "methodsRegistered"` with `countWhere` would silently produce
`count = 0` on every tenant (plus a `skippedNonObjects` warning) — not a fix,
a new dead check with different plumbing.

### The catalog's real, existing pattern for this exact shape

`identity:ca-legacy-auth-block` already filters a per-item **array field**
(`conditions.clientAppTypes`) via the whole-item scope, using the condition
grammar's `contains` operator, which is array-aware
(https://github.com/shanemccaw/Shane-McCaw-MSP/blob/75710823099dc62287c0611e88c6b78828431072/artifacts/api-server/src/lib/monitor-executor.ts#L807-L810):

```json
{"transform": "countWhere(\"{{state}} == 'enabled' && ... {{conditions.clientAppTypes}} contains 'other' ...\")", "sourceField": "value"}
```

`sourceField: "value"` is a member of `WHOLE_ITEM_SOURCE_FIELDS`
(https://github.com/shanemccaw/Shane-McCaw-MSP/blob/75710823099dc62287c0611e88c6b78828431072/artifacts/api-server/src/lib/monitor-executor.ts#L382),
so `countWhere` evaluates the predicate against each fetched item itself
(one user-registration-details row per item here), not against array entries.
This is the correct, already-proven shape for "does this item's array field
contain any of these values" — reused here rather than inventing entry-level
string filtering.

## User Review Required

**Legacy method value list** — the issue body specifies exactly
`sms`, `voiceMobile`, `voiceAlternateMobile`, `voiceOffice` as the Graph
values to treat as legacy. These are real Graph enum values for
`userRegistrationDetails.methodsRegistered` (SMS and the three voice-call
variants). No further product call needed here — using the issue's list
verbatim.

**Severity threshold** — the issue says "base the threshold/severity shape on
how comparable identity-domain checks in this catalog are structured, don't
invent a new pattern." The closest structural comparables are single-rule,
`count > 0` checks reporting a real security gap:
`identity:mfa-registration` (`"mfaRegistrationGapCount > 0"`, `warning`) and
`identity:legacy-auth-usage` (`"legacyAuthSignInCount > 0"`, `warning`).
Following that exact shape: one rule, `warning` severity, fires when
`legacyMfaMethodCount > 0`. This is a mechanical application of the existing
pattern, not a new product decision, so no stop-and-ask here.

## Proposed Changes

New manual migration `lib/db/migrations/manual/2026-09-18-mfa-method-breakdown-severity-rules-4601.sql`:

```sql
UPDATE monitor_checks
SET mapping = '[{"transform": "countWhere(\"{{methodsRegistered}} contains ''sms'' || {{methodsRegistered}} contains ''voiceMobile'' || {{methodsRegistered}} contains ''voiceAlternateMobile'' || {{methodsRegistered}} contains ''voiceOffice''\")", "sourceField": "value", "targetField": "legacyMfaMethodCount"}]'::jsonb,
    severity_rules = '[{"label": "{{legacyMfaMethodCount}} user(s) have a legacy (SMS/voice call) MFA method registered — phishing-susceptible compared to FIDO2/Windows Hello for Business", "severity": "warning", "expression": "legacyMfaMethodCount > 0"}]'::jsonb,
    updated_at = now()
WHERE key = 'identity:mfa-method-breakdown';
```

Run directly against local `DATABASE_URL` in this session (additive/corrective
data change to an existing row — no schema change, no destructive DDL; falls
under the "agent runs additive/corrective migrations itself" rule, not the
destructive-migration gate, which only covers `lib/db/drizzle/*.sql`).

No Drizzle TS schema change needed — `monitor_checks.mapping` /
`severity_rules` are existing `jsonb` columns, this only changes row data.

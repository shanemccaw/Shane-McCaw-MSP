## Answer to Shane's question

**Removing the box alone would not have made the floating card take focus.** The hypothesis assumed the card's own `cardInput.focus()` was still in the script and only losing a race to `TxtDomComment.Focus()`. It was not: #4447 (`71575585d`) deleted that call entirely. Since then, on every inspect click the C# call was the only focus claimant, so it won every time (not intermittently), moving OS focus from the WebView2 into the collapsed rail box. Removing it returns OS focus to the WebView2 (the native mouse-down had already put it there; the page script only intercepts `click`), but `document.activeElement` stays on the clicked page element, so you would still have had to click into the card.

To actually meet the goal, commit `635c3bc4c` restores a guarded `cardInput.focus()` in the in-page script. The race that made #4447 remove it needed a second claimant, and the rail box was that claimant.

**Measured (headless Chromium running the real `DomInspectorScript` extracted from the C# source, real mouse click on a page button, then typing + Enter):**

| | `document.activeElement` after click | typed text + Enter |
|---|---|---|
| Before (removal commit only) | the clicked page button (`target`) | no `VTT_DOM_BUG_SUBMIT` |
| After (`635c3bc4c`) | `__vtt_card_input` | `VTT_DOM_BUG_SUBMIT` with comment "typed without clicking the card" |

**Not verified:** real OS keyboard focus on the WebView2 HWND after a physical click inside BuildConsole. That rests on the native mouse-down behavior plus the fact that no `mousedown` handler prevents default. Driving or launching `BuildConsole.exe` is off-limits from a session (it can courier into Shane's live instance), so please confirm in your own running instance: click an element with the DOM Inspector on, type immediately, press Enter.

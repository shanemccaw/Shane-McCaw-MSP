## What shipped

The narrow bill-payment reference vault (#3150) is now a real, general password manager in
`web/shanes-life`, with the same security bar applied to the larger surface rather than a
lighter one.

- **`migrations/052_vault_password_entries.sql`** — run by me against the real local
  `finances` database in-session (`npm run migrate` -> `applied 052_vault_password_entries.sql`).
  Additive only: `kind` ('bill_reference' | 'login', defaulting so every existing 017 row keeps
  working), `username`, an encrypted notes triple (`notes_ciphertext`/`_iv`/`_auth_tag`, held
  all-or-nothing by a real CHECK), and `secret_updated_at` (real password age, distinct from
  `updated_at`, which also moves on a rename).
- **`src/core/vault.mjs`** — the AAD gained a field discriminator so a notes blob cannot be
  lifted into the password's columns and still decrypt; `"secret"` deliberately keeps the
  original un-suffixed string so every pre-#3242 row still opens. A login's mask is a fixed dot
  run — last-four leaks four real characters and a length-matched run leaks the length. Search
  runs over label/site/username, which is what the encryption permits.
- **`src/routes/api.mjs`** — `GET /api/vault` gained real server-side `kind` and `q` filters
  plus whole-vault counts; audit details carry `kind`/`notesChanged` and still no secret,
  no notes, no username.
- **`public/app.js` + `app.css`** — debounced search box, kind filter row, username-with-Copy on
  login rows (free: it is the half a sign-in page prints anyway), notes revealed inside the same
  20-second window under the same single assertion, and a real `crypto.getRandomValues` password
  generator with rejection sampling.

The vault stays off MCP and keeps its #3183 no-forms exception — `captures.body_text` is stored
in the clear and handed to a Claude conversation over a bearer token, so a password typed into
the universal capture box would be a readable password in a readable column before the vault
ever saw it. #3242 makes that exception stronger, not weaker.

## Open product decision — genuinely for Shane, asked on the issue

Issue scope item 4 ("new tab inside the existing Vault UI, or fold the bill-reference vault into
this one — ask rather than guess"). Built as **one vault with two real kinds**, filterable, which
is the fold-in answer done non-destructively: every existing bill reference is untouched and
still works. Chosen rather than blocked on because it is cheaply reversible — splitting into two
tabs later is a UI change over the same schema — and because two tables would have meant two
copies of the key handling, the assertion path and the audit trail. Asked explicitly in the issue
comment; say the word and it splits.

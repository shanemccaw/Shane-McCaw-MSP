- 2026-08-31 ✅ DONE — Shipped Phase 2: tab support added to the existing `FloatingChatWindow`
  (c29d67240). Real audit first confirmed Phase 1's shape: one `FloatingChatWindow` bound to a single
  `BoardChat` with one `ChatSafeWebView2` in a `Border BridgeHost`, `MainWindow.OpenFloatingChatWindow`
  closing/replacing any existing floaty, launched from the LeftSidebar chat-card context menu. EXTENDED
  that (did not rewrite): (1) introduced a private `FloatingChatTab` state object per open chat holding
  its own `BoardChat`, its own `ChatSafeWebView2`, last-captured markdown, a cached rendered
  `MarkdownRenderer` element, its unsent input draft, and its inline status — so switching tabs restores
  exactly what that chat looked like with no re-scrape and no lost draft. (2) `BridgeHost` changed from a
  single-child `Border` to a `Grid` that holds EVERY tab's WebView2 at once; only the ACTIVE tab's WV is
  `Visibility.Visible`, all inactive ones `Collapsed`. (3) A new tab strip row (Row 1) with per-chat chips
  (title + close ✕), hidden entirely when only one chat is open so a single-chat floaty still reads as the
  lightweight Phase-1 window. (4) `MainWindow.OpenFloatingChatWindow` now ADDS a tab (or focuses the
  existing tab) when the floaty is already up, instead of replacing the window; new `HasChat`/
  `AddOrActivateChat` on the window. The bridge itself (`FloatingChatBridgeScript` — insert+submit send,
  context-meter→markdown receive) is REUSED per-tab unchanged, wired with a per-tab
  `WebMessageReceived` closure so an inactive/throttled tab's frame updates only its OWN cached reply.
  Logging via `ActivityLog.Log("chat.floating", …)` (same channel #2059 used).
  **WebView2 hidden-throttle constraint (the Phase-1 carry-forward), resolved & documented for real:**
  a Collapsed WebView2 IS throttled — this is the exact same mechanism Phase 1 relied on to pause capture
  when the whole bridge strip is collapsed. So only the ACTIVE tab's bridge stays live/visible; each
  inactive tab's capture PAUSES the moment it's Collapsed and RESUMES (its 1.2s poll catches up to the
  latest assistant reply) when reactivated — i.e. an inactive tab does not update its rendered reply until
  you switch back to it. This is intentional and matches the answer the issue asked for: only the active
  tab's bridge needs to stay live. Each WV initialises its CoreWebView2 while it is the visible/active tab
  (a newly opened chat becomes active immediately), so nothing initialises while Collapsed — no reparenting.

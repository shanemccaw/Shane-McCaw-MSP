  **Audit first** confirmed the real send bridge (#2059/#2063/#2065): `FloatingChatWindow` holds one
  `FloatingChatTab` per open chat (keyed by `ConversationId`), each with its own `ChatSafeWebView2`; sending
  is `InsertAndSubmitAsync` → `FloatingChatBridgeScript.BuildInsertScript` (largest visible
  `div[contenteditable]` + `execCommand('insertText')`) then `SubmitScript` (click Send / Enter fallback)

  'no-composer' | 'error: …'`. #2063's `SendToActiveTabAsync`/`SendToActiveChatAsync` only ever target
  *whatever tab happens to be active* — wrong shape for a pin, which must land in the chat the question came
  from regardless of what's on screen. Added a parallel, narrower entry point instead of reusing the
  active-tab one: `FloatingChatWindow.SendToChatAsync(BoardChat, text)` resolves/creates the tab by
  `ConversationId`, activates it, polls (bounded 10s) for its `CoreWebView2` to be ready, then calls the SAME
  `SendToActiveTabAsync` — no new bridge mechanism, just correct tab targeting. `MainWindow.SendToChatAsync`
  opens the floaty (adding a tab, not replacing — matches `OpenFloatingChatWindow`'s existing behavior) if it
  isn't already up, awaits its `Loaded` event, then delegates.

  **DB:** `lib/db/migrations/manual/2026-08-31-chat-pinned-questions-2104.sql` — `chat_pinned_questions`
  (`chat_id INTEGER REFERENCES bt_chats(id) ON DELETE CASCADE`, `question_text`, `created_at`,
  `resolved_at`), same FK shape as the existing `bt_chat_issues` join table. Ran it myself against local
  `DATABASE_URL` (`CREATE TABLE`, 2x `CREATE INDEX`, self-marking `INSERT` — all succeeded). "Persists until
  resolved, silent auto-purge on stale/redundant, no archive list" (the issue's own words) implemented as:
  reads only ever return `resolved_at IS NULL` rows; resolving stamps `resolved_at` then a purge sweep
  deletes every already-resolved row in the same call — no archive table/view exists to browse; a partial
  unique index `(chat_id, question_text) WHERE resolved_at IS NULL` rejects a redundant duplicate pin at the
  DB layer (`ON CONFLICT ... DO NOTHING`). Verified all three paths directly against local Postgres before
  writing any C#: insert → duplicate insert returns 0 rows → resolve+purge leaves 0 rows. Added
  `BoardChat.Id` (previously only `ConversationId` was tracked) so C# can pass the real `bt_chats.id` FK.

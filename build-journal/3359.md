## Log
- 2026-09-10T00:05:00Z ⏳ IN FLIGHT — Migrating `GitHubIssueTimeSeriesService.GetAllIssuesAsync`
  (Home dashboard's burndown/velocity/ETA charts) off its own live
  `ListBoardIssuesAsync(GitHubIssueState.All)` per-5-min walk onto the local mirror.

  **Verified the closed-history question the issue body flagged (query, don't assume):**
  `bt_issue_mirror` holds 773 rows — 500 open, only 273 closed, and of those closed only
  31 carry a real `closed_at` (242 are NULL, marked-closed by the full walk without a
  timestamp). `min(created_at)=2026-07-28`, `min/max(closed_at)` both `2026-09-09` — i.e.
  the mirror has essentially NO historical closed-issue data (real repo has thousands of
  closed issues; v1.1 alone is ~947/1430). `bt_milestone_mirror` is empty (0 rows) so
  #3365-comment option (b) isn't even available, and milestone header counts can't
  reconstruct a per-day burndown anyway (no per-issue timestamps). **A like-for-like
  migration would produce a badly-wrong series — worse than today's fail-closed.**

  **Fix (option a, the closed-inclusive mirror — real backend, not a fixture):** the mirror
  already has every column the time series needs (created_at, closed_at, milestone_number,
  parent_number, sub_issue_count, child_issue_numbers) and `TryGetBoardIssuesAsync(openOnly:false)`
  already reconstructs the full `GitBoardIssue` shape. The only missing piece is *populating*
  the closed set with real timestamps. Adding a rate-limit-conscious closed-issue backfill
  (one `ListBoardIssuesAsync(All)` walk, gated to run ~once/24h inside the full sync, NOT
  per-tick — replacing Home's own per-5-min All walk), plus a `HasClosedBackfillAsync` gate so
  the time series reads live until the closed set is genuinely present. Then
  `GetAllIssuesAsync` reads mirror-first, falls back to live.

## Log
- 2026-09-16T00:00:00Z ⏳ IN FLIGHT — traced the race in `refresh-main-server.mjs` /
  `serving-checkout.mjs`; see `build-journal/4390-plan.md` for the full trace and fix
  design.
- 2026-09-16T00:20:00Z ✅ DONE — root cause confirmed: `refreshMainServer` called
  `verifyServingCheckout` exactly once, immediately after the weak
  `waitForFreshApiListener` "some new pid touched the port" signal fired -- landing in
  the gap before the rebuilt api-server actually finished binding (the real cycle
  `c-1789574065319-10396` bound :8080 ~4s after that one check ran). Fixed by adding
  `verifyServingCheckoutUntil` (serving-checkout.mjs), which retries the same real
  check for the rest of the rebuild's own `apiRestartTimeoutMs` budget, but ONLY while
  the failure looks like "still starting" (nothing listening / listener predates the
  rebuild / not yet attributable) -- any structural failure (commit genuinely missing,
  port held by a different checkout) still fails on the first attempt, unchanged.
  `refresh-main-server.mjs` now calls it with a deadline of
  `api.spawnedAt + apiRestartTimeoutMs` when an api restart happened.

  **Changes Made:** `scripts/dev-server/serving-checkout.mjs` (new
  `verifyServingCheckoutUntil` export), `scripts/dev-server/refresh-main-server.mjs`
  (uses it in place of the single `verifyServingCheckout` call for the api-restart
  path), `scripts/dev-server/serving-checkout.selftest.mjs` (new cases reproducing the
  exact race with an injected probe, plus a structural-failure case and a
  no-restart-in-flight case).

  **Verification Results:** reproduced the race directly (not just a code read) --
  an injected `readListeners` probe returns "nothing listening" on the first call and
  the real fresh listener on the second, matching the real cycle's shape exactly. A

  bug); `verifyServingCheckoutUntil` recovers on the very next attempt with no extra
  waiting once verified. A structural-failure case (port held by a different

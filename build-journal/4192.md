  **What landed.** `requireAccess(capability, tierModuleKey?)`, mounted after `requireAuth`, additive and opt-in — **zero** of the 616 `requireCapability` or 31 `requireTierFeature` call sites touched (`git show --stat` confirms: 6 files, all middleware/lib, no route file).   - **basis "rbac" → 403** carrying `requireCapability`'s own `denialMessage()` wording (exported from requireAuth.ts rather than re-worded), plus `details: { basis, capability }`.
  - **basis "entitlement" → 402** carrying `requireTierFeature`'s `TIER_UPGRADE_REQUIRED` body — now built by one shared `tierUpgradeRequiredBody()` both gates call, so the shape has a single definition — plus `basis`, the real `requiredTier` and `upgradePath` for #1135's upgrade panel.
  - **Either model unreadable → 503**, logged, never read as a denial. Tier-read failure included.
  - **The mandatory fix — every real denial is audited.** One `warn` on `logger.child({ channel: "auth" })` per denial, carrying `basis`, evaluateAccess's human-readable `reason`, capability, `effect`, `decidedBy`, principal and path, plus `moduleKey`/`requiredTier`/`currentTier` on an entitlement denial. Allows are deliberately not logged. This closes the gap #4191 found: neither existing gate logs a real deny today, only `unavailable`.

  **Ordering.** RBAC is decided FIRST with `tier: null`; the customer's subscription and the tier catalog are not merely unread but **never loaded** for a caller RBAC already denied — so a tier-read failure cannot turn a 403 into a 503. The second `evaluateAccess` call makes the composed decision, so one decision function still answers.

  **No drift by construction.** The evaluator input is built by `ladderEvaluationInput` (extracted from `roleClearsLadderCapability`) and `capabilityEvaluationInput` (extracted from `userHasCapability`); both existing gates now call those same extractions, so the gate and the composed gate cannot resolve a principal differently. Behaviour-preserving refactors — no call site, response or wording changed.

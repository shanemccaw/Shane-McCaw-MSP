## What shipped

- **`lib/db/src/schema/msp.ts`** — new `portalSopCustomStepsTable`
  (`portal_sop_custom_steps`: `customerId`, `sopId` [the opaque `msp_sops.sop_id`
  string, no FK — same convention `msp_sop_runs.sop_id` already uses], `position`,
  `title`, `description`, `basedOnVersion`, `addedBy`), unique on
  `(customerId, sopId, position)`. Also `mspSopRunsTable.sopVersion` — `msp_sops.version`
  captured at the instant a run starts, `notNull().default("")`.
- **`lib/db/migrations/manual/2026-08-30-sop-custom-steps-overlay-1558.sql`** — additive:
  `ALTER TABLE msp_sop_runs ADD COLUMN IF NOT EXISTS sop_version`, `CREATE TABLE IF NOT
  EXISTS portal_sop_custom_steps`, its two indexes, plus the self-marking
  `simulator_migration_runs` insert. Run against local `DATABASE_URL` in-session.
- **`artifacts/api-server/src/routes/msp-sops.ts`** — `POST /api/msp/sop-runs` now
  looks up the base SOP's current `version` at insert time and writes it as
  `sopVersion` on the new run row. Server-captured, not client-supplied.
- **`artifacts/api-server/src/routes/portal-sops.ts`** —
  - `GET /portal/sops`: `library[].steps` is now `{text, isCustom}[]` — the base
    definition's own steps followed by this tenant's overlay, one ordered list.
    `runnable`/`meta[id].auto` stay derived from the BASE steps only (a customer's own
    note can never make a procedure executable, matching how `POST /portal/sops`
    already forces a customer-authored SOP non-runnable by construction).
    `runs[].sopVersion` and (on `GET /portal/sop-runs`) `queue[].sopVersion` both
    surfaced, mirroring the `origin` field #1556 added.
  - New `POST /portal/sops/:sopId/custom-steps` — adds one step to the caller's own
    overlay on an existing MSP-authored SOP. 404s if the base SOP doesn't exist for
    this MSP (an overlay on nothing is meaningless — also where `basedOnVersion` is
    read from). Capped at 60 custom steps per SOP, same shape as the existing
    `POST /portal/runbooks/:runbookId/steps` precedent.

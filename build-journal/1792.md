## Log
- 2026-08-31 ⏳ IN FLIGHT — Implementing per-build Windows Job Object assignment in QueueWatcherService so spawned claude.exe (and its detached node.exe grandchildren) are cleaned up on the natural-completion path as well as the existing cancel/hard-kill paths. Per the locked-in correction: the job is scoped per-build and closed at that build entry's completion — closing BuildConsole must NOT kill in-progress builds.
- 2026-08-31 ✅ DONE — Shipped in `f7b7f8d47`.
  - **New `Services/WindowsJobObject.cs`** — P/Invoke wrapper: `CreateWithKillOnClose()` (CreateJobObject + SetInformationJobObject with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`), `Assign(hProcess)`, `TerminateAndClose()` (idempotent, deterministic `TerminateJobObject` reap of the whole tree), `DetachWithoutKill()` (clears the kill-on-close limit then releases the handle so members live on).
  - **`RedirectedProcessLauncher`** — launches the build `CREATE_SUSPENDED`, creates the job, `AssignProcessToJobObject` BEFORE the child runs an instruction (so no grandchild can escape the job), then `ResumeThread`. `CreateNoWindow` and all visibility behavior left exactly as-is. Job returned on `LaunchedProcess.Job`; degrades gracefully to pre-#1792 behavior if the OS refuses (thread is always resumed).
  - **`QueueWatcherService`** — stores the job per `RunningEntry`; `CloseBuildJob()` reaps it on (1) the natural-completion reap path (which did ZERO spawned-process cleanup before — the core bug), (2) `TryStop` (removes from `_running`, so it reaps directly), and (3) `HardKill` (now falls through to the Job Object backstop even if `Kill(entireProcessTree)` throws). Adopted builds (prior-instance launches) carry no owned job — unchanged.
  - **`MainWindow.OnClosed`** — new `DetachAllJobsForShutdown()` strips kill-on-close from every live build's job and releases handles WITHOUT killing, preserving the #1804 guarantee that closing BuildConsole never kills in-progress builds.
  - **App-close-does-not-kill was VERIFIED, not assumed.** The whole design is architected around it: the deterministic reap is the explicit per-build `TerminateJobObject` at that build's completion; the graceful-shutdown path actively neutralizes the kill-on-close limit for still-running builds. Honest residual: a *hard/forced crash* of BuildConsole (no `OnClosed`) would let the OS close the handles and `KILL_ON_JOB_CLOSE` reap in-progress builds — this is the one path graceful neutralization can't cover while honoring the issue's explicit request for the `KILL_ON_JOB_CLOSE` flag. Graceful close (File→Exit / window close) is fully covered. If Shane wants zero crash-risk instead, dropping the flag (relying solely on the explicit `TerminateJobObject`) is a one-line change — filed as a finding.
  - **Verification:** `dotnet build ... -c Release` clean (0 warnings, 0 errors). Ran a standalone harness replicating the exact launcher sequence (CREATE_SUSPENDED → CreateJobObject(KILL_ON_JOB_CLOSE) → AssignProcessToJobObject → ResumeThread) against a real process tree whose primary exits leaving a DETACHED grandchild, checked via the OS's own job PID list (`QueryInformationJobObject`): **TEST A** — grandchild survived the parent's exit but was still a job member; `TerminateAndClose` reaped the whole tree, nothing left alive (PASS). **TEST B** — `DetachWithoutKill` left the spawned process alive (app-close survival) (PASS).

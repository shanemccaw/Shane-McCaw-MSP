## Log
- 2026-09-09T18:47:00Z ⏳ IN FLIGHT — Investigating what drives `TopBatterUpCount.Text` / `TopAiBatterUpCount.Text` per the correction comment (Shane never opens the tab; he only watches the top-bar badges).

### Diagnosis (confirmed by code read)
- `_batterUpPanel` / `_aiBatterUpPanel` are permanent singletons — `MainWindow` fields built once (`MainWindow.BatterUpTabs.cs:40-41`), never destroyed. They live for the whole app lifetime regardless of whether their document tab is ever opened.
- The top-bar badges update ONLY via `CountChanged` → `SetCount` → `RefreshCoreAsync` → `RefreshAsync` (`MainWindow.BatterUpTabs.cs:49-52`).
- The automatic refresh path (#3253) is `GitHubIssueMirror.SyncCompleted` → `OnMirrorSyncCompleted` → `RefreshAsync`. That subscription is wired ONLY in each panel's `Loaded` handler and torn down in `Unloaded` (`BatterUpPanel.xaml.cs:87-99`, `AiBatterUpPanel.xaml.cs:74-86`).
- `Loaded` fires only when the panel attaches to the visual tree — i.e. only when the tab is opened. **Shane never opens the tab, so the subscription is never established, so the badge never auto-updates.** This is the confirmed primary cause of "the 5-min auto-update never visibly worked."
- The mirror sync itself fires `SyncCompleted` on every successful sync (`GitHubIssueMirror.cs:669-678`) on a 5-min interval driven by the QueueWatcher tick regardless of pause/readiness (`QueueWatcherService.cs:996-998`), so a constructor-time subscription genuinely delivers auto-updates without the tab ever opening.
- The only automatic caller of `RefreshAsync` that runs today is `LeftSidebar.BoardRefreshCompleted` (`MainWindow.xaml.cs:921-922`) — a MANUAL Git Board refresh / startup. That is why the badges only ever reflect the last manual refresh and manual refresh feels flaky.

### Fix
Move the `SyncCompleted` subscription from `Loaded` into each panel's constructor and never unsubscribe (drop `Loaded`/`Unloaded`). The instance is an app-lifetime singleton, so #3253's original concerns ("closed tab repaints off-screen" / "static event outlives the view") do not apply — the view IS the app-lifetime singleton, and the cheap off-screen render is exactly what keeps the always-visible badge fresh. This is the fix the issue's correction comment (point 3) proposed.

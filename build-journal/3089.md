- 2026-09-09T23:52:00Z ✅ DONE — Shipped as commit `02314deb5`.

  **The diff shape.** `buildCaPolicyDriftConfig` now keys by the policy's own Graph id. A creation is an `add` at `/policies/<id>`, a deletion a `remove`, a state flip a `replace` at `/policies/<id>/state`; a policy set Graph returns in a different order is no longer drift at all, and an add-one-remove-one between scans is exactly two per-policy events instead of "most fields of most policies changed". A policy set that cannot be keyed (an id-less policy, or two sharing one id) is refused as `not_comparable` with the specific reason rather than silently dropping a policy — a dropped policy would surface next scan as a `remove`, a deletion that never happened. `DriftSettingIdentity` loses `idField` and `resolveDriftSettingTarget` loses both its scan-items argument and #2819's positional baseline-order guard: the identity is now the path segment, so there is no position left to be wrong about. `monitor-executor.ts`'s `readDriftCollection` helper went with it.

  **The migration path — the part the dispatch asked for real care on.** `drift_baseline_snapshots` gains `config_version` (default 1, matching every pre-existing row) and `shape_migrated_at`; a spec declares `configVersion` + `migrateBaselineConfig`, and `collectDrift` upgrades a stale baseline **in place, on read, before it diffs anything** — same snapshot id, same `capturedAt`, same `signed` flag (a re-key changes no approved value), and the drift events attached to it have their positional setting paths rewritten to the real policy ids with their idempotency keys rebuilt to match. Deliberately in place rather than a re-baseline: a re-baseline adopts today's config as the approved reference and silently blesses any drift accumulated since the baseline was signed. Doing it on read rather than only in SQL is what keeps an environment whose manual migration has not run yet (Staging before its release step, a restored DB, a baseline captured between deploy and migration) from diffing two dialects and reporting a whole tenant as drifted. Two honest fallbacks: a baseline that genuinely cannot be keyed is superseded and re-captured with the real reason recorded on `drift_collection_status` (lossy, and stated as such), and a baseline **newer** than the running build is refused outright — `not_comparable`, never re-baselined over, so a rolled-back deploy cannot destroy a reference a newer build is still using. Bumping `configVersion` without supplying a migration is also caught and refused.

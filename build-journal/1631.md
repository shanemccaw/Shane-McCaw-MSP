- 2026-08-29 ✅ DONE — `wv.AcceleratorKeyPressed` doesn't exist in this repo's installed SDK
  (`Microsoft.Web.WebView2` 1.0.4129.50): confirmed by direct reflection against the resolved
  assembly and then definitively by a real `dotnet build` (CS1061 — `WebView2` does not contain a
  definition for `AcceleratorKeyPressed`). Neither `CoreWebView2Controller` nor
  `AcceleratorKeyPressed` are publicly exposed on the WPF `WebView2` control in this SDK version —
  both are internal. Adapted to the supported extensibility point instead: added
  `desktop/BuildConsole/Controls/ChatSafeWebView2.cs`, a small `WebView2` subclass overriding
  `HwndHost.TranslateAcceleratorCore` to swallow `VK_HOME`/`VK_END` (`WM_KEYDOWN`/`WM_SYSKEYDOWN`)
  before WebView2's own base-class plumbing turns them into the routed `KeyDown` that
  `EditorTabs` (a plain `TabControl`) was catching via its built-in Home/End navigation. Swapped
  `new Microsoft.Web.WebView2.Wpf.WebView2` → `new BuildConsole.Controls.ChatSafeWebView2` at all
  three construction sites (`MainWindow.xaml.cs` ~1856, `BuildChatWebView` ~2429, ~4360) — no other
  code at those sites changed, since the subclass IS-A `WebView2`. No other key handling touched;
  `Window_PreviewKeyDown`'s Ctrl+N/Ctrl+K/Ctrl+Tab etc. are untouched.
  - **Page Up / Page Down / arrow keys — checked, not fixed, left alone as instructed.** Per
    Microsoft Learn's own `TabControl.OnKeyDown` documentation, WPF's stock `TabControl` only
    marks the KeyDown event handled for **Ctrl+Tab, Ctrl+Shift+Tab, Home, and End** — plain
    Page Up/Down and the arrow keys are never inspected by `TabControl.OnKeyDown` at all, so even
    though WebView2 classifies them as accelerator keys too (per the same "doesn't map to a
    character" rule), there is no TabControl behavior downstream to trigger. They don't exhibit
    the bug, so they were left untouched.

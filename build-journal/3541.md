Confirmed the real gap and the real fix: `msp-launch-control.ts`'s `POST /execute` never creates a `msp_change_requests` row, so there is nothing for `human-action` to attest against. Also confirmed `human_action` was the wrong executor classification to begin with — `cr_executions.executor_kind` already has a real `write_action` value ("a change a code path can confirm"), which is exactly what a Launch Control Graph write is; `human_action` is reserved for "a change only a person can make... no code path observes it". Fix: `POST /msp/:mspId/launch-control/execute` now raises a real, pre-approved `standard` CR (same governance shape `POST /portal/change-catalog/:id/execute` (#1498) already established) before executing, then records the execution as `write_action` and closes the CR to `completed` on success — entirely server-side, no client attestation call needed. Extending `recordExecution` to support an immediately-known outcome for a synchronous (non-wf_run) write action.

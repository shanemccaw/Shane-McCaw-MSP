### What shipped

**1. The subscription gate.** `app.use("/api", subscriptionGate, router)` in `artifacts/api-server/src/app.ts` — one check point, mounted once, ahead of the whole router and therefore ahead of `requireAuth` and every `requireRole`/`can()` evaluation. Decision logic is a pure function in `lib/retention/subscription-gate.ts`; `middlewares/subscriptionGate.ts` is plumbing. No new role, no new permission, and no route knows the gate exists — an allowlist inside the gate is the only place that decides what stays reachable (both real export endpoints, all of `/auth/*` including MFA, the wall's own status endpoint, health/version).

Three judgement calls, all stated in the code:
- **Operators pass through.** The #1571 review queue exists to look at exactly these cancelled customers; gating the operator would make the wall opaque from the only side that can act behind it. Reading the existing `mspRole` to tell a customer principal from an operator one is not the "new role" part 8 rules out.
- **`/auth/` is allowlisted as one prefix**, not enumerated. Logout above all — trapping someone in a session they cannot end is worse than over-gating — and MFA, because #439's `mfaSetupPending` gate would otherwise deadlock against this one.
- **It fails OPEN on a database error.** The gate is a billing boundary, not a security boundary: everything behind it is still protected by `requireAuth`/`can()`, which run next and are unaffected. A cancelled customer briefly reaching a portal beats every active customer seeing a cancellation wall. Logged at `error`, never silent.

**2/3. Freeze on cancellation, resume on return.** `lib/retention/subscription-state.ts`. Written as a **reconciliation, not an `onStatusChange` hook** — the same reasoning part 8 used to reject the lock-down flag. `tenants.status` versus the new `subscription_lapsed_at` is a complete four-state comparison, so a status written by any path that never called the hook (a route, a migration, a seed, psql) still settles on the next pass. Three overlapping drivers: the two real `tenants.status` write sites in `msp-portal.ts` call it directly; the gate reconciles opportunistically when it sees a disagreeing pair on a live request; and an hourly sweep covers everyone. **The sweep is load-bearing, not belt-and-braces** — a cancelled customer makes no further requests, so it is the only thing that will ever notice them.

**4. The 7-year post-termination purge.** `lib/retention/post-termination.ts` plus `postTerminationDueAt()` in the pure `clock.ts`. Calendar arithmetic, not `years x 365d` — that multiplication loses a day per leap year, in the early direction, on an irreversible purge. The per-customer `postTerminationYears` override is honoured over the platform default, and the candidate query is coarse-then-exact so a longer-than-default window can never be purged early by a range scan. The executor is driven by a new `registerTenantDataPurger()` registry in `registry.ts` rather than a hardcoded table roster (the dev-only hard-delete in `admin-active-directory.ts` is the worked example of such a roster rotting). The tenant row survives its own purge as a tombstone — forced, not chosen, since `record_deletions.tenant_id` is `ON DELETE RESTRICT`.

**Also wired #1947's `advanceDueDeletions()`**, which had no caller at all, into the same hourly cycle in `index.ts` — deliberately *after* the reconciliation, so a cancellation cannot race a purge.

### Schema + migration (run in-session)

`lib/db/migrations/manual/2026-09-04-post-termination-retention-clock-2765.sql` — two additive nullable columns on `tenants` plus a partial index, run against the local `DATABASE_URL` and confirmed live.

- `subscription_lapsed_at` — WHEN the subscription stopped. `status` says whether, never when, and the 7-year window is a duration from that instant. Also the reconciliation's only memory.
- `post_termination_purged_at` — WHEN the purge ran; also the sweep's idempotence guard.
- **Neither is backfilled** (epic question E). A tenant that lapsed before this shipped has no real lapse instant, and inventing one would start an irreversible purge clock from a date that never happened.

Neither column is the tenant lock-down flag part 8 reversed — there is still no second "is this tenant locked down" concept to keep in sync with billing.

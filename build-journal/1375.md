### What shipped

**The scope derivation — the security-relevant half.**
`artifacts/api-server/src/lib/free-scan-write-scopes.ts` answers "which Graph application
permissions should THIS Prospect be asked for" entirely from real rows, with nothing authored:

    paid phase (free_scan_engagements.selected_phase_slugs)
      -> the phase's pillar                    (FREE_SCAN_SOW_PHASES — one phase, one pillar)
      -> this tenant's OPEN findings on it     (resolveRemediationChecklist + buildCheckKeyPillarMap,
                                                the same #521 resolution the pillar cards use)
      -> the ACTIVE config packs mapping them  (config_pack_templates.check_key — the same join
                                                #1539's writePackAvailable already keys on)
      -> those templates' real Graph writes    (baseline_action_templates method/endpoint/body)
      -> the documented application permission (requiredPermissionsForWrite, #1875's table)

The pillar map is rebuilt here rather than taken off `buildPillarSummary`, because that
function's per-card `findings` array is CAPPED for display and a capped list would silently
drop a permission a real finding needs.

**What the derivation actually produces, measured.** For a seeded Prospect with one identity
finding and one sharing finding: full scope → **3** permissions asked, **22** granted beyond
them; identity phase only → **2** asked, **23** beyond. The narrowing is real, not a claim.

**The design's third scope string never renders, and that is correct.** The design names
`Sites.FullControl.All` for the sharing-remediation work. The platform's real rule for the write
that work actually issues (`DELETE /sites/*/drive/items/*/permissions/*`) requires
`Files.ReadWrite.All` — Microsoft's own documented Application permission, quoted verbatim in
`graph-write-permissions.ts:807-813`. The derivation returns the real one. The design's copy is
applied only where the derived permission matches the name it was written for; everything else
falls back to the rule's own authored `justification` field.

**Honesty the design could not have known to ask for.** Microsoft's v2 `/adminconsent` takes no
scope parameter — it grants whatever the registration declares. Showing a narrowed list while
implying the grant stops there would be a false-narrow. The screen therefore also discloses
`grantedBeyondScope`: the permissions the same single click grants that the bought phases do not
need. A test asserts the two lists partition `REQUIRED_WRITE_APP_PERMISSIONS` exactly.

**The consent mechanism is reused, not rebuilt.** `public-free-scan-remediate.ts` mints the URL
with the same `signWriteConsentState` HMAC, the same single-use `consent_invite_tokens` row, the
same `"popup"` origin and the same ONE fixed callback as `/public/flow/write-consent-url` and
the admin route. The callback is untouched — it still requires Microsoft to actually issue a
write-app token for the tenant (#4197) before stamping `tenants.consent.writeBack`, and still
refuses when the consenting Microsoft tenant is not this customer's. Three gates were ADDED in
front of it, all evaluated before any token row exists: signed + `paid` engagement, read consent
present, and the bought phases genuinely requiring at least one requestable permission. Nothing
existing was loosened.

**Scope item 4, verified rather than assumed.** `RemediationGuideBody.tsx` does not exist —
`f40438cd` deleted the whole `copilot-journey` UI, preserved only at tag
`portal-archive-2026-08-29`. Its live successor is `lib/remediation-checklist.ts` (#1538). And
`/api/portal/remediation-tracker` is genuinely unreachable for a Prospect: it sits behind
`requireCapability("ladder.free")` (needs a JWT #656 structurally denies) plus
`requireTierFeature(remediationTracking)`. Paying does **not** create a `client_services` row,
so a paid Prospect is still JWT-less. Neither gate was loosened; the guide is served through the
Prospect's own door and writes the SAME `remediation_tracker_steps` rows, keyed by `checkKey`
under the real `customerId`, so the authenticated Portal reads them back unchanged later.

**Scope item 5.** The decline promise needed a portal route that works for a real customer; the
only one that existed was `POST /portal/consent/debug-write-reconsent-link`, marked "DELETE
BEFORE PRODUCTION" and hard-gated to `tenants.is_testbed`. Added
`POST /api/portal/consent/write-consent-link` — same mint and same callback, gated on
`ladder.customer-user` and on real read consent, no testbed special case. The guide screen also
keeps a "Grant write access" button, so a decline is reversible without waiting for a Portal
login.

**The page.** `/scan/remediate` (`FreeScanRemediate.tsx`) recreates the `{{ writeStage }}` block
verbatim and follows it with the design's `{{ paid }}` done block plus the real guide. Which
screen renders is decided by server state, never a stored UI step. The grant opens Microsoft's
popup and the page polls for the REAL `writeBack` grant with a bounded 5-minute wait — never
inferred from the popup closing. Review's payment-received block gains a Continue hand-off.

### Honest gaps
- The write-consent screen and the guide behind it are not covered by the browser manifest:
  reaching them needs a consented tenant with a completed scan AND a signed, paid engagement,
  and both the consent grant and the Stripe payment happen cross-origin. That half is covered by
  the two live-Postgres suites instead, and the manifest's own notes say so.
- Microsoft's consent screen is Microsoft's page and is never driven from a test.
- `resolveFreeScanWriteScopes` reads the tenant's findings once per request; on a tenant with a
  very large finding set that is a heavier read than the Review step's. Not observed as a problem
  on real data, and not optimised speculatively.

## Investigation findings (done — so implementation is immediate once #4542 lands)

### Detection lever (already present, currently unused — confirmed)
`desktop/BuildConsole/MainWindow.ResourceMonitor.cs` polls `GlobalMemoryStatusEx` every
1.5s into a full `MEMORYSTATUSEX` struct. `ullTotalPageFile`/`ullAvailPageFile` are in the
struct but **never read** (only `dwMemoryLoad`, `ullTotalPhys`, `ullAvailPhys` are used,
L72–77). Pagefile-in-use = `ullTotalPageFile - ullAvailPageFile`; a rising trend over
consecutive 1.5s samples is the genuine *leading* indicator Shane requires (predictive,
before physical RAM is exhausted / symptoms are visible). No new API or poll needed.

### Pause lever (already present — confirmed)
`QueueWatcherService.SetPaused(bool)` / `_paused` / `IsPaused` / `PausedStateChanged`:
while paused, `TickAsync` still reaps completions but **skips `GetNextQueueItemsAsync`
entirely** — no new claim/launch. There is precedent for a *second independent* launch
gate: `_appReady` (Git #1883) hard-gates the claim loop separately from `IsPaused`.
**Design:** add a THIRD internal auto-pause flag (e.g. `_memoryPressurePause`) that is
OR'd into the same claim gate — kept separate from `_paused` so it never clobbers Shane's
manual pause state and is not persisted to `BuildConsoleSettings.QueuePaused`.

### Honest "real vs aspirational" on throttling ALREADY-RUNNING builds (dispatch's key ask)
- **Pausing new launches is real and ready** — the `SetPaused`/claim-gate lever above.
- **Gracefully SUSPENDING a running build is NOT real.** There is no suspend/resume
  primitive for a running Claude Code process. The only lever that reduces an
  already-running build is `TryStop(queueItemId)` (Git #820), which does a hard
  `entry.Process.Kill(entireProcessTree: true)`, cancels the tailer, reaps the Job
  Object, and removes it from `_running`. That KILLS in-progress work (the build's turn
  is lost; its DB row must then be marked done/failed or requeued by the caller).
- **Therefore:** "graceful cancellation of the newest/least-progressed running build" is
  achievable ONLY as a hard process-tree kill + row requeue — a heavy, lossy lever, not a
  clean pause/resume. Recommendation: rely on the early/predictive new-launch pause as the
  primary cure (catch pressure before concurrency ever climbs that high). If a
  kill-newest escalation is wanted as a last resort, it must be built on `TryStop` +
  explicit requeue and accept the lost turn — design it as opt-in escalation, not the
  default, and only after #4542's cap makes the running count trustworthy.

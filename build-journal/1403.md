# #1403 — Multi-CLI (`--cli claude|gemini`) build-prompt flag not actually spawning gemini

- **Status:** ✅ DONE
- **Scope:** buildconsole
- **Started:** 2026-08-28
- **Commit(s):** b264242cd (cli dropped on every re-queue path), 30448f773 (gemini.exe path never matched a real install)

## Log
- 2026-08-28 ⏳ IN FLIGHT — investigating why `--cli gemini` build-prompt header flag doesn't result in gemini.exe being spawned (generalization of #1009's claude.exe --print spawn logic); burning Shane's Claude weekly usage every time it silently falls back to claude.
- 2026-08-28 ✅ DONE — Found TWO real, compounding root causes, fixed both, merge-verified via `verify-branch-merged.mjs` (exit 0):
  1. **cli dropped on re-queue (b264242cd).** The fresh-queue paths (EditBuildPromptDialog / chat-injected Queue button) correctly parse `--cli` and thread it into `QueueBuildAsync`'s `cli` param, and `QueueWatcherService.LaunchItem` correctly branches on `item.Cli` to pick `gemini.exe` vs `claude.exe`. But a GitHub-issue-linked build dedupes onto a SINGLE row (upsert by `github_number`), so every re-queue of that same issue — Retry/Resume Session/Reply (BuildQueuePanel.xaml.cs), Continue (GitDetailView.cs, BuildWatchWindow.xaml.cs) — called `QueueBuildAsync` WITHOUT passing `cli:`, silently overwriting the row's correct `'gemini'` back to NULL. `BuildWatchSlot` didn't even have a `Cli` field to carry it. Fixed all 5 call sites (matching the existing `buildSet`/`account` pattern) + added `BuildWatchSlot.Cli`.
  2. **gemini.exe path never matched a real install (30448f773), found while live-verifying fix #1.** `_geminiExe` was hardcoded to `~\.local\bin\gemini.exe`, mirroring Claude Code's own installer layout — but the real `npm install -g @google/gemini-cli` (confirmed live via `where gemini` on this machine) drops `gemini.cmd`/`gemini`/`gemini.ps1` shims under `%APPDATA%\npm`, never a `.exe` under `.local\bin`. `File.Exists` was FALSE for every real install, so a correctly-tagged build failed outright instead of running gemini. Added `ResolveGeminiExe()` to check the real npm global path first.
  - **Live verification (real process inspection, not the UI label):** replicated the exact fixed spawn decision + `ProcessStartInfo`/`UseShellExecute=false` call live, then walked the resulting process tree via WMI `Win32_Process` — confirmed a genuine `node.exe` running gemini-cli's real built entry file (`...\npm\node_modules\@google\gemini-cli\bu...`), zero `claude.exe` anywhere in the tree. `dotnet build desktop/BuildConsole/BuildConsole.csproj` succeeds, 0 errors.
  - **Known follow-up not fixed here (flagged on the issue, not silently left):** the args `LaunchItem` builds (`--permission-mode`, `--print`, `--output-format stream-json`, `--verbose`) are Claude Code-specific and are sent to gemini.exe unmodified too — gemini-cli's own flag surface differs, so a real `--cli gemini` build will now genuinely spawn gemini but may still error on those args. Out of scope for this issue (which is specifically "which binary gets spawned"); needs its own follow-up to generalize arg-building per CLI.

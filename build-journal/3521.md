### Root cause (Finding 1, #3459) — proven live
- #3459's real row 2155: `status=canceled, exit_code=0` (a SUPERVISORY cancel — build ran, exited clean, landed no work because its blocker wasn't done; the false-done reconciler reset it to canceled leaving exit_code=0). Its only blocker #3493 is CLOSED (14:25:43Z).
- `BatterUpFreeFlow` is **ON**, so Shane's manual Refresh Git DID invoke `BatterUpQueueService.QueueRowAsync` against #3459. It declined purely because #3517's predicate required `row.IsBlocked == true`. Once #3493 closed, `IsBlocked` flips false, so the one condition meant to catch "blocker cleared → launch now" instead DISQUALIFIED it → stranded `canceled` forever. Not a trigger/timing gap — a logic gap.

### Fixes (commit f302796e0)
1. **Re-queue logic** — `QueueRowAsync` now re-queues a supervisory cancel (canceled+exit0) whether or not its blocker is still open (still-blocked → held by the #1600 launch gate; cleared → launches). Loop-safe via a new `supervisory_requeue_count` column (one auto attempt, then manual only) — replaces the old IsBlocked-derived loop guard.
2. **Display** — supervisory cancels render `⏳ WAITING` (amber), not `🚫 CANCELED`, across the queue card pill, ghost label, and mini-map dot. A real user-cancel (exit_code NULL) keeps `CANCELED`.
3. **Finding 2 (stale rows)** — 21 `canceled` rows were for GitHub issues closed weeks ago (distinct mechanism: nothing reconciled a canceled row once its issue closed). Added `FalseDoneReconciler` Shape-C: a canceled row whose issue is CLOSED → `superseded` (reuses the same trustworthy open-issue snapshot, fail-closed), dropping it out of the active Canceled list with a real ReconciliationNotice. Runs on every manual Refresh Git.

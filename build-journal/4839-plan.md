# #4839 — Plan

Posted: 2026-09-19T05:40:00Z

## Problem Description
Four census checks store their flagged-count field equal to `_itemCount` (the total), so the pillar SIGNALS grid (#4578) renders wrong numbers to the customer. Latest stored rows for tenant `c4c814d4-3afe-441e-9145-62461d0a4fd3` (`tenants.id` 2080):

| check | flagged-count field | stored | `_itemCount` |
|---|---|---|---|
| `sharepoint:site-label-coverage` | `sitesWithLabelCount` | 99 | 99 |
| `sharepoint:storage-near-limit` | `sitesNearStorageLimitCount` | 99 | 99 |
| `teams:inactive-teams` | `inactiveTeamCount` | 18 | 18 |
| `teams:guest-membership` | `teamsWithGuestsCount` | 18 | 18 |

`sharepoint:site-label-coverage` = 99 directly contradicts `governance:sensitivity-label-adoption` `sensitivityLabelCount = 0` on the same tenant.

## Root Cause Analysis
Queried live `monitor_checks` (local DB). It is **not** a transform that "counts every row instead of the filtered rows" over a field that could filter — the data never carried a filterable signal at all:

| check | stored endpoint / transform | why it can only ever equal the total |
|---|---|---|
| `sharepoint:site-label-coverage` | Graph `/sites`, `count` on `id` | `/sites` items hold only `id, name, webUrl, displayName, createdDateTime, isPersonalSite, siteCollection, root` (read from the stored `raw_response`). No label field exists to filter on. |
| `sharepoint:storage-near-limit` | Graph `/sites`, `count` on `id` | Same item shape — no storage-used or quota field. |
| `teams:inactive-teams` | Graph `/teams`, `count` on `id` | Team objects carry no activity date (`createdDateTime` is null in the stored rows). |
| `teams:guest-membership` | Graph `/teams`, `count` on `id` | Team objects carry no member/guest data. |

The precedent `governance:ownerless-groups` works because its endpoint is `/groups?$expand=owners($select=id)` and its transform is `countEmptyArray` on `owners` — the endpoint returns the signal and the transform filters on it. The four broken checks were authored with the unfiltered `count` shape and no signal-bearing endpoint. So each needs a **real data source**, not just a different transform. Probed live against the tenant (read-only, DEV app registration, scratch script deleted afterwards):

- **Teams** — Graph usage report `/reports/getTeamsTeamActivityDetail(period='D90')` returns CSV (the executor already parses it, `isCsvReportResponse`/`parseCsvReport`). 18 rows (= current `_itemCount`); columns include `Last Activity Date`, `Is Deleted`, `Guests`. Live: 13 rows blank `Last Activity Date`, at least one dated 2023-10-06 (older than the window), `Guests` = 0 on all 18.
- **SharePoint** — CSOM `Tenant.GetSitePropertiesFromSharePoint` (same admin-host transport `sharepoint:tenant-sharing-capability` already uses) returns 96 site collections with `SensitivityLabel` (a `/Guid(...)/` — all-zero GUID on every site), `StorageUsage` and `StorageMaximumLevel` (MB). Live max usage 9.7 % of quota.

## User Review Required
- **Near-limit threshold is 90 % of the site's own storage quota.** The check name ("near limit") does not define a number and Microsoft publishes none for site collections; 90 is my choice, stored in the mapping so it is data, not code. Change it in `monitor_checks.mapping` if a different cut is wanted.
- **"Inactive team" = not deleted AND (no activity in the 90-day report window OR last activity older than 90 days)**, matching the check's own description ("no channel activity in 90+ days"). A team created inside the last 90 days with no activity yet counts as inactive.
- **Denominators shift for the SharePoint pair**: `_itemCount` becomes the CSOM site-collection count (96), not the Graph `/sites` count (99), so the SIGNALS sub-text reads "of 96 sites". `sharepoint:site-count` still reads Graph. Not fixed here — filed as a finding if it proves material.
- The Teams report needs `Reports.Read.All` — proven granted on this tenant (the probe returned 200). A customer tenant without it gets a normal check error rather than a fabricated number.

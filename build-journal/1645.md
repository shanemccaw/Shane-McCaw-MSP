## Log
- 2026-08-29 ⏳ IN FLIGHT — Investigating negative issue number reaching `gh issue view`; querying local Postgres for the offending row, tracing the write path, fixing data + adding a defensive guard in GitHubIssuesService.
- 2026-08-29 ✅ DONE — Root cause found by direct query, NOT the #1362 synthetic-epic suspicion. The negative numbers live in `bt_build_queue.github_number` (77 rows, −1..−1020; the reported `-26` is `id=238, title="local #26"`). These are **intentional, documented storage** for `--notGit` local builds — `MainWindow.LocalBuildId.cs:45` stores `githubNum = -id.Ordinal`. So there is **no corrupt data to delete**; deleting these rows would destroy real local-build records. The actual bug: `PopulateAssociatedIssueNumbersAsync` pre-seeded that negative sentinel into `AssociatedIssueNumbers`, which `BuildQueuePanel.TriggerBackgroundIssueTitleQueries` fed to `GitHubIssuesService.GetIssueTitleAsync(-26)` → `gh issue view -26`, and gh's flag parser rejects the leading dash ("unknown shorthand flag: '2' in -26"). Fixes: (1) write path — `PopulateAssociatedIssueNumbersAsync` now only pre-seeds a POSITIVE `github_number`; (2) defensive guard — `GetIssueTitleAsync`/`AddLabelAsync`/`RemoveLabelAsync` skip + log for any number ≤ 0 (the shared `gh` CLI choke point), independent of root cause; (3) consumer — `TriggerBackgroundIssueTitleQueries` filters `n > 0` so no pointless task is spawned. Other consumers checked: `GitHubIssueVerifier.VerifyBareNumberAsync` already guards `≤ 0`; `GitHubApiClient` builds REST URLs (`/issues/{n}`) so a negative yields a harmless handled 404 — only the `gh` CLI positional path is a hard failure. `dotnet build -c Release`: 0 errors (46 pre-existing warnings). Verified `8f2ef131e` is an ancestor of origin/main.

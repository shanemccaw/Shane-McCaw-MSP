## The judgment call, and the evidence that settled it

#2937 named two materially different fixes and asked which the row was actually meant to be. It is
**fix 2 — detonation, not an alert comment** — and the row's own provenance says so rather than my
reading of it.

**1. The catalogue row states the intent independently, and predates the template row.**

```
write_action_catalog id 204   created 2026-07-20 15:00:50-04
  domain              = 'Security (Defender)'
  action_name         = 'Submit file/URL for detonation'
  surface             = 'defender'
  required_permission = 'TBD - Defender Application permission'

baseline_action_templates action.submit-file-detonation   created 2026-07-20 18:21:15-04
  endpoint = /security/alerts_v2   method = POST
  body     = {"comment": "Submitted for detonation analysis"}
```

The catalogue row was written **three hours earlier** and records a Defender-surface action whose
Defender application permission was never determined. The template row written afterwards is where
the Graph endpoint and body appear. That is the order of a capability being stated first and an
endpoint being improvised for it later — not a typo in a Graph URL.

**2. `required_variables` is `["fileOrUrl"]`.** Neither the stored endpoint nor the stored body ever
consumes it. A comment-on-alert step would carry `["alertId"]` — which is exactly what
`action.resolve-alert` (`PATCH /security/alerts_v2/{{alertId}}`) genuinely carries. The orphaned
`fileOrUrl` is the surviving trace of the real intent.

**3. Re-reading it as an alert comment would substitute a different capability, not fix a defect.**
It would require rewriting the label, the description, the required variables, the catalogue
`action_name` and the catalogue `surface`. And alert writing is already covered twice over —
`action.resolve-alert` and `action.manage-incident` both exist. The catalogue does not need a third
alert-write step; it recorded that Shane wanted detonation.

## Why not simply move it behind `isNonGraphEndpoint()`

That was the other half of fix 2, and it is not available: it requires storing a **real** Defender
endpoint. Microsoft's documented Defender for Endpoint machine actions are Isolate, Unisolate,
RunAntiVirusScan, CollectInvestigationPackage, RestrictCodeExecution, StopAndQuarantineFile and
LiveResponse — none of them is a file/URL detonation submission. Inventing a plausible-looking
`/api/...` path so the row would "look non-Graph" would be fabricating an endpoint, which is
precisely the defect #2937 exists to correct. The honest state is that no endpoint has been designed.

## What shipped

1. **Migration** — archives the template (`status = 'archived'`, the schema's own first-class
   non-destructive retirement: *"Archived (not hard-deleted) templates are grandfathered into any
   config pack that already references them"*). No `config_pack_templates` row references it
   (verified: 0 rows), so nothing is grandfathered. The fabricated endpoint/method/body are left ON
   the archived row as the record of the defect; the description now states plainly that they are
   not real. Live count went 102 active → 101 active.
2. **Migration** — returns `write_action_catalog` id 204 to `endpoint_design_pending` with
   `template_id = NULL` and a real `blocked_reason`. That is the exact state its own sibling id 203
   ("Release from quarantine", also `surface = 'defender'`) already sits in. **The capability is not
   deleted** — the catalogue still records that Shane wants file/URL detonation, now as pending an
   endpoint design, which is true, instead of `execution_ready` pointing at a Graph operation that
   does not exist, which was not.
3. **`admin-write-actions.ts`** — archived templates are now genuinely refused on both `/preview`
   and `/execute` (409, `gate: "template_archived"`). Nothing enforced `status` on that route
   before, so archiving was decorative: an archived row still previewed and still executed by
   templateId. Found while implementing the fix; fixed here rather than filed, per the rules.
4. **`SimulatorLeftTree.tsx`** — the write-actions tree now renders the status badge for non-active
   rows, matching what the checks tree and packs tree already do. It dimmed them to `opacity-50`
   but gave no label, so an operator could see a row was different without being told why.
5. **`graph-write-permissions.test.ts`** — the existing "stays unmapped" assertion is kept
   deliberately, with the resolution documented on it. The archived row keeps its stored
   endpoint/method pair, so the mapper must keep refusing to invent a rule for it.

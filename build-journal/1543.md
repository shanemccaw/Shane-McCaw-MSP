## Log
- 2026-08-30 ⏳ IN FLIGHT — Building on #1539's landed fix-route dimension. This
  issue models the state where a finding resolves because the customer changed
  the tenant directly (no CR) — `drift-collector.ts` correctly still records
  that change as `attributed_unapproved`/`unattributed` (never `approved`, no
  forgiveness), while `remediation_tracker_steps.verificationState` correctly
  still moves to `verified` off the re-scan alone (never blocked by drift
  attribution — the tracker doesn't read drift_events at all today). Neither
  fact is wrong today in isolation; what's missing is a neutral, read-time
  surface that JOINS them so an MSP can see "this step verified AND the
  underlying setting changed outside change control in the same run" — the
  bypass signal the issue calls out as the most interesting state in the
  system. Plan: correlate via `msp_diagnostic_runs` (bridges customerId →
  tenantId + the run's [startedAt, completedAt] window) rather than adding a
  new column — the drift event and the tracker verification already share the
  same runId's time window, so this is a precise join, not a heuristic guess.
  No enforcement, no blocking, no naming a person — pure observation. Ends at
  the wire contract, no `artifacts/portal` page.

## What shipped

- **`artifacts/api-server/src/lib/remediation-bypass-resolutions.ts`** (new,
  mostly pure) — `domainsForStep()` bridges `REMEDIATION_TRACKER_STEP_CHECK_KEYS`
  (remediation-tracker-verification.ts) to `driftSpecForCheck()`
  (drift-check-specs.ts) to find which drift domain(s), if any, a tracker
  step's checks are tracked under. `correlateStepBypasses()` is the pure join:
  a verified step + the diagnostic run that verified it (its
  `[startedAt, completedAt]` window) + candidate drift events on that domain →
  the events whose `detectedAt` actually falls inside that exact run's window,
  i.e. were newly inserted/reopened by the SAME rescan that verified the step.
  `resolveBypassResolutionsForCustomer()` is the real orchestrator: loads a
  customer's `verified` tracker steps, their verifying runs (bridging
  `customerId` → `tenantId` via `msp_diagnostic_runs`, which already carries
  both), and drift events on the mapped domain(s) with a bypass verdict
  (`attributed_unapproved` / `unattributed`), then correlates per step.
- **`artifacts/api-server/src/routes/portal-remediation-bypass-resolutions.ts`**
  — `GET /api/portal/remediation/bypass-resolutions`, registered in
  `routes/index.ts`. Purely observational: neither table is written to.
- 10-case vitest suite (`remediation-bypass-resolutions.test.ts`, added to
  `vitest.config.ts` include) — locks `domainsForStep` against the REAL
  `STEP_CHECK_KEYS`/`DRIFT_CHECK_SPECS` registries (s8→ca-policy, s26→
  tenant-sharing-capability, s7 has no drift-tracked check, s18/s27 have no
  mapping at all) and the run-window join (inside/before/after/open-ended/
  no-run cases, plus a verdict-passthrough case proving nothing is ever
  upgraded toward `approved`).

No schema change, no migration — the two engines already fire from the same
`runDiagnostics()` call for a tenant, so `msp_diagnostic_runs`'s existing
`startedAt`/`completedAt`/`tenantId`/`customerId` columns are the whole bridge;
nothing needed authoring.

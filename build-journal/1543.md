## Log
- 2026-08-30 ⏳ IN FLIGHT — Building on #1539's landed fix-route dimension. This
  issue models the state where a finding resolves because the customer changed
  the tenant directly (no CR) — `drift-collector.ts` correctly still records
  that change as `attributed_unapproved`/`unattributed` (never `approved`, no
  forgiveness), while `remediation_tracker_steps.verificationState` correctly
  still moves to `verified` off the re-scan alone (never blocked by drift
  attribution — the tracker doesn't read drift_events at all today). Neither
  fact is wrong today in isolation; what's missing is a neutral, read-time
  surface that JOINS them so an MSP can see "this step verified AND the
  underlying setting changed outside change control in the same run" — the
  bypass signal the issue calls out as the most interesting state in the
  system. Plan: correlate via `msp_diagnostic_runs` (bridges customerId →
  tenantId + the run's [startedAt, completedAt] window) rather than adding a
  new column — the drift event and the tracker verification already share the
  same runId's time window, so this is a precise join, not a heuristic guess.
  No enforcement, no blocking, no naming a person — pure observation. Ends at
  the wire contract, no `artifacts/portal` page.

# Plan — #4620: literal `<unset>` Test Environment Variable value should warn, not fail 30s deep

Posted: 2026-09-18T05:02:35Z

## Problem Description

A Test Environment Variable stored with the literal 7-character value `<unset>` (the value
`TestManifestVariableScanner.AutoDefaultValue` auto-seeds for a newly-discovered, never-reviewed
variable) is indistinguishable from a real configured value to any code path that reads it
directly by name and only checks for null/blank. The intended failure mode is an explicit
"this isn't configured yet" warning; the actual failure mode for at least one real caller is a
confusing downstream error that reads like a product bug.

## Root Cause Analysis

BuildConsole already has a "pause-on-unset" mechanism (Git #953/#961/#803, commit `084daf9b`)
inside `TestRunVariables` (`desktop/BuildConsole/Services/TestRunVariables.cs`) that IS
`<unset>`-aware for manifest `{{name}}` interpolation:
- `SeedConfigVariables` (lines 97–151) flags any config var whose value equals
  `TestManifestVariableScanner.AutoDefaultValue` (or carries `NeedsReview`) into `_needsRealValue`.
- `Resolve` (lines 163–214) refuses to substitute a flagged name — it falls through to an
  extracted value if one exists, otherwise throws `VariableNotResolvedException` naming it
  explicitly, rather than shipping the literal `<unset>` string.
- `PrepareAsync` (lines 230–317) is called by every executor (Http/Graph/Ui/PowerShell) at the
  top of EACH step, BEFORE that step's own `Resolve` calls run — for an interactive run this
  pauses and prompts Shane for a real value; for a headless/non-interactive run it marks the
  name dismissed so the step fails clearly and immediately, not 30 seconds into an HTTP call.

So for actual manifest interpolation (`apiTests`/`graphTests`/`uiSteps`/`powerShellVerify`),
this part of #4574 is **already fixed** — it predates this issue's file date and already
surfaces `<unset>` as an explicit, named configuration failure at the very start of the step
that needs it, not deep into interpolation.

**The real remaining gap** is a *different* reader that does NOT go through
`TestRunVariables` at all: `MainWindow.ShaneAppRunScan.cs:161-169`
(`HandleShaneAppRunScanAsync`, backing the `shaneapp://runScan` protocol) reads
`TEST_PORTAL_EMAIL`/`TEST_PORTAL_PASSWORD` directly off
`BuildConsoleSettings.Load().TestEnvironmentVariables` via a local `GetVar` closure, and only
guards with `string.IsNullOrWhiteSpace(...)`. A value literally equal to `<unset>` (7
non-whitespace characters) passes that check as if it were a real credential — the code
proceeds to call `ScanRunnerClient.LoginAsync` with `<unset>` as the password, which fails as a
confusing remote auth/login error (`"testbed login failed: ..."`) rather than the clear,
immediate `"testbed Assessment credentials not set — add TEST_PORTAL_EMAIL..."` message the very
next lines already produce for the null/blank case. This is exactly the bug class #4620
describes — `<unset>` read as a real value, surfacing as a confusing failure instead of an
explicit config warning — just via a second, non-manifest code path the pause-on-unset work
didn't cover because it isn't part of a `TestRunVariables`-mediated run.

## User Review Required

None — this is a narrow, mechanical fix restoring the same "treat `<unset>`/blank as absent"
behavior the manifest-interpolation path already has, applied to the one direct reader that
lacks it. No product decision involved.

## Proposed Changes

In `desktop/BuildConsole/MainWindow.ShaneAppRunScan.cs`, change `GetVar`'s two callers' presence
check so a value equal to `TestManifestVariableScanner.AutoDefaultValue` (`<unset>`) is treated
the same as null/blank — i.e. still absent — and the existing `Fail(...)` message fires with the
same clear "credentials not set" wording, instead of reaching `LoginAsync` with the literal
placeholder string.

No new capability, no UI change, no behavior beyond restoring the correct "unset means unset"
check this file already almost has (it already checks IsNullOrWhiteSpace; this just extends that
same guard to the scanner's real placeholder literal).

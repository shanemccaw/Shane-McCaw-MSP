## Log
- 2026-08-30 ⏳ IN FLIGHT — `ReplitSshService` is a globally reachable singleton with zero
  `TargetEnvironment` enforcement, contradicting `TargetEnvironment.cs`'s own doc comment
  ("Agent/protocol executions (shaneapp://) are hard-locked to Dev"). Adding the real gate at the
  single choke point (`ExecuteCommandAsync`, which every other method routes through).
- 2026-08-30 ✅ DONE — commit `486644498` (verified an ancestor of `origin/main` via
  `git merge-base --is-ancestor`). Gate enforced at the one choke point
  `ReplitSshService.ExecuteCommandAsync` (all six other methods — `DeployAsync`,
  `RestartServerAsync`, `GetRemoteCommitHashAsync`, `GetPendingManualMigrationsAsync`,
  `TestConnectionAsync` — route through it), failing CLOSED with a clear message, never a silent
  no-op. Three-way policy (`GetRemoteAccessBlockReason` → pure `EvaluateRemoteAccess`):
  (1) **agent hard-lock** — new `ShaneAppExecutionContext` `AsyncLocal` marker set for the entire
  `shaneapp://` dispatch at the single point `MainWindow.HandleShaneAppUriAsync`, checked FIRST so
  no selector value unlocks SSH for an agent; (2) **default gate** — reads the live Target
  Environment selector via `LeftSidebar.GetSelectedTargetEnvironment()` (the single source of truth,
  same UI-dispatch read `LocalSqlExecutor` uses — NOT a duplicate flag), refuses unless Staging;
  (3) **explicit human authorization** — `AuthorizeManualStagingOperation()` per-flow scope opened
  only by the deliberate manual "Deploy to Staging" path (`StagingDeployService` +
  `StagingDeployDialog` migration read), so that legitimate flow works regardless of the selector
  and can never be opened from an agent context (throws there).
  **PostBuildDeployPipeline & ReplitWatcher decisions:** both INTENTIONALLY left subject to the gate
  (not exempted) — automated, no human click; under Dev their SSH fail-closes and they degrade to
  their existing HTTP #911/#805 (pipeline) and WebView2 (watcher) fallbacks, so nothing breaks; SSH
  resumes when Shane selects Staging. `SystemHealth`'s background Staging-SSH probe now reports an
  honest "⚪ Disabled (Target Environment not Staging)" instead of a red failure. No `shaneapp://`
  handler currently calls `ReplitSshService`, and the ambient marker makes it structurally
  unreachable from any that ever might.
  **Verification:** `dotnet build …BuildConsole.csproj -c Release` clean (0W/0E). Real gate test — a
  15-assertion harness run against the actual compiled assembly (`EvaluateRemoteAccess` + ambient
  `GetRemoteAccessBlockReason` under real `Enter()`/`AuthorizeManualStagingOperation()` scopes):
  **15/15 passed** — Dev/Production BLOCKED, Staging ALLOWED, agent-origin BLOCKED even under
  Staging + manual-auth, manual-auth ALLOWED under Dev, scope restore correct, agent context refuses
  to open manual-auth. Harness was temporary (in %TEMP%, outside the repo) and deleted.
  **Finding filed:** **#1840** (parented #1789, board = AI Batter Up) — the on-disk SSH private key
  still lets an agent shell run `ssh -i <key>` directly, bypassing this in-app gate; that's the
  residual half of the near-miss, a security/product decision to close, not code in this scope.

## Log
- 2026-09-11T01:54:12Z ⏳ IN FLIGHT — confirmed via `grep` that `BuildQueuePanel.xaml.cs`'s
  `ApplyFilter`'s `"Done"` branch had no `.Take()`/cap anywhere, and confirmed via direct
  local Postgres query (`bt_build_queue` status counts) that there are 1,894 real `done`
  rows today — the real, current scale that freezes the app. Implementing a capped
  recent-N default (ordered by real `QueueItem.UpdatedAt`) + an explicit "Show all" banner
  toggle per the issue's own preferred (and acceptable-fallback) fix shape. Building an
  off-screen `BuildQueuePanel` harness (same pattern Git #1760 already established — no
  Window shown, synthetic `QueueItem`s fed through the real `RenderQueue` path) to get a
  real before/after render-time measurement rather than "feels fine."
- 2026-09-11T02:15:55Z ✅ DONE — Real fix landed in two commits:
  - `cda26b8b6` — `ApplyDoneRecencyCap` caps the "Done" view to the 150 most-recently-
    completed rows by real `QueueItem.UpdatedAt` (applied after status + build-set
    narrowing so a build-set drill-down is never capped away). A new banner
    (`QueueDoneCapBanner`/`QueueDoneCapToggleLink`) reports the real shown/total counts
    and gives an explicit "Show all (may be slow)" toggle rather than silently
    truncating. `_showAllDone` resets whenever the filter changes away from "Done".
  - `fec56e10b` — while verifying, the off-screen harness (built to get real timing,
    same pattern as Git #1760) caught a real bug: a concurrent, unrelated Git #3613
    landed mid-session and changed `RenderQueue`'s contract (it now takes raw
    `_lastItems` and runs `ApplyFilter` internally; every call site was updated to
    match — except my own new `QueueDoneCapToggleLink_Click`, written against the
    pre-#3613 contract). That call site was double-applying `ApplyFilter`, silently
    corrupting `_doneFilterTotalCount` down to the already-capped count the second
    the "Show all"/"Show recent only" link was clicked. Fixed to pass `_lastItems`
    directly, matching every other call site; also made `UpdateDoneCapBanner` aware
    of `#3613`'s search-bypass path (hides while a search is active, since search
    bypasses `ApplyFilter` and the fields would otherwise be stale).
  - **Real before/after render time**, off-screen `BuildQueuePanel` harness (no Window
    shown, no App/service/mutex startup touched — a narrow component probe, never
    Shane's live app), fed 1,894 synthetic `"done"` `QueueItem`s (matching the real
    local `bt_build_queue` count) through the actual `RenderQueue` method via
    reflection, `Stopwatch`-timed including the deferred `Dispatcher.InvokeAsync`
    work RenderQueue itself schedules:
    - **BEFORE** (pre-#3612 behavior — all 1,894 done rows, unbounded): **~35,000–
      38,000 ms** (three runs: 35,682.7 / 21,454.5 / 37,645.9 / 34,914.2 ms — the
      21.4s run was a low outlier under lighter machine load; typical ~35s) — a real,
      confirmed multi-second-to-tens-of-seconds freeze, matching Shane's "locks up
      the entire app."
    - **AFTER** (capped to the 150 default via `ApplyDoneRecencyCap`): **~1,800–
      2,700 ms** (1,796.5 / 2,664.4 / 1,779.8 / 1,992.4 ms across runs) — roughly a
      **93–95% reduction**. Not literally instant (this bespoke DAG/card-graph
      architecture costs ~18ms/item real render time, confirmed roughly linear:
      150 × ~18ms ≈ the measured ~1.8–2.7s), but the core ask — never synchronously
      render the full unbounded historical set on the default click — is met, and a
      genuinely responsive sub-3-second render replaces a 35+ second lockup.
    - End-to-end banner/toggle verified through the real code path (not just the
      harness's own logic): capped view reads "Showing the 150 most recently
      completed of 1,894 done builds." / "Show all (may be slow)"; after a real
      click through `QueueDoneCapToggleLink_Click`, flips to "Showing all 1,894 done
      builds." / "Show recent only".
  - True virtualization of the DAG/canvas card graph was **not** attempted — per the
    issue's own scoping, it would be a materially larger undertaking against this
    bespoke swimlane/connector-line architecture (see Git #1760's own notes on its
    complexity) and the capped-default + explicit-expand shape is the issue's
    explicitly acceptable immediate fix. Not filing a separate virtualization issue —
    the issue body already names it as a future option, not a requirement.

## Log
- 2026-09-15T18:06:44Z ⏳ IN FLIGHT — confirmed real root cause via direct repro against local `BuildConsole` Postgres DB: NOT the schema mismatch the issue speculated (`blocked_by_numbers`/`blocking_numbers`/`board_status_name`/`milestone_number` all exist on `bt_issue_mirror` with the exact types the query expects — confirmed via `\d bt_issue_mirror` and running the exact query in psql, both succeeded). The real bug: `DatabaseRegistry.Resolve()` returns the raw `postgresql://user:pass@host:port/db` URI straight out of `.env.local`'s `BUILD_DATABASE_URL`, and hands it directly to `new NpgsqlConnection(connStr)`. Npgsql's `NpgsqlConnectionStringBuilder` does NOT parse `postgresql://` URIs — only ADO keyword=value pairs (`Host=...;Database=...`) — so `NpgsqlConnection..ctor` throws `System.ArgumentException: Format of the initialization string does not conform to specification starting at index 0.` on every open attempt. Reproduced this exact exception in an isolated scratch console app using the real `BUILD_DATABASE_URL` value. `GitModeGraphService.LoadGraphFromPostgresAsync`'s bare `catch {}` swallowed it silently and returned an empty-but-valid `GitModeGraphData`, which is why the tab rendered a blank "0 Issues • 0 Dependencies" success state forever. This same `DatabaseRegistry.Resolve()` bug also affects `GitModeTreeService` and `LocalSqlExecutor`'s buildconsole-db path — same root cause, one fix.

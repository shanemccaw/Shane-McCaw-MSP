- 2026-08-31 ✅ DONE — Fixed all three tab→epic resolution consumers in `desktop/BuildConsole/MainWindow.xaml.cs`:
  1. **`TriggerHandoffAsync`** (the reported bug): its epic-resolution chain was entirely nested under `if (chat != null)` and depended on `GetEpicForChat` / `tabState.GithubNumber` / `chat.IssueGithubNumber` — all nullable/stale — with zero title fallback. Added an `ExtractTabTitleIssueNumber(ExtractTabTitle(oldTab))` last resort after that block, so a tab titled `[#1202]` resolves `targetIssue=1202` whether `chat` is null or the whole chain came up empty. Prefers the canonical epic mapping, else uses the raw title number directly so a stale bt_epics cache can't turn a clearly-numbered tab back into "no associated epic".
  2. **#1802's own remaining gap** (`EditorTabs_SelectionChanged`, the Git Board scoping): #1802 fed the highlight only `resolvedEpic?.GithubNumber`, so a title number that parsed fine but wasn't in the epics-only cache `_chatEpicById` produced null → `SetActiveEpicGithubNumber(null)` **cleared** the highlight = the "not scoping down to #1202" symptom Shane reported. The board tree matches the active epic by raw `IssueNumber` (RenderTree), not epics-dict membership, so both branches (tracked BoardChat + untracked tab) now fall back to the raw parsed number. `SetActiveChatEpic` early-returns when `epicId==null`, so passing the raw number there is a harmless no-op.
  3. **Audit finding — `ResolveEpicNumberForTab`** (used by the "Start a new chat on Epic #N" context menu, both its label and `StartSuccessorChat`): had the identical gap and forced Shane through `NewChatEpicDialog` on a `[#N]` tab. Added the same title fallback centrally so both callers benefit. This is the "third one for Shane to hit next" the issue warned about.

  **What the dispatch asserted:** that Microsoft lists permission tiers as alternatives, that
  the derivation concatenated two tiers into one array, and that each of the 3 rules should be
  reduced to a single write permission — with `Policy.ReadWrite.SecurityDefaults` named as the
  likely correct one for the security-defaults PATCH.

  **What Microsoft's pages actually say** (fetched 2026-09-04, v1.0 and beta):

  | Rule | Application — least privileged | Application — higher privileged |
  |---|---|---|
  | `PATCH /policies/identitySecurityDefaultsEnforcementPolicy` | `Policy.Read.All` | `Policy.Read.All` **and** `Policy.ReadWrite.ConditionalAccess` |
  | `POST /identity/conditionalAccess/policies` | `Policy.Read.All` **and** `Policy.ReadWrite.ConditionalAccess` | `Application.Read.All` and `Policy.ReadWrite.ConditionalAccess` |
  | `PATCH /identity/conditionalAccess/policies/{id}` | `Policy.Read.All` **and** `Policy.ReadWrite.ConditionalAccess` | `Application.Read.All` and `Policy.ReadWrite.ConditionalAccess` |

  Microsoft's tables separate ALTERNATIVES with `,` and CONJUNCTIONS with `and`. All three
  cells above use `and`. The existing arrays were therefore documented conjunctions quoted
  correctly, not concatenated tiers. For the two CA rules the pair is Microsoft's own
  **least**-privileged tier — there is nothing narrower to reduce to.

  Microsoft states the reason outright on its Known issues page, under Identity and access,
  "Conditional access policy requires consent to additional permission": *"The
  conditionalAccessPolicy API currently requires consent to the Policy.Read.All permission to
  call the POST and PATCH methods."* The `conditionalaccesspolicy-update` page carries its own
  inline note: *"This method has a known permissions issue and may require consent to multiple
  permissions."* Stripping `Policy.Read.All` would 403 quickstart-v1 step 6
  (`create-ca-baseline-policy`) and micro-remediation `remediate-enable-ca-policy`.

  `Policy.ReadWrite.SecurityDefaults` **is** a real Graph application permission, exactly
  scoped ("Allows the app to read and write your organization's security defaults policy"),
  but it appears on neither the v1.0 nor the beta API page for the operation it describes.
  Did not switch to it — deciding it needs a real 204-vs-403 call, which is a write against
  the Security Defaults policy of `mccawsoft2.onmicrosoft.com` (Shane's real production M365
  tenant) and therefore a #1913 production-plane action, not a build-session one. Filed as
  #2846.

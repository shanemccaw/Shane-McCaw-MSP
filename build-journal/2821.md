  **The design decision the dispatch asked me to surface rather than pick silently — "which pipeline's row is canonical when the two disagree on shape".** I did not have to answer it, and the answer is that the question dissolves: the resolution **LINKS, never MERGES**. A duplicate keeps its own MOF property model, `read_cmdlets` and DSC ALL-OF permission set — all three read by `derive-ps-shapes-from-dsc.mjs` and `build-snapshot-registry.mjs`, all three destroyed by a merge. Only *coverage credit* moves. The graph row is canonical because coverage is a statement about what a check can actually call: a `monitor_checks` row addresses a REST path and the graph-origin row is keyed by that path; the m365dsc row's value is its shape, not its addressability. Recorded in full in `docs/graph-resource-model.md`.

  **Two evidence rules behind two precision gates.** Rules: `same-graph-path` (the DSC module's own `.psm1` GETs that literal URI) and `dsc-cmdlet-path-walk` (a `Get-Mg*`/`Get-MgBeta*` noun spent by a backtracking walk over the REAL modelled path tree — every segment consumed must already exist in the model, so the walk invents nothing and fails closed). Gates, applied to BOTH rules: name correspondence (every word of the DSC name must appear in the path; only a trailing `Policy` is noise) and target uniqueness (several DSC resources claiming one path is a shared-collection signature, so none is asserted).

  **The gates are not decoration — an ungated first draft produced real false positives.** It linked `TeamsUserCallingSettings` → `/users` and `AADGroupsSettings` → `/groups` through the incidental `Get-MgUser`/`Get-MgGroup` helper calls those modules make to turn a display name into an id (28 and 184 resources invoke those respectively), and 20+ `IntuneDeviceConfiguration*` rows onto `/deviceManagement/deviceConfigurations`. Erring toward NOT linking is deliberate: a false link credits a genuinely uncovered resource with another row's coverage and **hides a real gap**, whereas a missed link leaves the row exactly as today plus a stated reason.

  **Measured live against local Postgres:** 481 `origin='m365dsc'` rows examined → **24 resolved** (0 `same-graph-path`, 24 `dsc-cmdlet-path-walk`), 204 labelled with a real `canonical_gap_reason` rather than dropped (183 "no cmdlet noun resolves to a path the DSC name accounts for", 21 "the module GETs a collection it is only a SUBTYPE or CHILD of"). **7 of the 24 were phantom gaps** — a duplicate reading `check_coverage_count = 0` whose canonical row was already covered, so no check could ever have closed them — all on `surface='identity'`, matching the issue's own evidence. Corrected six-way split: 1539 total = 101 covered + 1253 uncovered + 6 no_executor + 26 unavailable + 129 operations + 24 duplicates.

  Rule 1 yielding **zero** links is the correct answer, not a failure: every `m365dsc` row carrying a `graph_path` today issues a *collection* URI it is one subtype of (15 `IntuneMobileApps*` → `/deviceAppManagement/mobileApps`) or a *parent* of the child it really reads (`AADCrossTenantIdentitySyncPolicyPartner` enumerates `/policies/crossTenantAccessPolicy/partners` to read each partner's `identitySynchronization`).

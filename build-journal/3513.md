## Log
- 2026-09-10T13:35:29Z ⏳ IN FLIGHT — Investigating false-done reconciler (#2685/#2775): tracing the code path that sets bt_build_queue.status='done', auditing the live table for the real false-done count, and extending the reconciler to catch the "done, no valid bookend / GitHub issue still open" class so those rows resurface as re-dispatchable work.
- 2026-09-10T13:55:02Z ✅ DONE — Shipped in commit `20db76d5b` (on origin/main, ancestor-verified).

  **Root cause (traced).** `BuildQueuePostgresClient.PromoteVerifyingToDoneAsync` promotes a `verifying`
  row to terminal `done` when its issue number is ABSENT from an open-issue snapshot. That is only sound
  if the snapshot is trustworthy. It wasn't, two ways: (1) an EMPTY set during the #3512 rate-limit storm —
  `MainWindow` Home reconcile called it via `GetOpenIssueNumbersAsync()`, which collapses a failed fetch to
  an empty set, with NO caller-side empty guard (BuildWatch/BuildQueuePanel both guard; MainWindow did not);
  (2) a TRUNCATED set — the same MainWindow call used the default 500 cap while 629 issues were open,
  dropping ~130 genuinely-open issues that were then read as "closed" and promoted to done.

  **Honest live audit (the count Shane asked for).** `bt_build_queue`: 1805 done total, 1709 done with a
  real github_number. Cross-referenced against a live `gh issue list` (629 open; mirror agreed at 628):
  **69 false-done rows right now** — status `done`, real github_number, GitHub issue STILL OPEN (the issue
  body cited 31; the complete figure is 69). Classified by origin/main bookend:
    - 48 have a git-verified DONE bookend (real ancestor commit) → work landed, issue just not closed →
      reconciler REVERTS them `done`→`verifying` (visible, awaiting the real close; not re-run).
    - 21 have NO verified DONE bookend (11 no bookend at all; 7 DONE claimed but commit not on main;
      3 other — #3412 IN FLIGHT, #3470 plain-format BLOCKED, #3475 plain-format DONE) → work never
      landed → reconciler resets `done`→`canceled` + board Backlog (re-dispatchable), same as BLOCKED.
  3 `verifying` rows are correctly waiting on open issues (left untouched).

  **Fixes (commit 20db76d5b).**
    1. `PromoteVerifyingToDoneAsync` now fails closed on an empty open set (central guard, protects every caller).
    2. MainWindow Home reconcile fetches open issues with a generous cap (was default 500 while >600 open).
    3. `FalseDoneReconciler` gains Shape B — a `done` row + real github + issue CURRENTLY OPEN is a false
       promotion; split by the same git-verified DONE-bookend check the dispatch gate trusts into
       revert-to-verifying vs cancel+Backlog. Fails closed if the open-issue fetch fails (never acts on bad data).
    4. New `RevertFalseDoneToVerifyingAsync` DB primitive (guarded `status='done'`, idempotent).

  **Verification.** BuildConsole builds clean (0 warnings, 0 errors). A non-destructive transactional DB
  simulation (BEGIN…ROLLBACK) confirmed: the detection query selects exactly the two done+open rows (not a
  closed-issue row, not a verifying row); the revert path flips done→verifying (UPDATE 1, idempotent
  UPDATE 0 on re-run); the cancel path flips done→canceled (UPDATE 1, idempotent); negative controls
  unchanged; 0 rows persisted. Did NOT launch BuildConsole.exe (per standing rule) and did NOT hand-mutate
  the 69 live rows — the shipped reconciler heals them automatically on the next board refresh (logged/
  auditable), and hand-reverting before the fix deploys would be re-poisoned by the still-running old app's
  500-cap Home reconcile. Shane: once you rebuild + relaunch BuildConsole, the first board refresh reconciles
  all 69.

  **Finding filed:** #3516 (`bug`, parented under Feature #1789, board "AI Batter Up") — `DoneBookendVerifier`
  only matches bold `**Status:**`/`**Commit(s):**`, so plain-format bookends (#3470, #3475) are silently
  missed by both the dispatch gate and the false-done reconciler.

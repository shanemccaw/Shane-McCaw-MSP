## The answer, per table

Traced every real writer and reader of all seven columns against the live local database.

| Table | Real id space | Decided by |
|---|---|---|
| `tenant_signal_history.customer_id` | **`tenants.id`** (changed) | table name; the design comment; the only writer is handed a tenants.id and only translated to a login to satisfy an FK that exists in no repo SQL; every reader fanned back out over `users.tenant_id`; portal-privacy, the tenant hard delete and both reset migrations all already assumed it |
| `inbox_message_links.customer_id` | `users.id` | `/inbox/messages/:id/crm` resolves it directly against `usersTable.id` |
| `insights_automations.customer_id` | `users.id` | fed to `fetchClientHealthScores()` → `client_health_history.client_id` |
| `insights_generated_documents.customer_id` | `users.id` | already documented as the document OWNER; the SCOPE is `msp_customer_id` |
| `live_document_shares.customer_id` | `users.id` | writer inserts `req.user!.id` |
| `script_run_results.customer_id` | `users.id` | read via `resolveCustomerUserIds()`; written from the token's customer |
| `script_download_tokens.customer_id` | `users.id` | admin + portal both pass a customer login |

Six were never genuinely ambiguous — Drizzle, the live FK and every code path already agreed. Only the testbed-reset migration read them the other way. One, `tenant_signal_history`, was genuinely contradictory and is the one that moved id space.

## What shipped

**Migration** `lib/db/migrations/manual/2026-09-07-tenant-signal-history-customer-id-2983.sql`, run against local Postgres. Follows the #1923 / #2730 precedent exactly: the users.id keeps its value under an honest name, and `customer_id` becomes a real tenants.id.

- `customer_id` → renamed `client_user_id` (users FK kept, correctly named)
- new `customer_id integer REFERENCES tenants(id) ON DELETE CASCADE`
- backfilled from `users.tenant_id`: **6,488 rows** (122 + 6,274 → tenant 1, 92 → tenant 3)
- **103 pre-existing NULLs left NULL** — unattributable; filed as #3077
- Wholly additive and reversible: nothing dropped, no existing value overwritten.

**Code**
- `lib/db/src/schema/index.ts` — `tenantSignalHistoryTable.customerId` repointed at `tenantsTable.id`, new `clientUserId`; an authoritative id-space comment written on all seven columns.
- `tenant-signals.ts` — `recordSignalTransitions` and `getStabilizedSignals` read/write the tenant directly; both users.id bridges deleted.
- `policy-engine.ts` — `evaluateAllPolicies` enumerates `customer_id` directly, no `users` join.
- `retention/purgers/declare.ts` — the `ambiguousCustomerId` key space is **gone**; every target now names one verified id space.
- `retention/purgers/modules.ts` — six tables moved to `userId`; `tenant_signal_history` declared twice, once per column, in its own space.
- `2026-08-27-testbed-reset-patch-projects-1396.sql` — the six users.id tables moved out of the tenants.id loop into the user-scoped loop; `insights_generated_documents.msp_customer_id` (its real NOT NULL scope, keyed on by no reset run ever) now swept.
- `2026-08-26-comprehensive-testbed-reset-1329.sql` — superseded historical file, left uncorrected but now carries a DO-NOT-RUN header saying exactly what it would destroy.
- `portal-privacy.ts` / `admin-active-directory.ts` tenant delete — predicates **unchanged**; they were written correctly against the intended meaning all along and are now actually correct.

**Two further defects the audit exposed, fixed here**
- `live_document_shares.customer_id` is a NOT NULL users.id with a NO ACTION FK and appeared in no per-user delete list — hard-deleting any user who had ever minted a share link failed on the constraint and rolled the whole transaction back. Now an explicit delete.
- `insights_generated_documents.msp_customer_id` was keyed on by no reset run, so a document with no resolvable owner survived every reset.

# Git #2122 — Settings: real UI control for max concurrent build slots

- **Status:** ✅ DONE
- **Scope:** buildconsole

## Log
- 2026-08-31 — Session started. Real audit: `MaxConcurrent` is sourced from
  `scripts/build-queue-watcher.config.json` (gitignored, shared with
  `build-queue-watcher.ps1`'s own `-MaxConcurrent` default) via
  `BuildTrackerConfig.Load()`. That class had `Load()` but no `Save()` at all.
  `QueueWatcherService._maxConcurrent` was `readonly`, set once in the
  constructor from `btConfig.MaxConcurrent`. No Settings UI field existed.
  Plan: add `BuildTrackerConfig.Save()` (writes back to the same JSON file,
  camelCase to match the hand-authored convention), make `_maxConcurrent`
  mutable with a new `UpdateMaxConcurrent(int)` method, add a numeric field +
  Save button to Settings > General, and live-apply through MainWindow.
- 2026-08-31 — ✅ DONE. Implemented the live-apply approach (attempted first per
  the issue, and safe here — TickAsync/Start Now both re-read `_maxConcurrent`
  fresh on every check, a plain int compare, no multi-step invariant a mid-cycle
  change could corrupt), so the "restart required" fallback was never needed:
  - `BuildTrackerConfig.Save()` (new) — writes the config back to whatever
    `FindConfigPath()` resolves; falls back to writing alongside
    `build-queue-watcher.config.example.json` if no config.json exists yet.
    CamelCase property names to match the hand-authored file convention.
  - `QueueWatcherService._maxConcurrent` — `readonly` → mutable; new
    `UpdateMaxConcurrent(int)` clamps to a minimum of 1 and logs the change.
  - `MainWindow.UpdateMaxConcurrentBuildSlots(int)` (new, in
    `MainWindow.SettingsTab.cs`) — forwards to the live `_queueWatcher`.
  - Settings > General now has a "Max Concurrent Build Slots" numeric field +
    Save button (`SettingsTabView.xaml` / `.xaml.cs`,
    `BtnSaveMaxConcurrent_Click`): persists via `BuildTrackerConfig.Save()`,
    then live-applies via `MainWindow.UpdateMaxConcurrentBuildSlots` if a
    watcher is already running this session; falls back to an honest
    "applies on next launch" message if not.
  - Verified: `dotnet build BuildConsole.csproj -c Debug` — 0 warnings, 0
    errors. Also smoke-tested the `Load()`/`Save()` round-trip (including the
    no-file-yet fallback path) with a throwaway scratch console project
    referencing the real `BuildTrackerConfig.cs`/`TargetEnvironment.cs` in
    place — confirmed the file is created at the real
    `scripts/build-queue-watcher.config.json` path, `MaxConcurrent` persists,
    and re-saving preserves the other fields. Scratch project and the test
    output config file were deleted before finishing; not committed.
  - No manual SQL migration involved. No production boundary touched — this
    is a local desktop-app (BuildConsole) settings change only.
  - Commit: (this bookend commit's own hash — see `git log -1`).

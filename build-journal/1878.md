  **Part 1 — one-click Resume button.** Added a "▶ Resume Session" button to the
  `AdoptedReadOnly` composer Grid in `ChatSessionPane.xaml` (~624), next to the existing
  note + Stop button (both left exactly as they were, per the issue's point 3). New
  `ChatSessionPane.ResumeRequested` event (mirrors the existing `StopRequested`/
  `DismissRequested` pattern — the pane itself has no knowledge of the queue, only the
  host does). Wired in both real hosts:
  - `BuildWatchWindow.BuildSlotVisual` → `ResumeAdoptedSlot(slot)`, calling
    `_db.QueueBuildAsync(slot.Title, slot.Prompt, slot.Model, slot.Effort, slot.Cwd,
    slot.GithubNumber, slot.BlockedByNumbers, resumeSessionId: slot.SessionId, ...)`.
  - `GitDetailView.StartBuildTailing` → `HandleBuildResume()`, the same call shape off
    `_associatedBuild`/`_buildPaneSessionId`.
  Both are the *exact same* `QueueBuildAsync(..., resumeSessionId, ...)` dispatch
  `BuildQueuePanel.xaml.cs`'s "▶ Resume Session (crash recovery)" context-menu item
  already uses (line ~4187 today) — same original prompt, same resume semantics, just
  reachable without leaving the pane.

  **Part 2 — investigated whether typed text can genuinely thread through as a
  follow-up message. Finding: the mechanism already exists and works, but isn't wired
  to AdoptedReadOnly, and wiring it is a real (if small) follow-up, not this build.**
  Both `BuildWatchWindow.SendSlotInput` (its 2nd branch, ~1712) and
  `GitDetailView.HandleBuildSend` (~2169) already implement genuine typed-text
  threading: when a slot isn't live (`!OwnsInteractive`), Shane's typed text becomes
  the **new turn's own prompt/message**, sent via `QueueBuildAsync(title, text, ...,
  resumeSessionId: sessionId, ...)` — the CLI's `--resume` then continues the real
  conversation with that text as the next turn, not a re-run of the original prompt.
  This is reachable today for `Terminal` mode (done/failed/exited builds), not
  `AdoptedReadOnly`. The issue speculated the blocker might be "the current
  `QueueBuildAsync` signature and resume flow may not support injecting a follow-up
  message cleanly" — **that premise is false**: the signature and resume flow already
  do exactly this, right now, for Terminal-mode builds. The actual blocker is purely
  the UI layer: `ComposerMode.AdoptedReadOnly`'s XAML block has no `TextBox` at all
  (by design, per #1839's own comment: "an honest read-only composer"), and
  `ChatPaneViewModel.CanSend` only gates `Interactive`/`Terminal`, excluding
  `AdoptedReadOnly`. Restoring a real `TextBox`/Send affordance to that mode — and
  deciding how it should coexist with the plain "Resume Session" button this build
  adds (same click vs. two distinct actions) — is a genuine product/UX call, not a
  one-line wire-up, so it's left as a follow-up rather than folded into this build's
  "keep the note and Stop button exactly as they are" scope. Filed as **#2095**,
  parented to #1202 (Epic: Build Console).

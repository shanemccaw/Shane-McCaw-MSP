# #1406 — pillar strip sub-line lied "On track" for never-scanned pillars

- **Status:** ✅ DONE
- **Scope:** platform
- **Commit(s):** 1f601293f (fix), 383ee8748 (IN FLIGHT bookend)

## Log
- 2026-08-28 ⏳ IN FLIGHT — `pillarStripSub()` (overviewModel.ts) only ever looked at
  finding counts, so a never-scanned pillar (`open === 0` because nothing was ever
  measured, not because it's healthy) printed the same "On track" as a real
  zero-findings scan. #1392 already resolved this exact ambiguity for the pillar
  score itself via the `evaluation` status (`scored` / `not_evaluated` /
  `insufficient_data`). Applying the same signal here: `pillarStripSub` now takes
  `evaluation` as a second argument and returns `NO_SCAN_DATA_LABEL` ("No scan data
  available") unless `evaluation === "scored"`.
- 2026-08-28 ✅ DONE — Shipped in 1f601293f (rebased onto main as 05efc5069).
  `pillarStripSub(counts, evaluation)` gates on `evaluation !== "scored"` before
  falling through to the finding-count logic; `portal-v2-overview.tsx` passes the
  pillar's real `p.evaluation` (the same field #1392 wired). Unit tests added:
  "On track" for a real zero-findings scored pillar stays, plus two new cases for
  `not_evaluated`/`insufficient_data` asserting "No scan data available". Verified:
  `tsx --test overviewModel.test.ts` 78/78 pass; `tsc --noEmit` clean on both
  touched files (two pre-existing unrelated errors elsewhere in the tree,
  untouched by this change). No live UI manifest change: same as #1339's pillar
  score, the only reachable test tenant (shane-mccaw-consulting) is always
  scored, so the never-scanned sub-line branch can't be exercised live — it's
  fully covered by the unit test, documented honestly in
  test-manifests/portal/portal-v2-overview.json's existing notes rather than
  faking UI coverage.

- 2026-09-17T02:20:00Z ✅ DONE — Real reproduction findings (via code tracing only — live UI automation against a running BuildConsole is off-limits per the standing "never launch BuildConsole.exe" rule, since it can courier into Shane's real live session; verification here is a clean build + wiring confirmation, as that rule prescribes):
  - **Path A** (in-page note card JS, `VisualTestTrackerTelemetry.cs` `DomInspectorScript`): confirmed the issue's own reading was correct — its keydown handler checks `ev.key === 'Enter' && !ev.shiftKey`, does NOT gate on `ev.ctrlKey`, so Ctrl+Enter already takes the same branch as plain Enter and calls `submitBug()` directly. This path is coded correctly on its own.
  - **Path B** (`TestModeComposerPanel`'s `PreviewKeyDown` → `BtnSaveBug_Click`, the "Save Bug Entry (Ctrl+Enter)" button Shane names): also coded correctly on its own — `e.Key == Key.Enter && Keyboard.Modifiers.HasFlag(ModifierKeys.Control)` fires reliably whenever WPF keyboard focus is genuinely within the composer's own visual subtree.
  - **The real gap — a third, previously-undocumented mechanism**: `TestModeDiagnosticsPanel`'s own "Add Comment" DOM-Inspector section (`TxtDomComment`, button "Send to Bug List (Enter)") is ALSO live and visible simultaneously with both of the above during docked Test Mode (`TestModeDiagnosticsPanel.Visibility` and `TestModeComposerPanel.Visibility` are both `Visible` together, `MainWindow.TestMode.cs:234/247`). Every DOM-Inspector element click fires **two independent, uncoordinated async focus-grabs** at once: the in-page JS's `cardInput.focus()` (a 30ms `setTimeout`, inside the WebView2's native HWND) and `TestModeDiagnosticsPanel`'s own `TxtDomComment.Focus()` / `Keyboard.Focus(TxtDomComment)` (dispatched via `Dispatcher.BeginInvoke(..., DispatcherPriority.Input)` from `OnDomElementInspected`). Since a WebView2 is a native HWND island, real OS keyboard focus can only be in one of these two targets at a time, and nothing in the code sequences which one wins. If the user has already clicked into the composer's `TxtNotesBox` (Path B) to type their note, the JS side's delayed steal can silently hijack real keyboard focus back into the browser mid-typing — so Ctrl+Enter (and plain Enter) can land somewhere with no submit handler tied to the text the user can see, explaining the "append instead of new bug, then have to click Save Bug Entry manually" symptom Shane described.
  - **Fix applied**: removed the JS-side `cardInput.focus()` steal in `VisualTestTrackerTelemetry.cs`'s `onClick` handler (the async, uncoordinated racer). The C#-side `TxtDomComment.Focus()` remains the single deterministic auto-focus target; the in-page card stays visible and mouse-clickable but no longer silently steals real keyboard focus 30ms after a click.
  - **Verification**: `dotnet build desktop/BuildConsole/BuildConsole.csproj -c Debug` — 0 warnings, 0 errors. Live click-through was NOT self-verified (per the standing rule against launching/driving BuildConsole.exe) — Shane should confirm Ctrl+Enter reliably saves without a manual "Save Bug Entry" click in his own running instance.

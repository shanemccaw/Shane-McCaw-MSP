- 2026-09-04T03:17:08Z ✅ DONE — Root cause CONFIRMED with real evidence, both threads are one bug:

  **Diagnosis (not guess-fix):**
  - Explore agent audited the Build Watch read-only-mirror rendering (ChatSessionPane / BuildWatchWindow.TailSlotLog / UpdateThinkingText): it is fully **per-card independent** — separate FileStream/TailedLength/LineBuffer/LastOutputUtc per card, no shared lock/semaphore/reader, no card-N→card-N+1 dependency. So the "mirror card N+1 waits for card N" symptom is NOT a render bug — it faithfully reflects the underlying builds genuinely starting one-at-a-time.
  - Real timing from tonight's incident log (`activity-2026-09-03.log`, ~22:46–22:59): builds #1496/#1492/#1497/#1498/#1499/#1500 started **~1.3–3 min apart, one at a time** into 6 free slots. Each individual provision→launched gap was small (~1s), one 35s spike.
  - Root mechanism: `QueueWatcherService.TickAsync` launches claimed items via a **sequential** `foreach { await LaunchItem(item) }`, and `LaunchItem` provisions its isolated worktree with an inline `git worktree add`. So build N+1's provisioning didn't even BEGIN until build N had fully launched. That serialization was always present but cheap (~1s) when worktrees were reused; with real accumulated repo bloat (355 branches, ~10k loose objects, ~23 stray C:\wt dirs) a fresh reused=False `git worktree add` grew to tens-of-seconds/minutes, turning a 6-slot batch into a multi-minute stagger that read as "hanging." Appeared "since the last recompile" because a restart re-provisions fresh instead of reusing warm worktrees — not a specific commit (#2770/#2720 both ruled out: #2720 is an edge-case readdir, #2770's settings retry is off-hot-path; BuildProgressTracker is a per-build ConcurrentDictionary, no shared lock).

  **Fix (commit f91cb7c57):**
  - `QueueWatcherService.PrewarmWorktreesAsync` — before the sequential launch loop, provision every claimed build's worktree CONCURRENTLY (bounded to 3 to avoid #2539's git-crash-under-burst). Idempotent, so LaunchItem's own provision call then hits the fast reused=True path. Launch loop stays sequential → the non-thread-safe `_running`/`_reservedSlots` mutations are untouched (verified they're plain Dictionary/HashSet, not thread-safe).
  - `WorktreeProvisionService.RunProvisionAsync` — log provisioning duration + a ⚠ SLOW flag for fresh adds ≥15s, so a future slowdown is diagnosable instead of surfacing only as a hang (issue body point #4).

Not live-launched (single-instance-mutex rule forbids launching BuildConsole.exe to verify — would courier into Shane's live session). Working tree clean.

  ROOT CAUSE: `BtnSend.IsEnabled` is only ever touched inside `SendAsync` (set false before the
  send, true in the `finally`) — confirmed via full-file grep, nothing else in
  `FloatingChatWindow.xaml.cs` disables it. The `try/finally` itself is structurally correct, so
  the only way the button gets stuck disabled is if `await InsertAndSubmitAsync(...)` (inside the
  try) never returns at all — i.e. the `finally` is never reached, not that it runs and re-disables.

  `InsertAndSubmitAsync` catches every C# exception from its own logic, so an uncaught throw isn't
  the mechanism. The real hole is `ExecScriptString`, which directly `await`s
  `CoreWebView2.ExecuteScriptAsync(js)` with NO timeout. WebView2's `ExecuteScriptAsync` gives no
  timeout guarantee of its own — if the renderer stalls (heavy re-render while a reply streams) or
  its process dies mid-script, the returned `Task` can hang indefinitely with nothing to complete
  it. `InsertAndSubmitAsync` awaits three separate `ExecScriptString` calls per send (insert,
  submit, verify) with no bound on any of them, so a hang in any one leaves `SendAsync`'s `await`
  parked forever and `BtnSend.IsEnabled = true` in the `finally` is never reached — exactly the
  reported "stuck disabled" symptom, and consistent with the original issue's own theory #3.

  #2072's contribution: it added a THIRD awaited round-trip (`VerifySubmitScript`, plus another
  600ms `Task.Delay`) on top of the pre-existing insert+submit pair, so it measurably widened the
  window per-send during which a WebView2-side stall can occur — but the unbounded-await pattern
  itself already existed before #2072 (insert/submit were already awaited with no timeout under
  #2063's `InsertAndSubmitAsync` refactor). So #2072 made the failure somewhat MORE likely to
  surface, without being the originating defect.

  FIX: bounded every `ExecScriptString` call with an 8s timeout via
  `Task.WhenAny(execTask, Task.Delay(ScriptTimeout))` in `FloatingChatWindow.xaml.cs`. A stalled
  WebView2 script now surfaces as `"error: timeout"` (routed through `InsertAndSubmitAsync`'s
  normal status-return path, no new exception type) instead of hanging the awaiting caller forever
  — `SendAsync`'s `finally` is now guaranteed to run within a bounded time regardless of WebView2
  renderer health, which directly fixes the "stuck disabled" failure mode.

  message, watch `BtnSend` across a genuine WebView2 renderer stall) is not automatable from this

- 2026-09-07T17:48:20Z ✅ DONE — All five parts of the issue's "what closing this looks like" shipped, verified against the real local PostgreSQL 18 dev database.

  **1. Extraction.** `hardDeleteUserWithinTx` moved out of `routes/admin-active-directory.ts` into `artifacts/api-server/src/lib/user-hard-delete.ts`. Its actor is now a union — `{ kind: "user", id, email }` or `{ kind: "system", process, reason }` — so the scheduled purge does not have to invent a user id for a permanent audit line. Still exactly ONE implementation; now three callers (the per-user route, the per-customer route, the purger). The dev-only `assertNonProductionEnvironment()` gate deliberately stayed on the two ROUTES: a scheduled retention purge is a production behaviour by design.

  **2. Identity module.** `identityPurger` in `retention/purgers/modules.ts`, with a new `phase: "identity"` that `orderedTenantDataPurgers()` runs strictly after every `"data"` module. That ordering is load-bearing, not cosmetic: the `userId` key space is resolved per module from `users WHERE tenant_id = ?` inside the purge transaction, so a module running after the accounts are gone would resolve an empty user set and report zero for rows still in the table — with the tenant then stamped purged and never swept again. Declared as a `finalize` step rather than a target list because destroying a `users` row needs the real cascade (nine NO ACTION dependents, several reachable only via the user's own projects/client services), and re-declaring that as targets would be a second copy of it. It also refuses to report success if any `users` row for the tenant survives the loop.

  **3. SET NULL attribution — confirmed correct as dispatched.** The audit row survives; its actor attribution is blanked. `audit_logs.actor_user_id`, `sales_offer_events.actor_user_id`, `project_closures.signer_user_id` and the rest are left to the database's own ON DELETE SET NULL. #1944 part 2 guarantees the permanent ACCOUNT of what happened, not that the person named in it survives — an audit trail still naming a deleted person would be retaining that identity under another column name. Every such column is censused before the delete so the audit line records how many attributions were blanked.

  **4. coverage.ts.** The `users.tenant_id` entry is gone from `TENANT_SCOPE_PURGE_EXEMPTIONS`, replaced by a note recording the settled decision and where the claim now lives. `declaredTenantScopeKeys()` gained `finalize.covers` so `users.tenant_id` reads as CLAIMED rather than producing a permanent false alarm.

  **5. Verification, against real live data.** New `identity-purge.live-db.test.ts` builds two real scratch tenants (one 8 years lapsed, one 1 year) with real rows across every FK shape, purges only the due one, and asserts: `users` rows gone; every NO ACTION dependent gone; the phase-order probe (`inbox_message_links`, purged by the `directory` module in the userId key space and NOT by the identity cascade) genuinely gone; `audit_logs` / `sales_offer_events` / `project_closures` / `customer_alert_settings` rows surviving with their actor blanked; the neighbour tenant's account, project and data untouched; the due tenant's `tenants` row surviving, stamped. **6/6 pass.** Full run of everything touching the changed modules: **13 files, 186 tests, all passing.** `pnpm run typecheck` clean. All scratch rows removed (verified 0 remaining).

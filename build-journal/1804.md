# #1804 — Closing BuildConsole kills running builds (live stdout pipe → durable file)

- **Status:** ✅ DONE
- **Scope:** buildconsole
- **Started:** 2026-08-30
- **Commit(s):** f9ae37c43 (fix), dcaf046a1 (IN FLIGHT bookend)

## Log
- 2026-08-30 ⏳ IN FLIGHT — `QueueWatcherService.LaunchItem` redirects claude.exe stdout/stderr into a BuildConsole-owned in-process pipe (`RedirectStandardOutput`/`Error` + `OutputDataReceived`). When the app exits the pipe's read end dies with it; claude/node hits EPIPE on its next write and crashes the whole build. Replacing the pipe with an OS-level durable file redirect (child owns the file handle → survives app close), then tailing that file to keep Build Watch live-streaming when the app stays open.
- 2026-08-30 ✅ DONE — Shipped in f9ae37c43. New `Services/RedirectedProcessLauncher.cs`: launches the build via Win32 `CreateProcess` with stdout/stderr pointed at durable files (`queue-{id}.log.raw` / `.err`) the **child** owns, stdin an owned pipe (interactive) or NUL (legacy). Handle inheritance is restricted to exactly the three std handles via `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` so concurrent builds can't cross-inherit each other's stdin pipe. A `BuildProcessHandle` (raw handle + `WaitForSingleObject`/`GetExitCodeProcess`) stands in for `System.Diagnostics.Process` with the same `HasExited`/`ExitCode`/`Id`/`Kill` surface, so the reap loop + stop/kill sites read unchanged. `QueueWatcherService` now tails the raw files (`StartRawTailers`/`LineTailer`, same FileShare.ReadWrite incremental read as ExternalLogWindow #1638) into the **unchanged** HandleOutput/HandleStderr pipeline — Build Watch live-streams while the app is open, but the build no longer depends on it. The human-readable summary `logPath` (#802 BuildLogView / TailBuildLog) is untouched; claude's raw JSON goes to the separate `.raw` file so those views render as before. Secondary-account token stripping + Build-Set env now flow through an `envOverrides` map the launcher applies to the child env block.
  - **Scoping vs #1792 (verified, not assumed):** kill-on-close is NOT tied to BuildConsole's process lifetime. There is no Job Object here and no special app-close handler — the child std handles are the only app→child coupling, and they're now durable files (+ an owned stdin pipe whose closure is a graceful EOF, not a crash). Closing BuildConsole therefore leaves the build running, exactly as #1792's correction requires. When #1792's Job Object lands it must stay scoped to each build's own completion (never the app lifetime), or it would re-introduce this bug.
  - **Live verification (real launcher code, not theory):** built a throwaway net8.0 harness linking the real `RedirectedProcessLauncher.cs`. (1) Detach test: launched a node ticker with stdout→durable file, then let the **parent harness exit immediately** while the child ran. Confirmed via `tasklist` the child (pid 39616) was still alive after the parent was gone, and the durable file accumulated all 47 ticks + its own `DONE` line over the full 15 s and the child then exited cleanly — under the old pipe it would have EPIPE-crashed within ~300 ms of the parent exiting. (2) Stdin/exit test: wrote `hello-from-stdin` down the owned stdin pipe; child echoed `ECHO:hello-from-stdin` to its stdout file; stdin-EOF exit produced `EXIT=3` read correctly through `BuildProcessHandle.HasExited`/`ExitCode`. Harness deleted afterward (outside repo).

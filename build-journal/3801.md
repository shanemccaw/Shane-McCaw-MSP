  **The body's point 2 turned out to be false, and I measured rather than assumed it.** There is no
  volatile field: every `QueueItem` field comes straight out of `bt_build_queue`, and a server-side
  hash of exactly the columns `GetQueueAsync` selects was byte-identical across 10 consecutive 5s
  samples taken while a build was running. The signature comparison was matching; `RenderQueue` /
  `RenderBuildSetRollup` were **not** firing every tick.

  **The real cost was that all the work to reach that matching comparison ran unconditionally on the
  UI thread every 5 seconds:** 2,281 rows re-read (~4.4 MB incl. every row's full `prompt`), then
  `JsonSerializer.Serialize(_lastItems)` producing ~4.4 MB of JSON — **20.8 MB allocated per call**,
  measured — much of it Large Object Heap, i.e. ~4 MB/s of sustained garbage on the dispatcher. And
  because the fetch was awaited directly off a `DispatcherTimer` tick, every Npgsql read-buffer
  continuation across those 4.4 MB resumed on the UI thread too.

  **Fix:**
  - `BuildQueuePostgresClient.GetQueueChangeStampAsync` — one ~110-byte stamp computed server-side
    over the same columns `GetQueueAsync` selects plus the `bt_chats`/`bt_chat_issues` rows feeding
    `AssociatedIssueNumbers`. 14 ms of server CPU. `prompt` deliberately excluded (big TOASTed
    column; its single writer sets `updated_at = NOW()` in the same UPDATE, and `updated_at` is
    hashed).
  - `RefreshAsync` probes first, before the fetch, on both paths but only skips on the poll path.
    Unchanged stamp → skip fetch, signature and both renders; the cheap derived tail (status counts,
    orphan banner, `CappedCountChanged`, `SyncError`, `QueueRefreshed`) still runs so the method's
    contract for subscribers is unchanged. A throwing probe is never read as "nothing changed".
  - `ComputeQueueSignature` replaces the JSON signature with identical field coverage streamed into
    a SHA-256 over each string's existing UTF-16 bytes — **0.79 MB allocated instead of 20.8 MB** —
    on a thread-pool thread.
  - `GetQueueAsync` started via `Task.Run` so its own continuations leave the dispatcher.
  - `bt_chat_issues` now `ORDER BY`'d — unordered it could reorder `AssociatedIssueNumbers` between
    two identical reads, the one genuine instance of the mechanism the body suspected.
  - Corrected the now-stale `QueueRefreshed` doc comment (still claimed #2900 had removed the timer).

  **Verification (honest):** `dotnet build --no-incremental` — 0 errors, 10 pre-existing warnings
  (`CS0067` on `FocusModeBar`, `CS0162` from #3698's `BuildMatrixDisabled` kill switch). Probe
  stability: the 10 identical samples above. Probe sensitivity, inside a **rolled-back** transaction
  against the real local DB (stamp returned to baseline after ROLLBACK): a no-op
  `SET status = status` left the stamp unchanged, while a `note` change and a +1µs `updated_at`
  change both moved it. Signature correctness: 36 assertions against the **real compiled**
  `ComputeQueueSignature`, invoked by reflection from a headless harness — determinism, all 28
  `QueueItem` fields, a 1-tick `UpdatedAt` change, an `AssociatedIssueNumbers` reorder, null-vs-`""`,
  adjacent-field shifts, row order, row count, `_queueIsStale`, persisted restart items. All pass.

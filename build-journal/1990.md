## Diagnosis (from real logs, not inferred)

Confirmed from `%AppData%\BuildConsole\logs\activity-2026-08-30.log` for the real #1988 session (= queue **#1027**, model=claude-fable-5 effort=xhigh, launched 10:18:37):

- `10:19:06` `[interactive-build] stop requested` (≈27.8s in — this is the "27803ms")
- `10:19:10` `soft interrupt honored — paused; Send guidance to resume`
- `10:19:25` `auto-finalizing idle interactive build (closing stdin so it exits)`
- `10:19:26` `build-watch completed: (queue #1027, failed, exit 1)` → board **Parked** 10:32.

Key facts established:
1. **The `done (27803ms)` on Shane's screen was NOT a build-complete signal.** It is the per-turn `--- done (Xms) ---` marker written by `QueueWatcherService:3223` for **every** assistant `result` event. `BuildWatchWindow:402` even documents "DO NOT mark the slot Done here." The run was actually recorded **failed (exit 1)**.
2. **`RequestStopAsync` (which logs `stop requested`) has only two callers — both UI Stop buttons** (`BuildWatchWindow.StopSlot:1793`, `GitDetailView.HandleBuildStop:2273`); no timer/close/automated path. So a **manual Stop** was clicked ≈27.8s in. Stop sends a `control_request` **interrupt** (`WriteInterrupt`), and an interrupt aborts in-flight tool calls, which come back as exactly *"The user doesn't want to proceed with this tool use. The tool use was rejected."* — the rejection messages on the screenshot.
3. **The issue-body hypothesis #1 (idle-finalizer treats a live permission prompt as idle → closes stdin → rejection) is NOT in the code path.** The idle timer (`ScheduleAutoFinalize`) arms ONLY on a turn `result` (→WaitingForInput) or a soft-interrupt pause — never during a mid-turn pending permission request. And BuildConsole never surfaces/answers permission `control_request`s at all: it runs `--permission-mode auto` and the only `control_request` it *sends* is `interrupt`. So there is nothing that "treats a permission prompt as idle." (Consistent with the issue's own warning that #1971/#1978 had their hypotheses disproven.)
4. The overwritten raw stdout (`queue-1027.log.raw`, mtime Aug-31) belongs to the **successful retry** of the same queue id (ran 41 min, shipped `2e9a39594`), so the 27.8s run's exact tool calls could not be re-read — the Aug-30 activity log is the primary evidence.

## The real, general danger fixed (issue points #2 + #3)

#1988 only landed `failed` because its Stop escalation forced exit 1. The **same** situation without a manual Stop — a session whose tools are refused, then a clean idle-finalize — exits **0** and the reap maps exit 0 → **done/Verifying**, indistinguishable from real completed work. That is the "reports done, nothing landed" danger, and it is model-agnostic.

## What shipped (`efda0cc3a`, `desktop/BuildConsole/Services/QueueWatcherService.cs`)

- **Detect + log rejections (issue #3):** the stream-json `tool_result` path now detects permission/interrupt rejections (`is_error` + the rejection sentinel text, via `LooksLikeToolRejection` — deliberately specific so an ordinary failing command does not match) and logs each one immediately on the `interactive-build` channel **with the refused command** (matched back to its `tool_use` by id via a bounded `ToolCommandById` map).
- **Exit distinctly (issue #2):** at reap, if the process exited **0** but the session had rejected tool calls, the exit code is remapped to a distinct sentinel **`-3` (rejected-tools)** so the row lands **failed/Crashed** instead of **done/Verifying**, with a clear log line naming the count and the last refused command. A build that already exited non-zero is logged too but left as-is (already failed).
- **Issue #1:** reported honestly as **not in the code path** — no idle-finalizer change was made, because making one would be "fixing something that was not broken" (the retraction's own caution).
- Replay-safe: the count is rebuilt during an adopted build's replay but the per-rejection log line is suppressed then, matching the existing usage/session-limit replay discipline.

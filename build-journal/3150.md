  All four halves of the issue's security requirement are real, not deferred:
  - **AES-256-GCM at rest.** Plaintext never exists in a column — only `ciphertext` + `iv` +
    `auth_tag` on migration 017's already-live table. The AAD binds each ciphertext to its own
    row id and owner, so lifting bytes from one row into another fails the tag check rather
    than decrypting cleanly. The row id is minted in JS before the encrypt, precisely so it can
    be part of that AAD.
  - **Key outside the DB.** `SL_VAULT_KEY`, base64, read once in `config.mjs`. Missing or
    wrong-length key ⇒ a 503 with a real explanation; it never degrades to storing anything
    readable, and the room says so out loud instead of failing at the first Reveal tap.
  - **A fresh assertion per reveal, not session presence.** Deliberately NOT gated on
    `sessions.last_verified_at` — that would make one assertion good for every entry inside a
    window, which is exactly what the issue rules out. The reveal is two requests carrying one
    assertion, with the challenge issued per entry (`purpose = vault:reveal:<id>`), so an
    assertion earned for one row cannot open another, and `consumeChallenge`'s atomic claim
    means it cannot be replayed to open the same row twice.
  - **An audit row per reveal.** `vault_reveals`, written inside the same transaction as the
    decrypt — a plaintext handed back is always a reveal that was written down, and a decrypt
    that throws rolls the audit row back rather than logging a reveal that never happened.

  UI is the handoff README §7 spec verbatim: the lock note, rows showing site + masked
  reference only, the Face ID overlay while the real assertion runs, the value shown for the
  real 20 seconds counted against the **server's** own `expiresAt` (then dropped from the DOM
  and from JS memory), Copy clearing the clipboard 60 seconds later, and the `vault` critter
  watermark per the critter spec's room map. Revealing a second entry puts the first back
  behind its mask. Deliberately not exposed over MCP — a bearer-token plane reachable from any
  chat is the wrong place to read a bank account number from, and a per-reveal passkey
  assertion cannot be satisfied by one anyway.

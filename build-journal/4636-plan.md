# #4636 — Plan + Walkthrough

## Problem Description

Live-observed (Shane, screenshot of Build Watch): the same GitHub issue #4604 ran as **three
real simultaneous BuildConsole sessions**. Two tabs ("M365Architect: … GH #4604" at 1h7m and
"Continue: M365Ar… GH #4604" at 3m27s) showed **byte-identical transcript text**, the same
220.3k token count, and the same 1/4 "Investigation & Discovery" progress — i.e. two live
processes resuming **one** session (a `--resume` replays the prior transcript, which is why the
two tabs render identically). A third tab was a genuinely independent session, also on #4604.
This is the exact #4553/#4554/#4609 failure mode: two+ real Claude processes on one
session/worktree — a real corruption risk (tab 1's own transcript already hit "name collision
from my prior worktree").

## Root Cause Analysis

**This is NOT a regression of #4553/#4554 — it is a distinct gap (finding #4611).**

Verified on current `main` (859d2d157) that every guard #4553/#4554 shipped is present and
still routes correctly:
- `BuildQueuePanel.RetryQueueItemAsync` / `ResumeCrashedSessionAsync` / `LinkOrphanToLiveSessionAsync` / `ResumeSessionGuardedAsync`
- `BuildWatchWindow.SendSlotInput` / `ResumeAdoptedSlot` → `QueueWatcherService.LaunchContinuationAsync`
- `GitDetailView` resume paths → `LaunchContinuationAsync`
- `QueueWatcherService.GetLiveQueueIdsForSession` / `WouldInterruptActiveWork`

Every one of those checks session liveness **at UI click time**. But the layer that actually
spawns the OS process — `QueueWatcherService.LaunchItemCore` — re-checks **nothing**: for any
row carrying `resume_session_id` it appends `--resume <session>` and launches blind
([QueueWatcherService.cs L3002-3006](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L3002-L3006)).
Critically, **every** launch path — the dispatcher tick, `LaunchContinuationAsync`'s own forced
relaunch (`SafeLaunch(claimed, isForced:true)`), Retry, Resume Session, Recover All,
session-limit auto-restart — funnels through `LaunchItemCore`, and worktree provisioning
([L2834](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L2834),
94s live) sits **between** the click-time guard and the actual spawn
([L3118](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L3118)).
So a session that becomes live again during that window — or any `queued` row that simply reaches
the dispatcher already carrying `resume_session_id` (a continuation left queued at the hard cap;
a `limit-paused` row auto-restarted in place; a Reply/continuation row) — launches the second
process the UI guards were built to prevent. The guards are best-effort; nothing at the one place
"a process is about to exist" is load-bearing. This is precisely open finding **#4611**.

Against the issue's two candidate root causes:
1. *Mid-task input + Send spawns a new session* — the Build Watch mid-task path
   (`SendSlotInput`) is itself guarded and reuses the row / stops the live process; but its guard
   is click-time and its own resulting launch still passes through the unguarded `LaunchItemCore`,
   so a duplicate can still emerge across the provisioning window.
2. *Resume/Continue duplicates the tab* — the two byte-identical tabs are two distinct queue rows
   both live on one session (Build Watch's slot admission dedups by queue id, so two tabs ⇒ two
   rows), i.e. process duplication, not a pure rendering bug.

Both reduce to the same missing backstop: `LaunchItemCore` must refuse to spawn a `--resume` when
that session is already live under another row.

## Proposed Changes (file-by-file)

1. **`desktop/BuildConsole/Services/QueueWatcherService.cs`**
   - Add a thread-safe helper `LiveQueueIdsForSessionThreadSafe(int exceptQueueId, string? sessionId)`
     that reads `_running` under `_gate` (the existing off-UI-thread-safe pattern) and returns the
     ids of OTHER live entries whose `SessionId`/`ResumeSessionId` matches — `LaunchItemCore` runs
     on a thread-pool thread, so it cannot call the UI-thread-only `LiveQueueIdsForSession`.
   - Add `TryDeferDuplicateResumeAsync(QueueItem item)`: if `item.ResumeSessionId` is live under
     another row, requeue `item` (preserving `resume_session_id`) so the 30s dispatcher tick
     retries it once the live process is gone, log it (throttled, once per deferral episode), and
     return true so the caller returns without spawning.
   - Call it in `LaunchItemCore` at two points: (a) an early cheap check right after account
     routing / before worktree provisioning (avoids provisioning a worktree we'd abandon in the
     common queued-row case); (b) the authoritative last-moment check immediately before
     `RedirectedProcessLauncher.Launch` (catches a session that went live during provisioning),
     disposing the pre-created `entry.TailCts` on that path.

2. **`desktop/BuildConsole/Services/BuildQueuePostgresClient.cs`**
   - Add `RequeueForLiveSessionAsync(int id)`: `UPDATE bt_build_queue SET status='queued',
     claimed_at=NULL, build_pid=NULL, build_pid_started_at=NULL, updated_at=NOW() WHERE id=@id AND
     status='running'`, preserving `resume_session_id`. Mirrors `RequeueLimitPausedAsync`'s shape.

Deliberately **not** stopping the live process from the dispatcher (that would kill possibly-active
work with no user prompt — #4553 established that needs asking) and **not** superseding the row
(that would silently drop a Reply's message). Deferring waits for the live session to finish, then
resumes cleanly — never duplicates, never loses the message.

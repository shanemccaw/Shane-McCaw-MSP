## Research conclusion (evidence-based, done before committing to an approach)
- `claude` v2.1.252: `--help` confirms "starts an interactive session by default, use -p/--print for non-interactive output." Interactive mode is a full-screen ANSI TUI that only renders correctly under a real TTY; `-p/--print` is one-shot (explicitly rejected by the issue).
- **Option 2 (redirected stdio, like the existing line-based `TerminalView`) is unusable** for genuine interactivity — no TTY, and one-shot print mode is not back-and-forth.
- **Option 1 (ConPTY) chosen.** `CreatePseudoConsole` (pure kernel32 P/Invoke, no dependency) gives `claude` a genuine pseudo-terminal. The VT stream is rendered by **xterm.js** (the same emulator VS Code's terminal uses) inside a **WebView2** — WebView2 was already a restored BuildConsole dependency (zero new download); xterm.js (~296KB) was vendored once and committed. This beats hand-rolling ANSI parsing and less-maintained pure-WPF VT libs.

## What shipped (all under desktop/BuildConsole/)
- `Services/PtySession.cs` — ConPTY wrapper: CreatePseudoConsole/Resize/Close, pseudo-console proc-thread attribute, raw byte I/O, resize, exit watch. Hosts `powershell.exe -NoLogo -NoProfile` in repo root so `claude` resolves off PATH on any machine (no hardcoded per-machine claude path).
- `Controls/ClaudeTerminalView.xaml/.cs` — WebView2 host; bridges pty↔xterm.js; **copy/paste routed through WPF `System.Windows.Clipboard`** (Ctrl+C copies selection else sends ^C interrupt; Ctrl+V / right-click paste). Lazily starts the session on first show; persistent shell; "Launch claude" / "Restart shell" toolbar.
- `Assets/xterm/{xterm.js,xterm.css,addon-fit.js,terminal.html}` — vendored xterm surface, served to WebView2 via SetVirtualHostNameToFolderMapping.
- `MainWindow.xaml` — new "Claude" TabItem next to "Terminal".
- `BuildConsole.csproj` — copies `Assets/xterm/**` to output.

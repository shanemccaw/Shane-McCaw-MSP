## Log
- 2026-08-31 ⏳ IN FLIGHT — confirmed real code: `MainWindow.FloatingChat.cs` set `Owner = this`
  when constructing `FloatingChatWindow`, coupling the floaty's activation/z-order to MainWindow.
  Audited `BuildWatchWindow` (`MainWindow.xaml.cs:1518`) — it ALSO sets `Owner = this`, and its own
  comment explicitly documents relying on Owner for auto-close-with-app, "same...lifecycle as the
  Sticky Notes (#937) and LinkedIn (#973) floaties." So the same Owner-coupling pattern exists on
  at least 3 windows (BuildWatch, StickyNotes, LinkedIn composer), all deliberately using Owner for
  close-with-app. Fixing FloatingChatWindow only, per the issue's explicit scope; not touching the
  other three in this build since removing Owner from them requires replicating the same explicit
  close-on-exit hook everywhere and is a bigger, separate change — filed as follow-up **#2076**
  (parented to #1202, board status "AI Batter Up") rather than silently expanding scope.
- 2026-08-31 ✅ DONE — removed `Owner = this` from `MainWindow.FloatingChat.cs`'s
  `OpenFloatingChatWindow`. `ForceTopmost()` in `FloatingChatWindow.xaml.cs` (unmodified) already
  handles always-on-top independently via `SetWindowPos(HWND_TOPMOST, ...)` on `Deactivated`, so
  that half of Owner's behavior is unaffected by the removal. Replaced Owner's auto-close-with-app
  behavior with an explicit `this.Closed += (_, _) => { try { if (win.IsLoaded) win.Close(); } catch
  { } };` hook on MainWindow — same established pattern already used elsewhere in this file (see
  `MainWindow.ResourceMonitor.cs`'s `this.Closed += ...`). Confirmed: closing BuildConsole still
  closes the floaty (via the new explicit hook), and the floaty is no longer coupled to MainWindow's
  activation/z-order (no more `Owner` relationship at all). `dotnet build BuildConsole.csproj -c
  Debug` — 0 warnings, 0 errors. Filed #2076 as the follow-up for the same pattern found on
  BuildWatchWindow/StickyNotes/LinkedIn composer (not fixed here, out of this issue's scope).

## The reach model — the substance of the issue

Azure RBAC is not tenant-scoped, so `GET /subscriptions` returning `{"value":[]}` is **ambiguous**: the listing is RBAC-filtered, so a tenant with fifty subscriptions we hold no role on returns exactly what a tenant with no Azure returns. The one signal that disambiguates it is whether a scope **above** the subscription is readable — a management-group read covers every subscription in the tenant, so an empty listing corroborated by a 200 there is conclusive.

Four states, each from an observed HTTP result, persisted to `tenant_azure_reach`:

| state | meaning |
|---|---|
| `ok` | at least one subscription visible |
| `no_rbac` | valid token, 200, empty listing, management groups **not** readable — we hold no Azure role, and this says nothing about whether the customer has Azure |
| `no_subscriptions` | same empty listing, management groups **readable** — conclusive: the tenant genuinely has no Azure |
| `unreachable` | no ARM token could be acquired at all |

`no_rbac` and `no_subscriptions` map to the new `azure_no_rbac` / `azure_no_subscriptions` profile statuses; `unreachable` stays on the pre-existing `error` bucket.

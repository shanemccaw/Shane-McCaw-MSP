- 2026-08-27 ✅ DONE — new `Services/PostgresServiceMonitor.cs` checks the real local PostgreSQL Windows service directly via `System.ServiceProcess.ServiceController` (confirmed real service name `postgresql-x64-18` on this machine; falls back to a `postgresql*`/`postgres` search for a future major-version rename). Deliberately separate from `SystemHealthService`'s existing "Local Database Pipe" check, which only proves the api-server's own SqlRunner HTTP pipe works and goes red whenever the api-server is down too — it can't distinguish "Postgres service is stopped" from "api-server is down". New always-visible status-bar segment (`MainWindow.xaml`/`.xaml.cs`) matches the existing Deploy/Replit dot+text convention, polls every 15s, and shows a "▶ Start" button only when the service is genuinely down (Stopped/Unknown) — never for Running/pending states. Start invokes `ServiceController.Start()`, then re-checks the SPECIFIC service that was started (not the generic Postgres finder) before reporting success; a Win32 ERROR_ACCESS_DENIED (5) is caught and surfaced as "requires BuildConsole to run elevated" rather than a raw exception. Wired into `ActivityLog` under the `system.health` channel.
  - **Verification:** `dotnet build` clean, 0 errors, only pre-existing warnings. Live-verified with a throwaway standalone harness (same class, real machine): (1) `CheckAsync()` correctly detects the real running `postgresql-x64-18` service; (2) `StartAsync()` on an already-Running service short-circuits `success=true` without needing elevation; (3) caught a real bug during this — the post-start re-check was calling `CheckAsync()`'s generic Postgres finder instead of checking the actual service that was started, so it could silently report success against the wrong service if the finder ever resolved differently. Fixed by adding `CheckSpecificAsync(serviceName)` and using it in `StartAsync`'s re-check; re-verified against a real stopped non-Postgres service (`Fax`) that the recheck now correctly reports `Fax: Stopped` rather than falsely borrowing Postgres's healthy state. Did NOT stop the real shared local Postgres service to test the down-path end-to-end — it's the shared dev DB other concurrent sessions may depend on; the down/Stopped/NotFound rendering and the ERROR_ACCESS_DENIED catch path are logic-reviewed against a real non-elevated shell (confirmed `IsElevatedAdmin: False` in this session) but not force-triggered against Postgres itself. The `Fax` service was left in its original Stopped state after testing (double-checked).
  - **Honest gap:** the elevation-denied message path (Win32 error 5) exercises well-established .NET `ServiceController` behavior but wasn't forced against the real Postgres service, to avoid disrupting the shared local dev DB.

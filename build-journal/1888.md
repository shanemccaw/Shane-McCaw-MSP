# #1888 — Screen clip: crosshair shows but drag-to-select never registers

- **Status:** ✅ DONE
- **Scope:** buildconsole
- **Started:** 2026-08-30
- **Commit(s):** `68bffc756` (IN FLIGHT bookend), `966eb877f` (fix). Both on `origin/main`.

## Root cause (the real reason, not either literal candidate in the issue body)
`RegionSelectOverlayWindow.xaml`'s mouse handlers (`MouseLeftButtonDown/Move/Up`) live on
`RootCanvas`, but the `Canvas` had a **null `Background`**. A WPF panel with a null background
is **not hit-test-visible over its empty (child-free) area**, so pressing on the dim overlay
never routed a mouse event through the Canvas — `RootCanvas_MouseLeftButtonDown` never fired,
so `_dragging` never became true and no selection rectangle was drawn. The `#40000000` dim is a
hittable brush but it's on the **Window**, not the Canvas, and the handlers are on the Canvas (a
null-background descendant), so the press fell through to the Window, which has no mouse handler.
Escape worked because `Window_KeyDown` is on the focused Window — which also proves the window
WAS activated/focused, ruling out the issue's candidate #2 (global-hotkey activation/focus).

This is shared code, so **both** paths had the bug: the #1866 desktop screen-clip path AND the
original #1472 VisualTestTracker region-capture path (both use this one overlay). Candidates #1
(virtual-screen config) and #2 (hotkey focus) were red herrings — the cause is path-independent.

## Fix
One line: `Background="Transparent"` on `RootCanvas` (Transparent IS hit-test-visible, unlike
null). The whole overlay now catches the drag; the Window's dim still shows through the
transparent Canvas. Fix commit `966eb877f`.

Win32 `mouse_event`/`SetCursorPos` — the same system input queue a physical mouse feeds, NOT a
headless handler simulation. Ran it against BOTH the fixed and the pre-fix (commit `be03fcb2c`,
null-background) XAML using the identical `.xaml.cs`:

- **Unfixed:** live drag (500,300)->(900,600) -> `_dragging=False`, `SelectionRect=Collapsed` ->
  **MouseDown never fired**, `DialogResult=False`, no selection. Reproduces #1888 exactly
  (crosshair shows, drag ignored, only close-out works).
- **Fixed:** same live drag -> MouseDown fired, `SelectedPhysicalRect = X=500 Y=300 W=400 H=300`
  (exactly the drag geometry), `DialogResult=True`, overlay closed cleanly. **PASS.**

The before/after proves the test is meaningful and would have caught the original bug — the gap
#1866's bookend admitted ("the interactive drag itself can't be driven headlessly").

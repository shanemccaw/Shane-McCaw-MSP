# #4679 — Plan & Walkthrough: self-halted-blocked builds never auto-resume

Base commit for all permalinks below: `abe2ce5c23ee08463e4c18f784df826dd9457022` (origin/main at session start).

## Problem Description

A build that self-halts as *blocked* — per the CLAUDE.md protocol it writes a `🛑 BLOCKED`
bookend, adds the `blocked` label, wires a real GitHub `blocked_by` edge, then exits the
process cleanly (exit 0) — never re-enters the automatic claim/launch cycle once its real
blockers close. It sits until a human notices and manually re-dispatches it, costing hours
of dead time per issue.

Real evidence (from #4679 body): #4650, #4651, #4652, #4641 (M365Architect builds, tracking
issues in this repo) each self-halted ~04:2x–04:4x on 2026-09-18, their blockers closed
shortly after, and none auto-resumed — all were manually re-dispatched ~9 hours later
(#4641 not at all until a human intervened).

## Root Cause Analysis

### This is a DISTINCT gap, NOT a regression of #3517/#3521.

#3517 and #3521 both operate on one specific state: a **supervisory cancel** — a row set to
`status='canceled', exit_code=0` by the false-done/board reconciler. #3517 taught
`BatterUpQueueService.QueueRowAsync` to re-queue such a row; #3521 replaced its `IsBlocked`
guard with a `supervisory_requeue_count` bound; #3661 added the dedicated
`WaitingRowAutoRequeueService` → `BuildQueuePostgresClient.SweepAutoRequeueWaitingAsync`
periodic-then-event-driven sweep. **Every one of these keys off `status='canceled' AND
exit_code=0`.**

A self-halted-blocked build **never reaches that state** on the code path this issue is
about, so none of #3517/#3521/#3661 can fire. Confirmed by reading the code + live
`bt_build_queue`:

1. **Where the row actually lands (answers issue Q1).** The only completion signal
   `bt_build_queue` gets is `QueueWatcherService` → `MarkCompleteAsync`. A clean exit (0) on
   a row **with a real `github_number`** lands at `verifying` (Git #1469 real-Verifying gate),
   `exit_code=0` — indistinguishable, at that instant, from a genuinely-completed build
   awaiting its issue's close.
   `MarkCompleteAsync`: [BuildQueuePostgresClient.cs#L1551-L1592](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/abe2ce5c23ee08463e4c18f784df826dd9457022/desktop/BuildConsole/Services/BuildQueuePostgresClient.cs#L1551-L1592)

2. **The claim loop never reconsiders it (answers issue Q2).** `GetNextAsync` →
   `SelectClaimCandidatesAsync` scans **only** `status='queued'` (`QueuedCandidateSql`). A
   `verifying` row is not a claim candidate, so it is never re-evaluated for launch.
   `QueuedCandidateSql`: [BuildQueuePostgresClient.cs#L385-L393](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/abe2ce5c23ee08463e4c18f784df826dd9457022/desktop/BuildConsole/Services/BuildQueuePostgresClient.cs#L385-L393)

3. **All three paths that could turn `verifying` → the re-dispatchable `canceled+exit0`
   state miss a `--cwd` / cross-repo build (answers issue Q3).** The evidence builds ran in
   M365Architect (`--cwd` into a separate clone), tracking issues in this repo:
   - **#3628 immediate reap correction** (the one that *does* detect a self-block at exit and
     reset to `canceled`) is gated on `!string.IsNullOrWhiteSpace(entry.WorktreePath)`. A
     `--cwd` build has `worktreePath == null` (it never went through worktree provisioning —
     `workDir = item.Cwd`), so this whole block is skipped.
     Gate: [QueueWatcherService.cs#L2319-L2348](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/abe2ce5c23ee08463e4c18f784df826dd9457022/desktop/BuildConsole/Services/QueueWatcherService.cs#L2319-L2348);
     `worktreePath` stays null for a `--cwd` build: [QueueWatcherService.cs#L2828-L2831](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/abe2ce5c23ee08463e4c18f784df826dd9457022/desktop/BuildConsole/Services/QueueWatcherService.cs#L2828-L2831)
   - **FalseDoneReconciler Shape A** detects a BLOCKED bookend via `DoneBookendVerifier`,
     which reads `git show origin/main:build-journal/{N}.md` from the **main repo checkout
     only** (`BuildTrackerConfig.FindRepoRoot()`). An M365Architect bookend lives in the
     M365Architect repo — confirmed absent here (`build-journal/4650.md` etc. do not exist in
     this repo) — so Shape A can never see it. It is also manual-board-refresh-only.
     Shape A: [FalseDoneReconciler.cs#L92-L132](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/abe2ce5c23ee08463e4c18f784df826dd9457022/desktop/BuildConsole/Services/FalseDoneReconciler.cs#L92-L132);
     main-repo-only bookend read: [DoneBookendVerifier.cs#L142-L180](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/abe2ce5c23ee08463e4c18f784df826dd9457022/desktop/BuildConsole/Services/DoneBookendVerifier.cs#L142-L180)
   - **#3661 `SweepAutoRequeueWaitingAsync`** only queries `GetWaitingSelfBlockedAsync()` =
     `status='canceled' AND exit_code=0`. A `verifying` row is never a candidate.
     [BuildQueuePostgresClient.cs#L3095-L3116](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/abe2ce5c23ee08463e4c18f784df826dd9457022/desktop/BuildConsole/Services/BuildQueuePostgresClient.cs#L3095-L3116)

   Net: a self-halted-blocked `--cwd`/cross-repo build is stranded at `verifying`, invisible
   to every auto-recovery path. Live `bt_build_queue` confirms these rows carry a real
   `github_number`, populated `blocked_by_numbers`, `repo_owner=shanemccaw /
   repo_name=Shane-McCaw-MSP`, and were only cleared by manual re-dispatch.

### Q4 — the local blocker set CAN be incomplete, but that half is already fixed; the
missing half is requeue.

Git #3623 already (a) re-checks live GitHub `blocked_by` edges at claim time
(`ApplyLiveBlockerEdgesAsync`) and (b) periodically re-syncs `blocked_by_numbers` from the
real GitHub dependency graph for rows including `verifying` and `canceled+exit0`
(`ResyncLiveBlockedByAsync`). So a row's stored blocker set is kept live-accurate. What
#3623 does **not** do is *requeue* — it only records edges. So #4641's stored set is now
complete (`{4642,4640}`), yet nothing moved it out of its stuck state. The fix must add the
requeue, and lean on #3623's existing claim-time live-edge re-check as the pre-launch safety
net (a requeued row is `queued`, so `ApplyLiveBlockerEdgesAsync` re-holds it if any live
edge is still open — we can never wrongly launch).

### Airplane-icon fold-in — SAME repo-scoping root cause (confirmed, real finding).

BuildConsole's bookend-check UI ("airplane icon") reads through the same `DoneBookendVerifier`
machinery, which is hardcoded to the **main repo** checkout (`BuildTrackerConfig.FindRepoRoot()`
→ `git show origin/main:build-journal/{N}.md`). For an M365Architect tracking issue the
bookend lives in the M365Architect repo, so the read returns "no bookend" and the icon shows
"missing bookend" even though a real bookend exists. This is the **same** main-repo-only
repo-scoping gap that stops FalseDoneReconciler Shape A from seeing these bookends — not a
separate mechanism. It is out of scope for this fix's code change (a multi-repo bookend
resolver is a larger change) and will be filed as a sibling finding under #3706; the fix
below deliberately routes around it by using the cross-repo-visible `blocked` **label**
instead of the bookend.

## User Review Required

None — this is a build-queue reliability fix using existing states/columns and existing,
documented signals (the `blocked` label + live GitHub blocker state). No schema change, no
product/entitlement decision.

## Proposed Changes

**No migration** — reuses existing `status`/`exit_code`/`blocked_by*` columns and existing
methods.

1. **`desktop/BuildConsole/Services/BuildQueuePostgresClient.cs`** — add
   `GetSelfHaltedBlockedVerifyingRowsAsync()`: rows at `status = <VerifyingStatus> AND
   exit_code = 0 AND github_number > 0 AND archived IS NOT TRUE` that declare at least one
   blocker (`blocked_by_number` or non-empty `blocked_by_numbers`). This is the candidate set
   of possibly-self-halted rows the existing `GetWaitingSelfBlockedAsync()` (canceled+exit0)
   misses.

2. **`desktop/BuildConsole/Services/BuildQueuePostgresClient.cs`** — extend
   `SweepAutoRequeueWaitingAsync` with a pre-step that runs **before** the existing
   canceled+exit0 requeue logic:
   - fetch the candidates from (1);
   - if any, live-fetch the set of open issues currently carrying the `blocked` label via
     `GitHubIssuesService.ListOpenByLabelAsync("blocked", ...)` — the cross-repo-safe positive
     evidence of a self-halt (a genuinely-completed `verifying` row awaiting close does NOT
     carry `blocked`);
   - for each candidate whose `github_number` is in that set, reset it to `canceled` via the
     existing `MarkFalseDoneReconciledAsync(id)` (guarded `status IN ('done', verifying) AND
     github_number IS NOT NULL`, leaving `exit_code=0`), and best-effort mirror its board to
     Backlog (`BoardStatusSync.Mirror(num, GitHubApiClient.BacklogOptionId, ...)`), exactly as
     Shape A / #3628 already do;
   - then fall through to the existing `GetWaitingSelfBlockedAsync()` requeue pass, which now
     includes the just-reset rows and requeues any whose blockers are confirmed clear (and
     leaves the rest sitting at `canceled+exit0` = ⏳ WAITING for the next trigger, exactly the
     #3661 design). Fail-closed: if the label query fails/returns empty, nothing is reset this
     pass (we only ever act on a positive label match), retried next trigger.

   This funnels a self-halted `verifying` row into the exact, well-tested `canceled+exit0`
   auto-requeue path #3661/#3517/#3521 already own, using a signal that works regardless of
   which repo the code (and its bookend) lives in. Telemetry stays on the existing
   `ActivityLog.Log("auto-requeue", …)` channel used throughout this sweep.

3. **`desktop/BuildConsole/Services/WaitingRowAutoRequeueService.cs`** — no signature change;
   its existing event-driven triggers (`QueueWatcherService.BuildFinished` + manual board
   refresh) now also drive the new verifying-detection because it lives inside
   `SweepAutoRequeueWaitingAsync`. Update the class doc comment to note the widened scope.

## What was actually wrong, and how the fix prevents overcommit

### Mechanism 1 — session-limit slot leak (the confirmed root cause)

**Before:** the `TickAsync` reap loop (`~line 1276`) removed a limit-paused build from
`_running` with an unconditional `_running.Remove(id)`, exactly like a normal exit. But a
limit-paused build is *promised back*: `SessionLimitAutoRestartService.FireAsync` flips its
row `limit-paused` → `queued` ~10-15 min later (`ResumeLimitPausedAsync`), and the next tick
re-claims it via `GetNextAsync` → `LaunchItem`, adding a **fresh** `_running` entry — with
nothing ever subtracted for the gap. So the instant it parked, `freeSlots = _maxConcurrent -
_running.Count` saw one extra free slot and launched a replacement; when the original resumed,
real running count exceeded `_maxConcurrent`. Across many sessions capping in the same usage
window under a 40+ queue, this compounded to the 9/10/11/15 Shane watched → crash.

**Fix (Option B — reserved-slot set keyed by queue id):**
- New `private readonly HashSet<int> _reservedSlots` (UI-thread-only, same as `_running`).
- **Add on park:** in the reap loop, right after `_running.Remove(id)`, `if (limitParked) _reservedSlots.Add(id)`.
- **Subtract from capacity:** `freeSlots = _maxConcurrent - _running.Count - _reservedSlots.Count`; Start Now's capacity gate uses `_running.Count + _reservedSlots.Count` too.
- **Release on reoccupy:** `_reservedSlots.Remove(item.Id)` at the top of `LaunchItem` (the resumed build now counts in `_running`).
- **Reconcile each tick (the authority for removal):** when `_reservedSlots.Count > 0`, `_reservedSlots.IntersectWith({ids currently 'limit-paused' per GetLimitPausedAsync})`. This drops a reservation the moment its row leaves limit-paused status — covering auto-resume, manual resume, cancel and delete in one step — and keeps a still-paused build reserved. Best-effort: a transient DB error keeps existing reservations (the safe, never-overcommit direction). No DB call in the common (no paused builds) case.

**Invariant established:** `_running.Count + _reservedSlots.Count` never exceeds `_maxConcurrent`.
A slot is reserved **iff** a `limit-paused` DB row exists for it, so a reservation can never
leak permanently (every exit path from limit-paused drops it; an app restart clears the whole
in-memory set and every pending build flows back through the normal claim path — no phantom
re-add to compensate for, nothing to persist).

**Deterministic trace of the exact crash sequence, under the fixed code (cap = 8):**
1. 8 running, 0 reserved → `freeSlots = 8 - 8 - 0 = 0`. Nothing launches.
2. Build #5 limit-hits → process exits → reap parks it → `_running.Remove(5)` (→7), `_reservedSlots.Add(5)` (→1). Same-tick reconcile: `GetLimitPausedAsync` includes #5 → kept. `freeSlots = 8 - 7 - 1 = 0` → **no replacement launches** (the old code computed `8 - 7 = 1` here and launched one — the bug).
3. ~15 min later `FireAsync` flips #5 → `queued`. Next tick reconcile: #5 no longer limit-paused → dropped (→0). `freeSlots = 8 - 7 - 0 = 1` → `GetNextAsync(1)` claims #5 → `LaunchItem(#5)` removes reservation (no-op) + adds `_running[5]` (→8).
   Running never exceeds 8 at any point.

### Mechanism 2 — premature auto-finalize while a sub-agent is in flight

**Before:** `ScheduleAutoFinalize`'s idle timer force-closed stdin whenever
`entry.AwaitingInputSince != null && !entry.Process.HasExited`, **never** consulting the
`entry.ActiveSubagents` list the code already maintains (added on a Task/workflow `tool_call`,
removed on its `tool_result`, in `AppendEvent`). A parent turn that went idle only because it
was waiting on its own Task-tool sub-agent got finalized mid-work: the tracked parent was
force-exited, its slot freed/badged green, and the sub-agent (when it runs as its own process)
left running orphaned and untracked outside the concurrency system — "claude.exe stays alive…
because they have a sub agent going."

**Fix:** the auto-finalize continuation now, under `_gate`, checks
`entry.ActiveSubagents.Count`. If the build is idle **and** has ≥1 active tracked sub-agent it
does NOT close stdin — it re-arms the idle timer (`ScheduleAutoFinalize`, valid under `_gate`)
and returns, logging the deferral. It re-checks after each idle interval; `ActiveSubagents`
empties on each `tool_result`, so a long-running agent simply keeps deferring until done. The
re-arm chain terminates on its own the moment the process actually exits (`HasExited` flips
`idle` false → no further re-arm). This only ever ADDS a guard that prevents a premature close;
it never makes finalize more aggressive, so it is strictly safer than before.

**Honest caveat (not a blocker for the fix, noted for completeness):** the guard protects every
case where `ActiveSubagents` genuinely reflects in-flight background work. For a foreground Task
the tool_result only lands on completion, so it is held active the whole time and fully
protected. Whether `ActiveSubagents` also captures a `run_in_background` agent *past its initial
ack tool_result* (which `AppendEvent` would remove on the matching `tool_use_id`) is not
determinable from static reading alone and would need live stream-json samples to pin down — but
this fix is exactly the issue's prescribed direction (consult the existing
`GetActiveSubagents`/`SubagentActivityInfo` mechanism) and can only make finalization safer.

## Also-checked items from the issue

1. **UI display of a limit-paused row (green/success vs distinct state):** already correct —
   **no code change made** (touching correct code would violate "commit only your own changes").
   In Build Watch, `ApplyItemStatusToSlot` maps `"limit-paused"` → `SlotState.Stalled`
   (`BuildWatchWindow.xaml.cs:1034`), and the local-exit path maps it to `Stalled` too when
   `_watcher.IsSessionLimitHit(id)` is true (`:903`). `IsSessionLimitHit` and `HasExited` both
   check `_retained` first, so a reaped-then-retained limit-paused interactive build keeps
   reporting `SessionLimitHit=true` and never flips to green Done. `SlotState.Stalled` renders an
   amber "STALLED" pill (warning border, session-limit tooltip, `CompletedAtUtc = null` so it's
   never counted done or auto-evicted) — distinctly NOT green/success. `BuildQueuePanel` likewise
   renders limit-paused as its own Park state throughout. Shane's earlier "displays GREEN"
   observation predates this mapping.
2. **`RegisterLimitHit` / restart-relaunch reuses the held slot correctly:** confirmed. The
   parking side (`RegisterLimitHit`, unchanged) arms the restart; the resume side
   (`FireAsync` → `ResumeLimitPausedAsync` → `queued` → `GetNextAsync`/`LaunchItem`) is where the
   held slot is released and reoccupied — the reconcile drops the reservation the same tick the
   row leaves limit-paused, and `LaunchItem` clears it again defensively before re-adding to
   `_running`. Parking side fixed without breaking the resume side (see the trace above).

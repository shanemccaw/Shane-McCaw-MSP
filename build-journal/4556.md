## Changes Made

- `lib/db/src/schema/msp.ts` — widened `monitor_checks.required_service_plans`'s `$type` from
  `string[] | null` to `string[] | string[][] | null`; doc comment explains both the existing
  flat ANY-OF shape and the new nested AND-of-OR shape.
- `artifacts/api-server/src/lib/license-gate.ts`
  - `tenantHasRequiredLicense` now detects a nested `string[][]` (first element is itself an
    array) and evaluates `.every(group => group.some(sku => tenantPlans.has(sku)))` — AND
    across groups, ANY-OF within each group. Flat `string[]` behavior is completely unchanged.
    This reuses the exact array-of-arrays shape `config-pack-preconditions.ts` already uses for
    `requiredLicenseSkuLists`, so it's one shared implementation rather than a new pattern.
  - `licenseFeatureName`/`describeRequiredLicense` now produce readable text for the nested
    case (groups joined with `" and "`, e.g. `"Microsoft Entra ID P1 or P2 and Microsoft
    Intune"`).
  - Added `INTUNE_A: { family: "Microsoft Intune", label: "" }` to `LICENSE_SKU_DISPLAY`.
  - `monitor-executor.ts` needed **no code change** — its existing
    `Array.isArray(check.requiredServicePlans) && .length > 0` guard and calls into
    `tenantHasRequiredLicense`/`licenseFeatureName` already pass the raw column value straight
    through; both functions handle the nested shape transparently.
- New migration `lib/db/migrations/manual/2026-09-17-ca-device-compliance-all-of-intune-4556.sql`
  — additive, idempotent UPDATE of the one `identity:ca-device-compliance` row:
  `required_service_plans = [["AAD_PREMIUM","AAD_PREMIUM_P2"],["INTUNE_A"]]`, updated
  description, `schema_version` bumped 2→3. **Ran locally against `DATABASE_URL`** (additive
  DDL/DML per CLAUDE.md) — confirmed via `SELECT`, row now shows the nested value and
  `schema_version = 3`.
- Extended `license-gate.test.ts` (grouped `tenantHasRequiredLicense`/`licenseFeatureName`/
  `describeRequiredLicense` cases) and `monitor-executor.test.ts`'s
  `identity:ca-device-compliance` describe block (new "P1 present but no Intune → still a
  license gap" test — the real defect this build fixes — plus updated fixtures/expected text
  for the other cases in that block).
- **Audit (per dispatch note):** queried `monitor_checks` and `write_action_catalog` directly.
  Confirmed the other three #4512 CA checks (`ca-mfa-coverage`, `ca-legacy-auth-block`,
  `ca-policy-count`) only need P1/P2 (no device-state grant, no Intune dependency), and all 12
  `write_action_catalog` Conditional Access rows are generic "Create/Update/Delete CA policy"
  actions not scoped to a device-compliance grant. `identity:ca-device-compliance` is the only
  row with a real unmet AND requirement. No new finding to file.

- Architecture for THIS issue: the settled table's "Tenant state" column is two
  independent, already-real per-tenant consent keys on `tenants.consent`
  (`graph.status`, `writeBack.status`) — not policy.isActive (that is #1547's own
  separate opt-in gate on the policy object). "Not opted in" = the tenant has not
  granted Graph READ consent at all (`consent.graph.status !== "granted"`) — literally
  cannot detect divergence without it, matching "no evaluation, no action". Within a
  connected tenant, `writeBack.status === "granted"` decides `engine_enacts` vs
  `checklist_item`, mirroring `resolveTenantWriteCeiling` from #1539's resolver.
  Building a pure resolver (`policy-enactment-route.ts`) + a preview wire endpoint on
  the existing `msp-standing-policies.ts` route file. No new schema — this issue
  resolves against state that already exists.

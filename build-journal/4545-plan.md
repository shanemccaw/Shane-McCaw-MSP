# Plan: #4545 — close the 4 remaining tenant-precondition gaps

Posted: 2026-09-17T23:38:55Z

## Problem Description

`resolveTenantWritePreconditionRefusal` (`artifacts/api-server/src/lib/tenant-write-preconditions.ts`)
is the one #4513/#4528 evaluation that refuses a tenant write BEFORE it fires when the tenant
lacks a catalog-recorded license, or when a step would turn Security Defaults off with no
enforcing Conditional Access replacement in the same run. It is wired into three real paths
today: Config Pack runs (`config-pack-orchestrator.ts`), a single `execute_action`
(`admin-execute-action.ts`), and SOP runs (`sop-execution.ts`). Four other real execution paths
fire the same class of `baseline_action_templates` write and skip it entirely:

1. **`admin-baseline-templates.ts:370`** — the template test-run route
   (`POST /admin/baseline-templates/:templateId/test`) calls
   `runBaselineTemplateAgainstTenant(templateId, ...)` gated only by `isTestbed`. The testbed
   tenant `mccawsoft2` is also the real production M365 tenant (#1913): running
   `quickstart-v1.disable-security-defaults` from here turns Security Defaults off with no
   replacement, and no license check runs at all.
   https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e244549245eb8ffbeb818b2066a2050d1921dcd/artifacts/api-server/src/routes/admin-baseline-templates.ts#L333-L378

2. **`admin-write-actions.ts:422`** — the write-actions simulator execute
   (`POST /admin/write-actions/:templateId/execute`) has the identical shape: testbed-gated only,
   no license or Security Defaults check before `runBaselineTemplateAgainstTenant`.
   https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e244549245eb8ffbeb818b2066a2050d1921dcd/artifacts/api-server/src/routes/admin-write-actions.ts#L387-L448

3. **`workflow-executor.ts:10083`** (real case block at `~10153`) — the generic
   `execute_baseline_template` workflow node, reachable from any workflow definition fired via
   `admin-workflows.ts`, has no license or Security Defaults check. #4529's
   `compensateSecurityDefaultsForRun` re-enables Security Defaults after a failed/cancelled run —
   a compensation *after* the write, not a refusal *before* it.
   https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e244549245eb8ffbeb818b2066a2050d1921dcd/artifacts/api-server/src/lib/workflow-executor.ts#L10152-L10247

4. **`msp-launch-control.ts:558`** — `POST /msp/:mspId/launch-control/execute` already runs the
   #3947 proactive license gate (a different, older, equally-real mechanism keyed off the
   catalog row's own `required_license_skus`), but has no Security Defaults replacement rule at
   all before `runBaselineTemplateAgainstTenant` fires.
   https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e244549245eb8ffbeb818b2066a2050d1921dcd/artifacts/api-server/src/routes/msp-launch-control.ts#L405-L594

Evidence: `grep -n "ecurityDefaults\|evaluateConfigPackPreconditions\|resolveTenantWritePrecondition"`
over these four files returns no match apart from the #4529 compensation lines in
`workflow-executor.ts`.

## Root Cause Analysis

`resolveTenantWritePreconditionRefusal` was introduced under #4528 and wired into the three
paths that existed at the time it was scoped (pack / execute_action / SOP). Nothing enforces
that a *new* write-firing call site also calls it — it's an opt-in convention, not a structural
gate, so every call site that fires `runBaselineTemplateAgainstTenant` (or an equivalent write)
has to remember to call the shared precondition function itself, in the right order, before the
write. Four call sites that predate or sit outside #4528's original scope never got wired.

## Proposed Changes

All four call through the *same* `resolveTenantWritePreconditionRefusal` /
`loadRequiredLicenseSkuListsByTemplate` pair already used by the three correct paths — no new
precondition logic, no per-site reimplementation.

- **`artifacts/api-server/src/lib/tenant-write-preconditions.ts`** — export one shared
  `PRECONDITION_HTTP_STATUS: Record<string, number>` (`license_required`: 409,
  `security_defaults_replacement_not_enforcing`: 422, `ca_enforcement_requires_promotion`: 422)
  so the two new HTTP routes below map a refusal code to a status the same way
  `admin-execute-action.ts` and `admin-config-pack-run.ts` already do, instead of a third/fourth
  copy of the same object literal.

- **`artifacts/api-server/src/routes/admin-baseline-templates.ts`** (test-run route, ~L368) —
  before calling `runBaselineTemplateAgainstTenant`, call `loadRequiredLicenseSkuListsByTemplate`
  and `resolveTenantWritePreconditionRefusal` with a single step built from the already-selected
  `template` row (`method`/`endpoint`/`bodyTemplate`) and `customer.tenantId`/`payload`. Refuse
  with the mapped status + the refusal body (same shape `admin-execute-action.ts` returns) instead
  of executing.

- **`artifacts/api-server/src/routes/admin-write-actions.ts`** (execute route, ~L404-422) — same
  pattern: the `template` row is already selected in full; add the same precondition call between
  the existing `template.status !== "active"` check and the `runBaselineTemplateAgainstTenant`
  call, refusing before the write.

- **`artifacts/api-server/src/lib/workflow-executor.ts`** (`execute_baseline_template` case,
  ~L10187) — after resolving `ebtCustomerRow.tenantId`, select the template's
  `method`/`endpoint`/`bodyTemplate`, load its license lists, and call
  `resolveTenantWritePreconditionRefusal` with a single step (passing through
  `caEnforcementMode: "immediate"` only when the run's payload already carries it, same test the
  existing `ebtCaEnforcement` derivation uses). On refusal: `nodeError = true`,
  `switchChosenHandle = refusal.code` (consistent with the existing `ebtResult.errorType`-driven
  handle below), `output` carries `success:false`, `errorType`, `error`, and the refusal's
  `details` — no write is attempted.

- **`artifacts/api-server/src/routes/msp-launch-control.ts`** (execute route, ~L550-566) — after
  the existing CA-enforcement-kind refusal and before `raiseChangeRequestForLaunchControlExecution`
  (never raise a Change Request for a write that's about to be refused), add the same
  `loadRequiredLicenseSkuListsByTemplate` + `resolveTenantWritePreconditionRefusal` call using the
  already-selected `template` row and `customer.tenantId`/`payload`. The existing #3947 proactive
  license check stays as-is (it already gates license, with its own `errorType: "license_gap"`
  response shape other callers depend on) — this addition is what actually closes the gap named in
  the issue: Security Defaults replacement. Rule 0 (CA enforcement) and rule 1 (license) in the
  shared evaluator will simply find nothing new to refuse at this point, since they're already
  covered earlier in this route.

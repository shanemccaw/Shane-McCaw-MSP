## DPI approach (per the issue's explicit ask)
Worked in **physical pixels end-to-end**, converting once at the boundary. The overlay's
authoritative selection comes from the **Win32 `GetCursorPos`** at drag start/end, not WPF's
per-visual-root DIP mapping. `GetCursorPos` and `Graphics.CopyFromScreen` share the same GDI /
process coordinate space, so a selection spanning two monitors at different scale factors is
captured at the right offset and size regardless of DPI — no single `TransformToDevice` factor is
ever applied across a monitor seam. The WPF-DIP `SelectedRect`/WebView2 path is untouched.

**DPI test caveat (honest):** Shane's two monitors are **both 96 DPI (100% / 1.0× scale)** —
`Screen.AllScreens` reported `DISPLAY1 {1920,0 1920x1080}` and `DISPLAY2 (primary) {0,0 1920x1080}`,
both `dpi=(96,96)`, virtual screen `0,0 3840x1080`. So I could **not** exercise the *different*-DPI
case on this hardware; I'm saying that plainly rather than implying I tested it. The approach is
DPI-agnostic by construction (physical cursor coords + CopyFromScreen in the same space), and an
across-two-monitors selection is geometrically possible via the 3840-wide virtual screen.

## Verification (headless harness exercising the identical code paths)
The interactive drag itself can't be driven headlessly; it's build + code-review verified. Everything
else was run for real via a throwaway STA harness using the exact CopyFromScreen / PNG-save /
multi-format-clipboard logic (harness lived in `%TEMP%`, deleted — tree left clean):
- **Release build:** `dotnet build ... -c Release` → 0 warnings, 0 errors (twice: original, and again after the recovery rebase onto current main).
- **Capture + save:** `CopyFromScreen` into a 24bpp bitmap → PNG. 300×200 clip, 8934 bytes, 21 distinct
  sampled colors (real desktop pixels — the Catppuccin base `RGB(24,24,38)`, **not** a flat/black
  frame). In-app the overlay is **closed** (not merely hidden) before capture, then WPF renders are
  flushed + a 120 ms DWM settle, so the dim layer is gone before the read.
- **Clipboard fidelity (the "pastes black" test):** round-tripped the clipboard back — `ContainsImage=True`,
  formats present = **`System.Drawing.Bitmap, Bitmap, PNG`**, image read back `allBlack=False`
  (center `RGB(25,25,38)`). This is the exact byte set a real paste (Paint/Office/browser) receives.
  24bpp target means `CopyFromScreen`'s unset alpha can't produce transparent→black. I could not
  drive Paint's GUI headlessly; the round-trip read of the CF_DIB/PNG the OS holds is the strongest
  real check available and it is not black.
- **Same-second collision:** two clips at second `:14` produced `...14-884.png` and `...14-887.png` —
  distinct (millisecond precision, with a `_N` counter backstop for the same ms).
- **Esc / both-sinks-independent:** by construction — the service returns before any clipboard/disk
  call when `ShowDialog()!=true`, and disk save / clipboard copy are independent try/catch blocks
  each surfaced via toast, so a failure of one never loses the other silently.
- **PrintScreen registration on THIS machine:** not run live (headless), but wired both ways:
  `RegisterHotKey(VK_SNAPSHOT)` (gated by the new `ScreenClipGlobalHotkeyEnabled` setting, default on)
  with the refusal path fully handled — logged on `system.core`, a one-time toast, and the reason
  placed in `BtnScreenClip.ToolTip` — plus an in-app `KeyUp` fallback for `Key.Snapshot` that only
  fires when the global registration was refused (double-fire guard), backed by the service's
  `_overlayOpen` re-entry guard.

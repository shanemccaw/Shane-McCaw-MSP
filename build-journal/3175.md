## Log
- 2026-09-08T03:51:58Z ⏳ IN FLIGHT — Picking up #3175. The #3140 orphan-ledger guard (`assertNoOrphanLedgerRows`) fails closed whenever the shared `finances` `schema_migrations` ledger names a migration file a concurrent sibling build applied but has not yet landed on `origin/main`. That blocks `runMigrations`, which blocks server boot, which blocks `npm start` AND `npm run check`. Plan: implement the issue's own "smallest correct fix" — distinguish a ledger row that is *ahead* of this worktree (a sibling's higher-numbered migration; nothing on disk can be a rename of it) from one that is genuinely *missing* (a rename of a file this worktree does have at that number). Fail closed only on the second.
- 2026-09-08T04:12:00Z ✅ DONE — Shipped the ahead-vs-missing split. `scripts/check-migration-numbers.mjs` gains `highestOnDiskMigrationNumber()` and `classifyOrphanLedgerFilenames()`; `assertNoOrphanLedgerRows()` now throws only on `missing` and returns `{ ahead, missing, highestOnDisk }` so `web/shanes-life/src/migrate.mjs` can log the ahead rows in its own voice and carry on. `findOrphanLedgerFilenames()` keeps its original "not on disk" meaning untouched, because `bin/reconcile-ledger.mjs` depends on exactly that.

  **The rule:** an orphan whose leading number is strictly above every number on disk cannot be a rename of anything in this checkout — there is no file at that number here at all — so it is a sibling's unlanded migration and is harmless. Everything else stays fatal, including the case where a sibling *took your number first*, which needs you to renumber; the failure message now names which of the two real causes it is instead of only describing a rename.

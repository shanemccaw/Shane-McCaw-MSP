So the DB-write half of the pipeline is not currently reproducing broken on the evidence available.
- Root-caused a real, code-provable bug via static+DB evidence: `OpenWebTab`'s "deduplicate if already open" loop matches by exact URL. `EpicChatUrlBuilder.BuildEpicChatUrl` builds a **fully deterministic** URL for a given epic number (same `McpInstructionLine` + label every time, no nonce) — so a second "Start New Chat" against the SAME epic, in the same app session, silently reselects the FIRST click's existing tab instead of opening a new WebView2/new navigation/new watcher/new bt_chats row. This was completely unlogged before this build (the dedup-match `return` had zero ActivityLog line). This directly matches Shane's "the transition doesn't work right, the saving doesn't work right" — a repeat attempt (very plausible exactly while troubleshooting this issue) looks like nothing happened.
- **No genuine live click-through repro was performed this session** — BuildConsole has no `shaneapp://`-style protocol for driving its own WPF menus/dialogs (those protocols target the product apps, not BuildConsole's own UI), and rebuilding+restarting Shane's live, currently-running BuildConsole instance to pick up new diagnostics would have killed his live session, which is not this session's call to make. This is an honest, stated limitation per the "genuinely unreachable" escape valve (Git #2160), not an assumed default.

## What shipped
- `desktop/BuildConsole/MainWindow.xaml.cs`:
  1. **Fix**: `OpenWebTab`'s URL-dedup now skips entirely when `injectPrefillPoll` is true (true for every real "New Chat" call site: `MenuNewChat_Click`, Hand Off Now, `OpenOrCreateEpicChat`, and every LeftSidebar epic/issue/milestone "New Chat" menu item routed through `EpicChatRequested`'s `InjectPrefill=true` sites) — so a repeat "Start New Chat" against the same epic always opens a genuinely new tab/conversation instead of silently reselecting a stale one. The dedup itself is now also logged (both the skip and the reuse case), where before it was completely silent.
  2. **Diagnostics** (`git-board.chat` channel), exactly the 3 stages the issue asked for, so the NEXT live occurrence pinpoints the real break instantly:
     - `[link 1]` the real return value (or exception) of `AddScriptToExecuteOnDocumentCreatedAsync(EpicChatAssociationWatcherScript)` — confirms the watcher script actually got installed (risk point #1).

# Build Plan — Git #4552

**Posted:** 2026-09-17T23:59:10Z

## Problem Description

`evaluateCaPolicyImpact` (`artifacts/api-server/src/lib/ca-policy-promotion.ts`) computes
a Conditional Access report-only policy's "would block / would interrupt" impact by
reading only `GET /auditLogs/signIns` on Graph **v1.0**. That endpoint lists **interactive
user sign-ins only**. Non-interactive user sign-ins (token refreshes, background client
sign-ins — where legacy-auth and device-condition blocks actually concentrate) and
workload identity sign-ins (service principal / managed identity — relevant to any policy
scoped to service principals) are separate Graph event types, readable only via the
**beta** `/auditLogs/signIns` endpoint with
`$filter=signInEventTypes/any(t: t eq 'nonInteractiveUser' | 'servicePrincipal' | 'managedIdentity')`.

The impact response is honest about this gap today (`coverageNote`), and the operator UI
(`artifacts/msp-console/src/console/modules/LaunchControl.tsx`) surfaces that note
verbatim — but a policy can show 0 blocked interactive sign-ins and still break real
non-interactive or workload traffic the instant it is promoted to enforced.

## Root Cause Analysis

- `graphFetchForTenant` (`artifacts/api-server/src/lib/graph.ts:815`) already supports
  absolute `https://graph.microsoft.com/beta/...` URLs verbatim (Git #1796) — the
  transport is not the blocker.
- `evaluateCaPolicyImpact` only ever issues one paginated read, against the relative
  v1.0 path `/auditLogs/signIns?...`, which Microsoft Graph resolves to interactive user
  sign-ins only (undocumented on v1.0, documented behavior of the beta
  `signInEventTypes` filter's absence).
- `summarizeReportOnlyImpact` / `AffectedUser` (`ca-policy-impact.ts`) assume every row
  carries `userId`/`userPrincipalName` — true for interactive and non-interactive user
  sign-ins, but service principal / managed identity sign-in rows carry
  `servicePrincipalId` / `servicePrincipalName` instead, with no `userId`.

## Proposed Changes

1. `artifacts/api-server/src/lib/ca-policy-impact.ts`
   - Add `SignInCategory = "interactiveUser" | "nonInteractiveUser" | "servicePrincipal" | "managedIdentity"`.
   - Extend `GraphSignInForImpact` with an optional `category` (caller-tagged; absent ==
     `interactiveUser`, preserving today's v1.0-only test fixtures unchanged) and optional
     `servicePrincipalId` / `servicePrincipalName`.
   - `summarizeReportOnlyImpact` keys affected identities by `userId ?? servicePrincipalId`
     and falls back to `userDisplayName ?? servicePrincipalName` for display, so a workload
     identity's blocked/interrupted sign-ins are tallied without a `userId`.
   - Add a `byCategory: Record<SignInCategory, CategoryImpactCounts>` breakdown to
     `ReportOnlyImpactSummary`, and a `category` field on each `ImpactEvent` — additive
     fields only, existing `toMatchObject`/`.map()` assertions in
     `ca-policy-impact.test.ts` are unaffected.
   - Aggregate `wouldBlock` / `wouldInterrupt` / `affectedUsers` / `evaluated` (consumed by
     `impactFingerprint` and `promotionReadiness`, and rendered directly by
     `LaunchControl.tsx`) now sum across all four categories — the real fix the issue asks
     for, with no caller changes needed downstream.

   Reference (pre-change): https://github.com/shanemccaw/Shane-McCaw-MSP/blob/2319db4a8b499b2cdcd3df0ab8908d108920e131/artifacts/api-server/src/lib/ca-policy-impact.ts

2. `artifacts/api-server/src/lib/ca-policy-promotion.ts`
   - `evaluateCaPolicyImpact` reads sign-ins for all four categories: the existing
     v1.0 interactive read (`/auditLogs/signIns?$filter=createdDateTime ge {from}`,
     unchanged), plus three new beta reads on absolute
     `https://graph.microsoft.com/beta/auditLogs/signIns?$filter=createdDateTime ge {from} and signInEventTypes/any(t:t eq '{type}')`
     for `nonInteractiveUser`, `servicePrincipal`, `managedIdentity`.
   - Each category gets its own bounded page loop (own `pagesRead` counter, same
     `MAX_SIGN_IN_PAGES` cap) — a workload-identity page storm cannot silently starve the
     interactive read's page budget or vice versa.
   - `complete` becomes true only when every category's read completed; `pagesRead`
     sums all four; a new `readByCategory` field on `CaPolicyImpact` reports each
     category's own `pagesRead`/`complete` for operator-visible transparency.
   - A `graph_error`/`consent_revoked`/`entra_premium_required` on ANY category still
     fails the whole evaluation (existing all-or-nothing failure shape) — an operator
     never sees a partial count presented as complete.
   - `COVERAGE_NOTE` updated to state all four event types are now included.

   Reference (pre-change): https://github.com/shanemccaw/Shane-McCaw-MSP/blob/2319db4a8b499b2cdcd3df0ab8908d108920e131/artifacts/api-server/src/lib/ca-policy-promotion.ts

3. `artifacts/msp-console/src/api/ca-promotion-api.ts` — widen the `CaPolicyImpact`
   frontend type to match the new additive fields (`byCategory`, `readByCategory`,
   `category` on `ImpactEvent`) so the client type doesn't silently drift from the real
   wire shape. No UI rendering changes required for this issue — `LaunchControl.tsx`
   already renders `summary.wouldBlock` / `wouldInterrupt` / `affectedUserCount` directly,
   so once the backend aggregates real counts across all four sign-in categories, the
   existing UI reflects the real, undercounted-no-longer impact with zero further changes.

### What the investigation actually found (it changed the build)
The issue's own architecture note is correct and was confirmed directly, not assumed.
ShanesSurvival's WPF app already owns the real initial Plaid Link (`PlaidLinkService.cs`) and the
real cursor-based `/transactions/sync` (`PlaidSyncService.cs`, cursor in
`plaid_items.sync_cursor`, migration 002) into the same real `finances` database Shane's Life
reads. **So Shane's Life did NOT get its own Link/OAuth flow for normal syncing** — nothing built
here fetches a transaction or a balance, and `bin/check.mjs` now asserts that opening the Banks
room moves neither `sync_cursor` nor `last_synced_at`. The audit's §3 comparison table
("Webhooks: None / None") is accurate: neither app had one.

### The real open question in the issue — decided
**Reconnect/update-mode UI lives in Shane's Life (web), not ShanesSurvival.** Reasons, in order of
weight: (1) the webhook that discovers a break has to land on an always-on hosted URL, and putting
the alert here with the fix on the desktop splits one action across two apps; (2) this is reachable
from a phone, the WPF app needs Shane at his PC; (3) Plaid Link in a plain browser needs none of the
WebView2 `"null"`-origin `postMessage` workaround the WPF host required (audit §3); (4) update
mode does not rotate the access token, so ShanesSurvival's stored cursor keeps working untouched.
ShanesSurvival's initial-link flow is unchanged — nothing in `desktop/` was touched.

### What shipped
- `web/shanes-life/migrations/041_plaid_item_health.sql` — **run by this session against the real
  local `finances` database** (ledger row `041_plaid_item_health.sql`, applied 22:36:26). Adds
  `plaid_items` health columns (`health_status` + CHECK, `health_code/message/changed_at`,
  `consent_expires_at`, `webhook_url`, `webhook_registered_at`, `last_webhook_at`,
  `transactions_pending_since`, `reconnected_at`) and the `plaid_webhook_events` table. Every
  column nullable or defaulted, so the WPF app keeps working against `plaid_items` unchanged.
- `src/core/plaid.mjs` — real Plaid REST calls (raw fetch, zero new dependencies, matching
  `PlaidClient.cs`'s proven body-credentials shape), ES256 `Plaid-Verification` verification,
  and the item-health store.
- `src/routes/plaid-webhook.mjs` + `POST /api/plaid/webhook` wired in `server.mjs` above both
  routers (authenticated by Plaid's signature, never the session cookie). `alg` is pinned rather
  than read from the token; body SHA-256 and Plaid's 5-minute replay window both checked. A rejected
  delivery is a 403 **and** a recorded row with `verified = false`.
- Update-mode reconnect: `POST /api/money/banks/:id/reconnect-token` (`access_token` instead of
  `products`) and `.../reconnect-complete`, which re-reads `/item/get` rather than trusting
  Link's `onSuccess` — a reconnect that did not take stays broken on screen.
- `GET /api/money/banks`, `/banks/events`, `POST /banks/refresh`, `/banks/register-webhooks`.
- Money → **Banks** tab in `public/app.js`, Plaid Link loaded on demand (no third-party script tag
  on every page load), plus the OAuth return leg at `/plaid-oauth`.
- 6-hourly `runPlaidItemMaintenance()`: registers the webhook on items the WPF app linked without
  one, and polls `/item/get` so a break is still caught when webhooks cannot deliver. Nudges only
  on a real transition **into** a reconnectable state — Plaid re-sends `ITEM: ERROR` on every
  failed call.
- Docs: a real README section, and `.env.example` entries for `SL_PLAID_*`. **No credential
  values were read, copied or committed** — the WPF app's settings file was deliberately not opened.

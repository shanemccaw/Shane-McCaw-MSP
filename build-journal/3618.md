- 2026-09-11T02:44:07Z ⏳ IN FLIGHT — Investigation done. The crash is a genuine
  cross-thread UI access, but the root is NOT the #3564 gallery/live-count render path
  (that path correctly uses `.ConfigureAwait(true)` in `FixedRibbonRenderer`, so its
  continuations marshal back to the UI thread — verified safe). The real root is the
  tenant-load event path in `Services/TenantService.cs`:
  `LoadTenantsAsync` awaits its HTTP calls with `.ConfigureAwait(false)` (the service-layer
  convention), so its continuation — where it commits `_tenants`/`CurrentTenant` and raises
  `CurrentTenantChanged` / `TenantsChanged` (lines 130-150) — runs on a **threadpool thread**.
  Most UI subscribers touch WPF elements directly with no `Dispatcher` marshaling:
  `TenantSwitcher.UpdateCurrentTenantView`/`RefreshList` (TextBlock/ItemsSource),
  `MainWindow.OnCurrentTenantChanged` (`LeftReferencePanelControl.SetTenantName`, tab open),
  `TelemetryConsoleView`/`SowAssessmentView` async lambdas. Only `VaultPanelView` and
  `ConsolePanelView` were already wrapped in `Dispatcher.Invoke` — a partial, incomplete
  patch of exactly this hazard, which is what confirms it. This predates #3564 (introduced
  by #3540's real TenantService), so the issue's #3564 attribution is a reasonable but
  incorrect hypothesis; reporting honestly. Planned fix: marshal the state-commit + event
  raise in `LoadTenantsAsync` back onto the captured UI `SynchronizationContext` (single
  source-level fix that covers every present and future subscriber), keeping
  `ConfigureAwait(false)` for the actual network I/O. Verify with a constructed WPF
  dispatcher repro that reproduces the cross-thread throw before the fix and confirms it
  is gone after.

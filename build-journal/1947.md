### THE OPEN QUESTION #1947 ASKED — answered from the schema, not guessed

**Does #1556's `origin: policy | lifecycle | remediation | manual` generalize across record types?**

**No. The axis generalizes; the enum does not. Each record class needs its own provenance
column following #1556's pattern, and the platform normalizes them in one place.**

The evidence is already in the database — five record classes, five vocabularies, three
column names:

| Record class | Column | Real vocabulary |
|---|---|---|
| `msp_sop_runs` (#1556) | `origin` | `policy \| lifecycle \| remediation \| manual` |
| `config_resources` | `origin` | `graph-metadata \| m365dsc \| both` |
| `msp_diagnostic_findings` | `finding_source` | `baseline \| policy` |
| `msp_change_requests` | `source_kind` | `microsoft_change` |
| `m365_roadmap_items` | `source_kind` | `roadmap \| message_center \| manual` |
| `msp_risk_decisions` | — (FK edges) | `spawned_by_change_request_id`, `spawned_by_remediation_step_id` |

Three things settle it:

1. **`config_resources.origin` already uses the identical column name for a different
   axis** — which discovery transport produced the row, not what created the record.
   Declaring #1556's four values "the platform provenance enum" would put two unrelated
   vocabularies behind one name: the duplicate-authority problem #1759 had to undo.
2. **#1556's values are meaningless for most classes.** A status report is not
   `lifecycle`-origin. Writing one would be a value that maps onto nothing — the exact
   fabrication this project forbids. Note `policy` appears in three of the vocabularies
   above meaning three different things, which is what a forced merge would have hidden.
3. **`msp_risk_decisions` has no provenance column at all** — provenance is a pair of
   nullable FKs, which no shared enum could have been truthfully backfilled from.

What the gate actually needs is **one binary**: did a human create this by hand? #1944
part 1 never asks "remediation or lifecycle", only whether a bypass checkbox should
render. Every vocabulary above can answer that about itself without agreeing with the
others. So `origin-registry.ts` is a registry of per-class resolvers producing that
binary, and `record_deletions.record_origin` stores each class's raw value **verbatim**
so the account of a deletion says what that record's own table said.

### What shipped

**Schema — `lib/db/src/schema/retention.ts`**, migration
`lib/db/migrations/manual/2026-09-04-retention-foundation-1947.sql`, **run by me against
the local `DATABASE_URL`** (2 CREATE TABLE, 6 CREATE INDEX, self-marked in
`simulator_migration_runs`). Additive only; no existing table touched; nothing backfilled
(#1944 question E).

- `retention_policies` — per-customer. **Every duration column nullable**, so null means
  "platform default" and a surface can report a value AS the default without a second
  flag column. Defaults are declared constants (90 / 30 / 7 years), never literals.
- `record_deletions` — one lifecycle row per deletion across all record types. Central
  because three of #1944's requirements are cross-type by construction: the sweep's
  single indexed scan, the #1571 operator queue and countable ghost backlog, and part 2's
  requirement that the account of a deletion **survive the purge of the record it
  describes** (a column on the record cannot outlive the record). Hence `tenant_id
  ON DELETE RESTRICT`, not CASCADE.
- `softDeleteColumns()` — the `deleted_at` / `deleted_by` / `delete_reason` triple defined
  **once** for consuming modules to spread. It is the cheap read-path marker so a module's
  list query can say `deleted_at IS NULL` without a join; the ledger is the authoritative
  state, and one helper writes both in one transaction so they cannot drift.

**The clock — `artifacts/api-server/src/lib/retention/clock.ts`.** Stored as
`(stageEnteredAt, stageRemainingSeconds)`, never as `deleted_at + 90d`. `stage_due_at` is
a maintained convenience for the sweep index and is **NULL while frozen**, so the sweep's
partial index physically does not contain a frozen row — the freeze is enforced by index
shape, not only by a WHERE clause. Stage advance starts at the real boundary instant, not
at `now`, so a late sweep cannot hand a record extra tier-2 life.

**Two independent gates, both must pass** (#1944 is explicit): `reference-guard.ts` refuses
a delete and names *every* blocker (the chain, not the first); `origin-registry.ts` decides
only whether the bypass is *offered*. A soft-deleted dependant still blocks — the two-click
defeat is written out as its own test. An edge that throws is treated as blocking.

**Also:** `registry.ts` (a module registers four small functions and gets the whole
lifecycle), `policy.ts`, `lifecycle.ts` (softDelete / restore / requestAcceleration /
decideAcceleration / purgeNow / freeze / resume / reconcile / advanceDueDeletions /
ghostStateOf). `clock.ts`, `reference-guard.ts`, `origin-registry.ts` and `registry.ts`
import neither the database nor the platform logger (whose sink writes to
`platform_log_stream`), so the mechanism's core is testable as pure functions.

**All three registries ship EMPTY** — per-module wiring is each consuming module's own
issue. Deliberately absent: no lock-down flag (part 8 reversed part 7), no audit table
(#1946 owns it; this consumes `createAuditLog`), no notification firing (#1942's rules
consume the transitions `advanceDueDeletions()` returns, so there is one scheduler not
two), no permission check (#1704's `can()`).

### Findings filed (both parented under #1944, `bug`, milestone v1.1, board "AI Batter Up")

- **#2847** — No per-customer subscription state exists. Part 8 justified the routing gate
  by "reusing a fact the platform already tracks for billing"; per customer that fact is
  not there. `msp_subscriptions` is MSP-scoped (`msp_id` unique, one row per MSP), so the
  only per-customer signal is `tenants.status`, an operational enum that nothing writes
  `inactive` to on non-payment. Consequence: the gate would never fire and a lapsed
  customer's clocks would keep running through a window part 7 says must be frozen — a
  data-loss direction. Isolated to one constant (`RETENTION_CLOCK_RUNNING_TENANT_STATUSES`)
  so there is exactly one place to change.

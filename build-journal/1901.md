  **Scope was larger than the issue body said, and the body was not wrong — it was stale.**
  #1901 lists 13 endpoints, "verified live 2026-08-30 by running the real derivation over every
  `config_pack_templates` row." Re-running that exact derivation on 2026-09-04 returned **19
  unmapped steps across 16 distinct endpoints**: `governance-groups-v1` had been wired in the
  intervening days, adding `POST /groups/*/owners/$ref`, `PATCH /groups/*` and
  `POST /groupLifecyclePolicies`. Covered all 16 rather than the listed 13 — the issue's intent
  is "cover the uncovered endpoints", and leaving three behind would have left a whole pack
  permanently reading "Write permissions not verified", the precise harm the issue describes.

  **Every rule was read off the real Microsoft Learn page for that exact method + path**, with
  the Application row quoted verbatim into `documentedApplicationTiers`. No permission was
  inferred from a sibling endpoint or from memory.

  **Derived request set: 17 → 23.** The six added are `LicenseAssignment.ReadWrite.All`,
  `DeviceManagementConfiguration.ReadWrite.All`, `DeviceManagementApps.ReadWrite.All`,
  `DeviceManagementManagedDevices.ReadWrite.All`, `User.DeleteRestore.All`,
  `SecurityIncident.ReadWrite.All`. **The PIM endpoints added nothing**, contrary to the issue
  body's prediction that PIM and Intune assignment operations in particular would enlarge the
  set: both PIM schedule-request pages list `RoleManagement.ReadWrite.Directory` as a documented
  higher-privileged alternative, and quickstart-v1 step 2 already holds it. A test now pins the
  added-six list, since the issue itself flagged consent-screen growth as the real cost.

  **Three states, not two.** Added `appOnlyUnsupported` to the rule type for
  `PATCH /roleManagement/directory/roleAssignmentApprovals/*/steps/*`, whose Application row
  reads `Not supported.` in all three of that page's permission tables. Modelling it as an
  ordinary rule with `permissions: []` would have made `required` and `missing` both empty and
  rendered the executable **READY** — the exact false-green the table exists to prevent.
  `GET /api/admin/write-permissions` now returns `appOnlyUnsupportedSteps` as its own category,
  distinct from `unmappedSteps` (unknown) and `missing` (grantable). Filed as #2854.

  **Three steps documented-but-refused**, not requested: governance-groups-v1's owner and
  visibility steps need tenant-wide `Group.ReadWrite.All`, and its expiration policy needs
  `Directory.ReadWrite.All` with no alternative at any tier. Both are on the standing
  never-request list. Reported as refused, not as a missing consent. Filed as #2856.

  **Two rules document a broken stored template while their permission is still right:**
  `action.delete-ca-policy` stores `PUT` on a resource Graph exposes no PUT for, and
  `action.assign-app-protection-policy` targets `managedAppPolicies`, an abstract base type with
  no `assign` action. The permission is identical whichever way each is fixed, so the derived
  set is correct regardless, and the packs stop reporting unmapped steps meanwhile. Both carry
  an uppercase warning in their justification and **a test asserts those warnings are still
  present**, so the finding cannot be quietly deleted by a later reader who checks the endpoint
  against Learn and tidies up. Filed as #2855.

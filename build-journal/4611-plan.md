# #4611 — Plan

## Problem Description

`QueueWatcherService.LaunchItemCore` launches `claude.exe --resume <session>` whenever
`item.ResumeSessionId` is set, with **no check that the session isn't already live under
another queue row**. Every UI-level guard added by #4547/#4553/#4554
(`WouldInterruptActiveWork`, `GetLiveQueueIdsForSession`, the Reply/Retry click-time
checks) runs at click time in the UI, not at the moment the process actually spawns. Two
real dispatcher paths can carry a `queued` row with `resume_session_id` still set past
those click-time checks and straight into an unguarded launch:

1. **A continuation queued at the hard cap** — `LaunchContinuationAsync` (queue-manual
   claim path) deliberately leaves the row `queued` with `resume_session_id` intact when
   every slot is full (see its own comment at
   `desktop/BuildConsole/Services/QueueWatcherService.cs:4164`). By the time a slot frees
   and the periodic pickup loop dispatches it, the session may be live again (adopted
   elsewhere, or resumed a second time by a different Reply).
2. **Session-limit auto-restart** — `SessionLimitAutoRestartService` calls
   `_db.ResumeLimitPausedAsync(account)`, which flips `limit-paused` rows back to
   `queued` in place with `resume_session_id` preserved, then the pickup loop launches
   it with no liveness check at all.

Live evidence cited in the issue: `activity-2026-09-15.log` shows queue #2947 and #2957
both live on the same session `c4180db4`.

## Root Cause Analysis

`LaunchItemCore` (`desktop/BuildConsole/Services/QueueWatcherService.cs:2747`) is the
single real launch call site — every caller (pickup loop, `ForceLaunch`,
`LaunchItemExplicit`, `LaunchContinuationAsync`'s own `SafeLaunch`) funnels through it.
Its `--resume` decision at
[`QueueWatcherService.cs:3002-3006`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L3002-L3006)
adds `--resume <item.ResumeSessionId>` unconditionally whenever the field is non-blank.
Nothing above it calls the existing liveness primitives
(`IsProcessAlive`/`GetLiveQueueIdsForSession`, both already defined at
[`QueueWatcherService.cs:3883-3909`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L3883-L3909))
for that session before adding the flag.

`LaunchContinuationAsync` itself (the explicit, user-triggered "Reply" path) already does
this correctly — it calls `LiveQueueIdsForSession` at
[`QueueWatcherService.cs:4103`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L4103),
refuses if more than one live copy exists, and stops-and-confirms-exit
(`StopForContinuationAsync`) before its own `SafeLaunch` call at
[`QueueWatcherService.cs:4204`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L4204).
So that legitimate path never trips a new backstop — it always finishes its own stop
before reaching `LaunchItemCore`. The two dispatcher paths above never go through
`LaunchContinuationAsync` at all — they reach `LaunchItemCore` directly from the pickup
loop's periodic tick with the row's `resume_session_id` already set on the DB row, so
there is no click-time UI guard sitting upstream of them either. `LaunchItemCore` is the
only point that actually knows a process is about to be spawned for this item, which is
exactly why the issue calls it out as the correct backstop location, not another
UI-side duplicate of the same check.

## User Review Required

None — this is a pure backstop/bugfix at an already-identified call site, following the
exact pattern (`MarkLaunchFailedAsync` refusal with a clear reason) every other pre-flight
guard in `LaunchItemCore` already uses (worktree provisioning failure, missing exe,
unusable secondary/primary account). No product decision involved.

## Proposed Changes

### `desktop/BuildConsole/Services/QueueWatcherService.cs`

Insert a liveness check immediately before the existing `--resume` branch at
[`QueueWatcherService.cs:3002-3006`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/859d2d157f6c632721f7110c4266c5a517cc03bc/desktop/BuildConsole/Services/QueueWatcherService.cs#L3002-L3006):

- When `item.ResumeSessionId` is non-blank, call the existing
  `LiveQueueIdsForSession(item.Id, item.ResumeSessionId)` (already used by
  `LaunchContinuationAsync`, no new primitive needed).
- If it returns any live queue id(s), refuse the launch: log a clear `ActivityLog`
  line naming the colliding queue id(s) and session, then call
  `MarkLaunchFailedAsync(item.Id, reason)` and `return` — the same fail-closed shape
  every other guard in this method already uses (worktree provisioning, exe-not-found,
  secondary/primary account checks a few lines above/below).
- Do **not** attempt an automatic stop-and-relaunch inline here. That sequencing
  (`StopForContinuationAsync` + reservation bookkeeping) is deliberately owned by
  `LaunchContinuationAsync` as an explicit user action; duplicating it inside the
  generic launch path used by every caller (pickup loop, `ForceLaunch`, limit-pause
  auto-restart) would risk killing a process out from under a caller that has no
  reservation/UI context to handle it safely. Refusing and surfacing the reason is the
  correct backstop — consistent with the issue's own "either stop... or refuse... —
  never launch the second process" guidance, and matching this method's existing style.
- Because this sits directly above the resume/fresh-session branch and reuses an
  already-defined helper, it is intentionally NOT a new UI-side check — it fires for
  every real caller of `LaunchItemCore`, closing the exact gap the issue describes.

   clean compile.

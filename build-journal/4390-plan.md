# #4390 — plan

## Problem (from issue body)

Cycle `c-1789574065319-10396` (`.logs/dev-server/cycles.log`) rebuilt the api-server
correctly and bound :8080 ~4s after the cycle's own live-check ran, but the cycle
reported `ready: false` / NOT LIVE (exit 3) anyway. `waitForFreshApiListener`
(`scripts/dev-server/refresh-main-server.mjs`) is supposed to wait up to
`apiRestartTimeoutMs` (240s), yet the whole cycle finished in 36s with `ready: false`.

## Trace

- `refreshMainServer` (refresh-main-server.mjs) calls `restartMainApiServer`, which
  awaits `waitForFreshApiListener` — a weak "some pid other than the old ones is now
  on :8080" poll — then immediately calls `verifyServingCheckout` (serving-checkout.mjs)
  exactly ONCE for the authoritative live-check.
- Real cycle record: `portReady: true` (waitForFreshApiListener found a fresh pid) but
  `ready: false` because that one immediate `verifyServingCheckout` call found nothing
  listening on :8080 (`live.api.listening: false`). The real server (per
  `.logs/dev-all/dev-all.log`) didn't finish seeding/binding until ~4-9s later.
- Root cause: a single point-in-time snapshot, taken right after a weak early signal,
  can land in the gap between "something briefly touched the port" and "the rebuilt
  api-server is actually, stably listening." There was no retry — one bad snapshot
  meant a permanent NOT LIVE for a restart that had already succeeded.

## Fix

- Add `verifyServingCheckoutUntil` (serving-checkout.mjs): retries the same real
  `verifyServingCheckout` check on a short interval until it verifies or a deadline
  passes — but ONLY while the failure looks like "still starting" (nothing listening
  yet / listener predates the rebuild / can't yet attribute). Any structural failure
  (commit genuinely missing, port held by a different checkout) returns on the first
  attempt — retrying that would just delay an honest failure.
- `refreshMainServer` now calls `verifyServingCheckoutUntil` with a deadline of
  `api.spawnedAt + apiRestartTimeoutMs` when an api restart happened, instead of one
  bare `verifyServingCheckout` call. Non-restart paths (front-end-only changes) are
  unchanged (deadline `Date.now()` = single check, same as before).

## Verification

- Reproduced the exact race in `serving-checkout.selftest.mjs` with an injected probe
  whose `readListeners` returns "nothing listening" on the first call and the real
  fresh listener on the second — proving a single `verifyServingCheckout` call reports
  NOT LIVE (matching the real cycle) while `verifyServingCheckoutUntil` recovers.
- Added a structural-failure case (port held by a different checkout) proving it does
  NOT retry away the deadline.
- Added a no-restart case (no `apiSpawnedAt`) proving it stays a one-shot check.
- Ran `node scripts/dev-server/serving-checkout.selftest.mjs` — all assertions pass.

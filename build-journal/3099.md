## What shipped

50 btree indexes covering every foreign-key column referencing `users(id)` that had none —
declared in `lib/db/src/schema/{index,msp,rbac}.ts` and in
`lib/db/migrations/manual/2026-09-09-index-users-fk-columns-3099.sql`, run against the local
`DATABASE_URL` in-session.

The issue said 53 unindexed FK columns as of 2026-09-07; the live count on 2026-09-09 was **55
per-constraint / 51 distinct (table, column) pairs across 45 tables**. 50 are indexed. The 51st,
`script_download_tokens.client_user_id`, is deliberately skipped: #3079's destructive DROP is
already written and waiting on Shane, it no longer exists in the Drizzle schema, and it has never
held a non-NULL value.

The migration uses `CREATE INDEX CONCURRENTLY` — so it carries **no `BEGIN`/`COMMIT` and must be
run with `psql -f`, not the SQL Runner**. Reasoning is in its header, along with a `DO` block that
drops `INVALID` leftovers from an interrupted run so a retry actually rebuilds them.

Also removed the 60s `hookTimeout` override #2999 added to
`artifacts/api-server/src/lib/retention/reinstatement-ticket.live-db.test.ts` as a workaround for
this exact problem. It passes under the ordinary 20s global timeout now.

## Verification (all real, local PostgreSQL 18.6 `shanemccawmsp`)

- Migration ran clean: 50 `CREATE INDEX`, 1.19s total, 0 `INVALID` indexes afterwards.
- Unindexed FK columns referencing `users`: **55 → 1** (only the deliberately-skipped one).
- Controlled same-session A/B (`enable_indexscan`/`bitmapscan`/`indexonlyscan` on vs off), warm
  backend, two passes each way — a naive before/after wall-clock is noise-dominated here, so this
  is the honest measurement:
  - `DELETE` of 100 users in one statement: **480 / 507 / 617 / 598 ms off → 331 / 268 / 278 / 346 ms on** (~1.8x)
  - `DELETE` of a single user: 12.6–15.7 ms either way — **no reliable change**, because 45 of the 46
    referencing tables hold one or two pages, so the ~77 RI trigger invocations are the whole cost
    at this data volume.
- The structural result, per RI check, on the largest table in the set (`emails`, 2,308 rows / 1,752 kB):
  `SELECT 1 FROM emails WHERE linked_user_id = 99999 FOR KEY SHARE` →
  **Seq Scan, 146 buffers, 2.842 ms** without the index vs **Index Scan, 2 buffers, 0.201 ms** with it.
  73x fewer buffers, 14x faster; the seq-scan side grows with the table, the index side does not.
- `npx tsc --noEmit` clean for both `lib/db` and `artifacts/api-server`.
- `pnpm --filter @workspace/db run test` — 56/56 pass.
- `vitest run src/lib/retention/` — **103/104 pass**. The one failure,
  `tenant-scope-coverage.live-db.test.ts`, was **already red before this build** and is unrelated
  (two `tenant_id` columns from #2455's RBAC foundation, commit `884515a1e`, claimed by no purger).
  Filed as #3363, not patched.
- `pnpm --filter @workspace/scripts run check-drift` — ✅ no drift.

## Findings filed

- **#3361** — seven `users(id)` foreign keys are declared twice (both a Postgres `_fkey` and a
  drizzle `_users_id_fk` constraint, identical ON DELETE actions), so 7 of the 77 AFTER DELETE RI
  triggers on `users` are pure duplicates. Sub-issue of #1944, `bug`, board = AI Batter Up.

## Honest gaps

- The migration has been applied to **local dev only**. Staging/Replit is a release-time action
  and is what the #1630 line records.
- `emails.linked_user_id` is `1` for 2,255 of 2,308 rows locally, and for that one value the
  planner correctly keeps the seq scan. An index cannot help a lookup returning 98% of a table;
  it helps every other user id.

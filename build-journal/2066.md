## Log
- 2026-08-31 ⏳ IN FLIGHT — real audit done first, per the issue's own "real audit
  required" section:
  - `desktop/BuildConsole/Services/IssueMentionInjector.cs` (Git #1253) already parses
    every `#NNN` in a chat's DOM via `ISSUE_RE` inside `decorateTextNode`/`runScan`, but
    today only ever posts a message on hover (`BT_HOVER_ISSUE`) or click
    (`BT_OPEN_ISSUE`) — there is no existing "report everything currently detected"
    message. Reusing it means adding a batch report at the end of `runScan()`, not a
    second parser.
  - `bt_chat_issues` (many-to-many, Git #1362/#828) already exists but is a
    *deliberate/authoritative* association table — populated only by explicit
    Link/Unlink calls (`ChatMappingsDocumentView`, `LinkChatToIssueAsync`,
    `AssignChatToEpicDialog`) and read to resolve `epic_id` fallback and the "linked
    issue" pills in the Chats tree. Per the issue's own instruction not to conflate
    with #2013, and by the same logic not with this deliberate table either — stuffing
    noisy incidental mentions into it would corrupt epic-resolution and the "linked"
    UI semantics. Building a NEW table for the noisy signal instead.
  - Real close-detection mechanism already in the app: `LeftSidebar.PopulateGitTrackerBoardAsync`
    polls every ~20s and fires `GitBoardOpenIssuesRefreshed(HashSet<int> openNumbers)`
    with the full current open-issue set (repo-wide, up to 10k issues); `BuildWatchWindow`
    and `BuildQueuePanel` already subscribe to it to evict closed-issue state. Reusing
    the same event for auto-pruning the new mention table instead of inventing a new
    poll.
  - `BoardChat.ClaudeUrl => https://claude.ai/chat/{ConversationId}` is the existing
    canonical chat-URL format; keying the new table on that (not requiring a `bt_chats`
    row to already exist) matches "associate them with that chat's URL" and avoids
    needing to create phantom `bt_chats` rows for chats never explicitly linked to an
    issue.

# #3020 — selftest.mjs concurrency scenarios (3/9) intermittently flake on real cross-process git races

- **Status:** ✅ DONE 2026-09-13T03:16:00Z
- **Scope:** buildconsole (scripts/dev-server)
- **Started:** 2026-09-12
- **Commit(s):** 27411fd84 (rebased/pushed to main as a986d4b78)

## Log
- 2026-09-12T00:00:00Z ⏳ IN FLIGHT — investigating lock.mjs / selftest.mjs Scenario 3 & 9 races (index.lock collisions, update_ref HEAD races) despite lock.mjs mutex.
- 2026-09-13T03:16:00Z ✅ DONE — Root cause found: `lock.mjs`'s atomic `mkdirSync(lockDir)` win and its `owner.json` write are two separate syscalls. Between them, `lockDir` exists but `owner.json` doesn't yet. A second process's `tryAcquire` landing in that window read `owner === null`, and `isStale(null, ...)` unconditionally returned `true` — treating the winner's brand-new lock as orphaned, breaking it (`rmSync`), and recreating it as its own. Both processes then believed they held the mutex and ran concurrent `git merge`/`commit` against the shared server worktree, producing exactly the `index.lock` / `update_ref` collisions selftest.mjs Scenarios 3 and 9 hit intermittently. All merge/commit call sites (`coordinator.mjs` runCycle/runSetMemberCycle, both only invoked after `tryAcquire` succeeds) were already correctly serialized — the gap was in lock acquisition itself, not a bypass of it. Fix: `isStale()` now uses the lock DIRECTORY's own age (`statSync(lockDir).birthtimeMs`, falling back to `mtimeMs`) to tell a genuinely orphaned lock (crashed holder, dir old) from a live one still mid-write (dir very young) — a missing `owner.json` is only "stale" once the dir is older than `NEW_LOCK_GRACE_MS` (2000ms), comfortably above the real gap and well under `staleLockMs` (90s default). Verified with 15 consecutive full `selftest.mjs` runs post-fix — 53 passed / 0 failed every single time (5-run batch + 10-run batch), vs. the issue's reported ~1-in-3 flake rate pre-fix. Committed as `27411fd84`, rebased onto `origin/main` and pushed as `a986d4b78`. `verify-branch-merged.mjs` confirms ancestry. No new findings filed — this was a single, real gap in `lock.mjs` itself, not a missing serialization call site elsewhere.

# #4602 — Plan: sharepoint:inactive-sites countIfLastSignInOlderThan mismatch

## Problem Description

Live-verifying #4538's `$select` fix against testbed tenant 2080 showed
`sharepoint:inactive-sites` reporting `inactiveSiteCount: 143` against
`itemCount: 143` — every single SharePoint site counted as inactive, including
one whose real `lastModifiedDateTime` was one day old at scan time.

## Root Cause Analysis

`countIfLastSignInOlderThan` (added by #4524's migration as the mapping
transform for this check) is hardcoded to test
`signInActivity.lastSignInDateTime`, not the mapping rule's own `sourceField`:

https://github.com/shanemccaw/Shane-McCaw-MSP/blob/a21895db4c1c9c40de10c1d95a4b0f9fbd10d1cc/artifacts/api-server/src/lib/monitor-executor.ts#L1625-L1651

`sharepoint:inactive-sites`'s mapping rule is
`{"sourceField":"lastModifiedDateTime","transform":"countIfLastSignInOlderThan(90)",...}`.
Sites carry no `signInActivity` property at all, so:
- the `sourceField` ("lastModifiedDateTime") gate at line 1637-1638 passes for
  every real item (it's present on all 143 sites);
- `lastSignIn = resolvePathInData("signInActivity.lastSignInDateTime", item)`
  is `null` for every item (sites don't have this field);
- line 1641's `if (lastSignIn == null) { ev.add(...); continue; }` — the
  "never signed in counts as stale" convention, correct for users — counts
  every single site as stale.

`countIfLastSignInOlderThan` is correctly used elsewhere by
`identity:stale-accounts` and `governance:guest-staleness`, both of which
really do read `signInActivity` (see #4524's migration). This transform must
not change for them.

`severity_rules` on this check's row is also `[]` (confirmed via
`node scripts/db/psql.mjs`). Per the dispatch instructions this is left alone
unless trivially confirmed to already be tracked — a quick `gh issue search`
found no open issue naming `sharepoint:inactive-sites` `severity_rules`
specifically, so it is left as a known, un-filed gap rather than expanding
scope here.

## User Review Required

None — this is a mapping/transform-semantics bug fix with an additive,
non-destructive migration. No product decision, no money/entitlement impact.

## Proposed Changes

1. **New transform `countIfFieldOlderThan(N)`** in
   `artifacts/api-server/src/lib/monitor-executor.ts`, a sibling of
   `countIfLastSignInOlderThan` that compares the mapping rule's own
   `sourceField`-resolved value (already computed into `vals`) against the
   `N`-day cutoff, instead of a hardcoded `signInActivity` path. Unlike the
   sign-in transform's "never signed in counts as stale" convention, a missing
   value here is NOT counted as stale (under-report + warn, matching
   `countEmptyArray`'s established philosophy) — this is exactly the bug
   being fixed: an endpoint or item missing the field must not read as 100%
   stale.
   - Regex: `/^countIfFieldOlderThan\(\s*(\d+)\s*\)$/`
   - `countIfLastSignInOlderThan`'s own case block is untouched.

2. **Migration** `lib/db/migrations/manual/2026-09-18-sharepoint-inactive-sites-field-transform-4602.sql`
   — repoints `sharepoint:inactive-sites`'s mapping `transform` from
   `countIfLastSignInOlderThan(90)` to `countIfFieldOlderThan(90)` (same
   `sourceField`, `targetField`, `requireField`, `select_params`
   unchanged), bumps `schema_version`, self-marks in
   `simulator_migration_runs`. Additive/idempotent — run directly against
   local `DATABASE_URL` in this session.

3. Doc-comment updates (transform name lists only, no logic change) in
   `artifacts/api-server/src/lib/monitor-check-trace.ts` and
   `artifacts/admin-panel/src/adminv2/screens/endpoints/EndpointsBody.tsx`.

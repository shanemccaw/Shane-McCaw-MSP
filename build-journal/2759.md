## What shipped

**Store** — `lib/db/src/schema/config-attribution.ts` +
`lib/db/migrations/manual/2026-09-04-config-change-attribution-2759.sql` (run against local
Postgres; recorded on #1630). Four tables:

| table | what it holds |
|---|---|
| `config_change_scopes` | the CR / risk-decision → configuration bridge, every row stating the BASIS it was derived from |
| `config_change_lifecycle` | open / resolved / reopened per drifted setting, keyed on the RAW property path |
| `config_change_attributions` | one verdict per `config_diff_changes` row, always — including the ones that attribute to nothing |
| `config_change_attribution_matches` | every scope that matched, not just the winner, so a contested row is auditable |

Attribution is a SIBLING table, not columns on `config_diff_changes`: that table is sealed by
`config_diff_reject_mutation_on_sealed()` and must stay that way, but a verdict legitimately moves
as change requests and risk acceptances move.

**Engine** — `artifacts/api-server/src/lib/config-change-attribution.ts`. Resolves a change request
down to the real Graph endpoint it wrote (`cr_executions.actual_outcome`, or `change_catalog_items`
→ `config_packs` → `config_pack_templates` → `baseline_action_templates.endpoint`) and matches that
against the real resource registry (`config_snapshot_resource_types.graph_version` + `graph_path`).
Five verdicts: `attributed_change` · `accepted_risk` · `contested` · `unattributed` · `ignored`.
Nothing falls back to the category-wide blanket the existing drift path uses — a change request with
no derivable endpoint attributes NOTHING.

**Wire contract** — every change row on `GET /api/portal/config-state/changes/:diffId` and
`GET /api/msp/config-state/diffs/:diffId` now carries `attribution` and `lifecycle`; both surfaces
also carry a diff-level verdict roll-up. New `POST /api/msp/config-state/diffs/:diffId/attribution`
runs/re-runs the pass. Reads Change Control and the Risk Register; writes only its own tables —
never a CR, a risk decision, or the sealed diff.

## Four real defects the live runs found, all fixed

1. **Inverted snapshot window.** `baseline_assessment` diffs legitimately compare against a
   reference captured LATER than the subject (testbed diff row 11: base 11 hours after head). The
   window was built base-first, so it inverted and matched nothing — every change silently
   `unattributed`. Now ordered by time.
2. **Lifecycle keyed on the NORMALISED property path.** Measured on testbed diff row 9: 340 change
   rows, 340 distinct `(resource_key, object_identity, property_path)` triples but only **72**
   normalised ones. 126 array members collapsed onto one row and overwrote each other inside a
   single pass — the first live run reported 83 resolutions and 19 reopenings on a diff where
   nothing had returned to anything. Now keyed on the raw path.
3. **Non-`drift` modes fed the lifecycle.** A lifecycle is a claim about one tenant over time; a
   baseline assessment or cross-tenant compare is not a time series. Verdicts are still computed for
   every mode; only the lifecycle is restricted to `drift`.
4. **`ON DELETE SET NULL` vs the verdict CHECK.** The cascade runs as an UPDATE that nulls the edge,
   the CHECK rejected it, and the whole DELETE aborted — a change request that had ever attributed a
   diff row could never be deleted again. The CHECK now accepts the FK **or** the preserved display
   ref (`cr_ref` / `rbd_ref`), so history survives a prune and stays falsifiable. Pinned by its own
   test.

Also: an ambiguous endpoint now resolves to NOTHING rather than the first registry row.
`exchange-online://Set-Mailbox` was resolving to `m365dsc:EXOCalendarProcessing` purely on row
order — a scope pointing at the wrong resource is worse than no scope.

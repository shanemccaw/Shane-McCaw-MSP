## Log
- 2026-09-09T00:00:00Z ⏳ IN FLIGHT — confirmed root cause in `web/shanes-life/public/app.js`:
  `medsDaypartRank()` is purely name-based (morning=0/midday=1/night=2/untimed=3) with no
  time-of-day awareness, and `viewMeds()`'s `current` selection
  (`ordered.find((b) => b.rank < 3 && !b.batchState.takenToday)`) picks the earliest untaken
  rank regardless of real clock time -- so Night-taken-at-12:37am makes Morning "current"
  immediately. Adding a real local-hour >= 6am eligibility gate on rank 0 (Morning) before it
  can become "current"; before 6am with Night taken, Morning falls back to the existing
  dimmed "later" treatment (no `current` found) rather than jumping ahead.
- 2026-09-09T00:20:00Z ✅ DONE — added `medsRankEligibleNow(rank, now)` next to
  `medsDaypartRank()` (rank 0 / Morning requires real local hour >= 6; ranks 1/2/3 unaffected),
  and gated the `current` batch `find()` in `viewMeds()` on it. When nothing untaken is eligible
  yet (e.g. Night taken at 12:37am, Morning not eligible until 6am), `current` is `undefined` and
  every untaken timed batch falls back to the existing dimmed "later" card state -- an honest
  "nothing due right now" rather than jumping ahead to Morning, using the mechanism that already
  existed for this case rather than inventing new UI. Verified via `node --check` (syntax) and a
  Node-side simulation of the extracted eligibility/selection logic against the real reported
  scenario: Night+Midday taken, Morning untaken -- at 12:37am `current` is `undefined` (no batch
  jumps ahead), at 6:01am `current` correctly becomes Morning; also checked the 5:59am/6:01am
  boundary directly. `web/shanes-life/` has no unit-test harness for `app.js` (browser-global

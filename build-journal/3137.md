  **What shipped**
  - `web/shanes-life/src/core/money.mjs` (~760 lines) — a literal port of
    `DashboardService.ComputeAsync`, reading ShanesSurvival's own real `accounts`, `debts`,
    `income_sources` and `expected_one_time_events` rows in the shared Postgres. Integer cents
    throughout, mirroring the C#'s use of `decimal`, so eleven summed bill shortfalls cannot
    drift on float error. The warn-and-exclude rule for a bill with no target or no Plaid
    balance is preserved exactly, and `total_available`/top line stay NULL (not 0) when there is
    no gate balance.
  - `whatIf()` (`top − habit − amount`, naming the largest-shortfall account when negative),
    `simulateTransfer()` (arithmetic on copies, borrowed-from-bill flag, `executed: false`
    structurally — nothing in the module can move money), `computeBudgetDay()` (from
    `income_sources.next_pay_date`, rolled forward whole `pay_frequency_days` cycles so the card
    cannot claim a payday that already happened).
  - Migration `027_money_habits.sql` + `setHabit()`/`listHabits()` — the habit model behind the
    design's "really" line. ShanesSurvival had nowhere to store it (`accounts` holds bill
    targets, `debts` what is owed, `smoke_log` what was actually smoked), so hardcoding the
    design's `$148` was the only alternative and is exactly the fixture-data failure this repo
    bans. **No habit row was seeded** — the table ships empty and the "really" line is `null`
    until Shane or Claude states a real amount, rather than a line reading "$0.00 a cycle".
  - Real routes: `GET /api/money/gate`, `GET /api/money/budget-day`, `GET /api/money/what-if`,
    `POST /api/money/simulate-transfer`, `GET|PATCH /api/money/habits`.
  - Real MCP tools: `get_gate_status`, `what_if`, `simulate_transfer` (the design README's own
    list), plus `set_habit` so the habit model is settable conversationally.

  **Real bug caught and fixed during verification.** Budget Day first rendered a real Sep 11
  payday as `2026-09-10` / "Thu, Sep 10". `isoDate()` was re-normalising an
  already-UTC-midnight Date through local getters, walking the date back a day west of
  Greenwich. Split into `asUtcDate()` (once, from a raw DB value) and `utcIso()` (never
  re-normalises); the check now asserts `storedNextPayDate` against the real column.

- 2026-09-04T16:11:02Z — ✅ DONE — Real root cause confirmed via live Log Analytics
  (`ContainerAppConsoleLogs_CL`, workspace `49aebe53-057e-44a5-a301-78b82bd3b472`),
  NOT OOM (the issue's own stated, unconfirmed guess — ruled out: no
  ContainerTerminated/eviction system-log event exists near either failure
  timestamp). Both `get-data-classification` (07:41:13Z) and
  `get-dlp-sensitive-info-types` (07:47:21Z) crashed with the IDENTICAL uncaught
  PowerShell terminating error at `child-worker.ps1:85`
  (`Send-ChildResult`'s own `ConvertTo-Json` call):
  `The type 'System.Collections.Hashtable' is not supported for serialization
  or deserialization of a dictionary. Keys must be strings.` PowerShell 7's
  ConvertTo-Json refuses any IDictionary with non-string keys; both cmdlets
  return objects carrying such a dictionary somewhere in their property graph.
  The failure WAS on stderr the whole time (the parent relays it onto the
  container's own log stream) — it just showed up as a raw multi-line
  ANSI-colored PowerShell trace, not a structured `{"message":...}` JSON line,
  so it read as "no stderr" to the grep the issue's own evidence used. 225
  objects was a correlation, not the cause.
  Fix: `services/ps-execution/child-worker.ps1` — added
  `ConvertTo-JsonSafeValue`, which recursively walks the whole result graph
  (dictionaries, collections, PSCustomObject/wrapped-.NET-object properties)
  and coerces every dictionary key to a string before `Send-ChildResult` ever
  calls `ConvertTo-Json`; wrapped `Send-ChildResult`'s own serialization in
  try/catch as defense-in-depth so any future unanticipated shape fails loud
  with a structured stderr log line instead of a silent-looking trace dump.
  Verified: reproduced the exact `ConvertTo-Json` error locally against a
  synthetic non-string-keyed Hashtable nested inside a PSCustomObject,
  confirmed the fix resolves it byte-for-byte, confirmed the file still
  parses cleanly (`Parser]::ParseFile`). Built + pushed

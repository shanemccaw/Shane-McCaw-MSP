# Plan: #4537 — `count` transform counts array-field PRESENCE not CONTENT

Posted: 2026-09-17T22:20:00Z

## Problem Description

`applyMapping`'s `"count"` transform in
[`artifacts/api-server/src/lib/monitor-executor.ts:1535`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e244549245eb8ffbeb818b2066a2050d1921dcd/artifacts/api-server/src/lib/monitor-executor.ts#L1535)
counts every value that is not `null`/`undefined`. Microsoft Graph returns array-typed
fields as `[]` (an empty array — present, not null) for an item with none of that
property, e.g. `assignedLicenses: []` for an unlicensed user. An empty array is
non-null, so `count` counts it — meaning for an array-typed `sourceField`, `count`
always equals `itemCount` regardless of the array's real length.

Confirmed live against testbed tenant 2080 (2026-09-17, per the issue body):
`cost:underutilized-premium` → `itemCount: 27`, `underutilizedPremiumLicenseCount: 27`
(should reflect only users whose `assignedLicenses` is non-empty).
`cost:group-based-licensing-adoption` → `itemCount: 104`,
`groupBasedLicensingGroupCount: 104` (should reflect only groups whose
`assignedLicenses` is non-empty). Both checks use
`{"transform": "count", "sourceField": "assignedLicenses", ...}`.

## Root Cause Analysis

`case "count"` (and no other `count`-family case) only guards `vals[i] == null` —
it never distinguishes "array present but empty" from "array present with items."
`countEmptyArray` (the closest sibling transform, added for the inverse case —
counting *ownerless* groups) already has the array-aware pattern this needs
(`Array.isArray(v)` + `.length`), it's just never applied inside `count` itself.

### Audit of other checks on the same transform

Queried `monitor_checks.mapping` for every row with `"transform": "count"`
(`node scripts/db/psql.mjs`, see bookend for the full list — 112 checks). All but
three use a scalar `sourceField` (`id`, `Name`, `displayName`, `severity`, etc.) —
unaffected, since a scalar is either present (truthy check passes as before) or
absent (already excluded).

Three genuinely use an array-typed Graph field with `count`:

1. `cost:underutilized-premium` — `assignedLicenses` (named in the issue).
2. `cost:group-based-licensing-adoption` — `assignedLicenses` (named in the issue).
3. `identity:mfa-method-breakdown` — `sourceField: "methodsRegistered"` against
   `/reports/authenticationMethods/userRegistrationDetails`. Graph's
   `userRegistrationDetails.methodsRegistered` is always an array (possibly `[]`
   for a user with zero registered methods), so this check has the identical
   presence-vs-content defect: `legacyMfaMethodCount` always equals the row's
   `itemCount`. This check additionally has `severity_rules: []` (no rules
   attached) — a separate, pre-existing gap that is out of scope for this fix
   (the transform bug is fixed; whether the check should instead filter for
   *legacy-specific* method names via `countWhere`, and whether it needs
   severity rules at all, is a design question for the check's own owner, not
   this transform-level bug). Filed as a finding, see below.

No other `count`-transform mapping in the table uses an array field.

## Proposed Changes

Fix `case "count"` in
[`artifacts/api-server/src/lib/monitor-executor.ts`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e244549245eb8ffbeb818b2066a2050d1921dcd/artifacts/api-server/src/lib/monitor-executor.ts#L1535-L1543)
so that when a value is an array, it's only counted when non-empty (mirroring the
`countEmptyArray` array-detection pattern already in the same file at
[monitor-executor.ts:1585-1614](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e244549245eb8ffbeb818b2066a2050d1921dcd/artifacts/api-server/src/lib/monitor-executor.ts#L1585-L1614)).
Scalar values keep their existing non-null behavior — no change for the 109
scalar-field checks in the audit above.

No schema/migration needed — this is a pure code fix to the executor; the
`monitor_checks.mapping` rows for all three affected checks are already correct
(`"transform": "count"` is the right vocabulary word, it's the transform's own
implementation that's wrong).

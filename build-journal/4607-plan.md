## Problem Description

`artifacts/api-server/src/lib/tenant-write-preconditions.live-verify.ts` (the opt-in
live-verify suite, run only via `vitest.live-verify.config.ts`, never in the default
regression sweep) has 3 of 7 tests failing against the real local Postgres and the
real testbed tenant (`mccawsoft2` / tenant row id 2080,
`c4c814d4-3afe-441e-9145-62461d0a4fd3`):

- `execute_action (#4528) > preview reports license_required and not ready on the
  unlicensed testbed tenant`
- `execute_action (#4528) > confirmed:true is refused 409 before any write`
- `SOP run (#4528) > SOP-SEED-IAM-03 (creates a CA policy) is refused license_required
  before any claim, persist or fire`

All 3 assert `code === "license_required"` and now get `"ca_enforcement_requires_promotion"`.

## Root Cause Analysis

`evaluateConfigPackPreconditions`
([config-pack-preconditions.ts#L229-L247](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/main/artifacts/api-server/src/lib/config-pack-preconditions.ts#L229-L247))
evaluates rule 0 (Git #4522 CA-enforcement) before rule 1 (license). Rule 0 refuses any
step whose *resolved* write is classified `create_enforced` or `enable_existing` by
`classifyCaEnforcementWrite`
([ca-enforcement-mode.ts#L100-L116](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/main/artifacts/api-server/src/lib/ca-enforcement-mode.ts#L100-L116)) —
a resolved body with `state === "enabled"`, on a POST to
`/identity/conditionalAccess/policies` or a PATCH/PUT to
`/identity/conditionalAccess/policies/{id}`.

**Confirmed live, direction (a) vs (b):** queried the real DB rows the 3 failing tests
exercise —

```sql
select template_id, method, endpoint, body_template from baseline_action_templates
where template_id = 'microrem.enforce-ca-policy';
--  microrem.enforce-ca-policy | PATCH | /identity/conditionalAccess/policies/{{policyId}} | {"state": "enabled"}

select sop_id, jsonb_pretty(steps) from msp_sops where sop_id = 'SOP-SEED-IAM-03';
--  step 3 "Enforce the policy": PATCH /v1.0/identity/conditionalAccess/policies/{id} { state: enabled }
```

Both write shapes hard-code `"state": "enabled"` directly in the template/SOP-step
content itself — this is **not** a stored per-policy state row, not a leftover CA
policy from an earlier live-verify run, and not affected by
`{{caPolicyState}}`/`withCaPolicyStateDefault`'s report-only fallback (that fallback
only applies when the template body reads the `{{caPolicyState}}` placeholder — these
two do not). Every run of `evaluateConfigPackPreconditions` against these exact steps
will classify them `enable_existing` and refuse under rule 0, on any tenant, regardless
of license state or of anything in `tenants`/`msp_sop_runs`/any policy table. There is no
transient test debris to clean up: **direction (a) applies.**

This also means the tests were never wrong about *what* the tenant lacks (it does lack
Entra ID P1, confirmed via the same `getProvisionedServicePlanNamesForTenant` read the
suite's own `beforeAll` performs) — they're wrong about *which* rule fires first, because
#4522 added rule 0 after these assertions were written for #4528 and rule 0 now wins the
race for these two specific writes.

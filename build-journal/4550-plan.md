# #4550 — Plan

Posted: 2026-09-17T23:59:51Z

## Problem Description

The customer-facing "hold window" cards on `/runbooks`
(`artifacts/portal/src/pages/runbooks.tsx`) show a "scan verdict" for a
report-only Conditional Access policy — clear / signals / watch — plus the
evidence sentence (`scan_line`), sourced from `portal_hold_windows.scan_verdict`
/ `scan_line` / `scan_source` / `scan_at`
([`lib/db/src/schema/msp.ts#L8300-L8380`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/2319db4a8b499b2cdcd3df0ab8908d108920e131/lib/db/src/schema/msp.ts#L8300-L8380)).

#4522 (5b7489b34) built the real evaluator — `evaluateCaPolicyImpact(tenantId,
policyId)` in
[`ca-policy-promotion.ts#L157-L219`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/2319db4a8b499b2cdcd3df0ab8908d108920e131/artifacts/api-server/src/lib/ca-policy-promotion.ts#L157-L219),
which reads real `GET /auditLogs/signIns` report-only outcomes for a policy and
returns would-block / would-interrupt counts, affected users and readiness. It
is wired to one place only: the **MSP-operator** read endpoint `GET
/api/msp/:mspId/customers/:customerId/ca-policies/:policyId/impact`
([`msp-ca-policy-promotion.ts#L126-L146`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/2319db4a8b499b2cdcd3df0ab8908d108920e131/artifacts/api-server/src/routes/msp-ca-policy-promotion.ts#L126-L146)).
Nothing calls it and writes the result to `portal_hold_windows`.

## Root Cause Analysis — the real, full data path

1. **Evidence exists, live, on Graph.** `GET /auditLogs/signIns` on the tenant
   carries `appliedConditionalAccessPolicies[].result` = `reportOnlyFailure` /
   `reportOnlyInterrupted` / etc. for every sign-in evaluated against a
   report-only policy. Real, reachable today (confirmed live against the
   testbed tenant `c4c814d4-3afe-441e-9145-62461d0a4fd3` this session — see
   Verification Plan).
2. **The pure arithmetic exists.** `summarizeReportOnlyImpact` /
   `evaluateCaPolicyImpact` in
   [`ca-policy-impact.ts`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/2319db4a8b499b2cdcd3df0ab8908d108920e131/artifacts/api-server/src/lib/ca-policy-impact.ts) /
   `ca-policy-promotion.ts` turn those rows into would-block / would-interrupt
   counts.
3. **The only caller is a read-on-demand MSP-operator endpoint.**
   `GET /api/msp/:mspId/customers/:customerId/ca-policies/:policyId/impact`
   calls `evaluateCaPolicyImpact` and returns the result straight to the
   response — it never persists it (`msp-ca-policy-promotion.ts#L126-L146`).
   `git grep -n "evaluateCaPolicyImpact"` across `artifacts/api-server/src`
   confirms this route and the verify script are the only two callers; neither
   writes to the database.
4. **`portal_hold_windows` is never written outside a QA fixture.**
   `git grep -n "portalHoldWindowsTable).values\|.insert(portalHoldWindowsTable)"`
   across the whole repo returns exactly one hit:
   `routes/admin-testbed.ts:979`, the `/admin/testbed/seed-runbooks` QA-seed
   endpoint. There is no production insert path for a hold window at all
   today (hold-window *creation* itself is a separate, larger gap than this
   issue — see Finding below). `git grep -n "scanVerdict:\|scanLine:\|scanAt:"`
   confirms the same: outside that one seed file, `scanVerdict` /
   `scanLine` / `scanAt` are only ever *read* (`portal-runbook-wire.ts`,
   `portal-runbooks.ts`, `msp-runbooks.ts`), never written.
5. **The read side (`GET /portal/runbooks` → `toWireHold` →
   `runbooks.tsx`) is already correct and needs no change.**
   `loadRunbooksForCustomer` /
   `toWireHold` in `portal-runbook-wire.ts#L147-L199` already project
   `scan_verdict`/`scan_line`/`scan_source`/`scan_at` straight onto the wire
   shape the page renders. This is confirmed by the seeded QA fixture
   rendering correctly today — the drop is entirely on the write side.
6. **The gap `portal_hold_windows` itself names but doesn't have: no link
   from a hold window to the CA policy it observes.** The table has no
   `policy_id` column, so even if a job existed, it would have nothing to
   scan *against* for a specific window.

**Where it's dropped, precisely:** a report-only policy's real impact is
computed live (step 2) and shown live to an MSP operator on-demand (step 3),
and then thrown away — it is never written to the one row
(`portal_hold_windows`) the customer-facing surface actually reads (step 4).
There is no scheduled or triggered job anywhere in the codebase that closes
that gap; `git grep` across `seed-system-workflows.ts` / `workflow-executor.ts`
/ `node-type-registry.ts` for anything CA-impact-shaped returns nothing.

## User Review Required

None — this is the "missing column / missing job" case the standing rules
call out as ordinary build work, not a product decision. (A related, larger
gap — hold windows are never *created* live at all, only via the admin QA
seed — is a separate, pre-existing issue outside this one's scope; filed
separately, see Findings below.)

## Proposed Changes

1. **`lib/db/src/schema/msp.ts`** — add `policyId: text("policy_id")`
   (nullable — only CA-policy-gated windows carry one) to
   `portalHoldWindowsTable`, plus an index for the scan job's own lookup
   query (`WHERE policy_id IS NOT NULL AND closed_at IS NULL`).
2. **`lib/db/migrations/manual/4550-portal-hold-windows-policy-id.sql`** —
   additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` + index, run by this
   session against the local `DATABASE_URL`.
3. **New `artifacts/api-server/src/lib/ca-hold-window-scan.ts`** — the
   writer. `handleCaPolicyHoldWindowScan(nodeData, payload)`: selects every
   open (`closed_at IS NULL`) hold window carrying a `policy_id`, joined to
   its tenant; for each, calls the real `evaluateCaPolicyImpact(tenantId,
   policyId)` (reused unchanged, no new Graph logic) and derives a real
   `scan_verdict` (`clear`/`signals`/`watch`) and a real, data-driven
   `scan_line` sentence from the actual counts/affected users returned —
   never a canned string. A non-`ok` read (consent revoked, license gap,
   Graph error, policy not found) is written honestly as `watch` with the
   real reason in `scan_line`, not silently skipped — the exact "silently
   dropped" failure mode this issue is about must not just move one layer
   down.
4. **`artifacts/api-server/src/lib/node-type-registry.ts`** — register
   `ca_policy_hold_window_scan` (not AI-dependent).
5. **`artifacts/api-server/src/lib/workflow-executor.ts`** — dry-run stub +
   real dispatch case for the new node type, following the
   `policy_evaluate_due` pattern exactly (import the handler, one `case`
   block).
6. **`artifacts/api-server/src/lib/seed-system-workflows.ts`** — new
   `__system__: CA Policy Hold Window Scan` schedule workflow, cron `0 * * *
   *` (hourly — matches the field's own `scanCadence` default and the
   established #1163 hourly-reconciliation convention), one node
   (`ca_policy_hold_window_scan`), no payload scoping (sweeps every tenant,
   same shape as the Policy Engine's divergence sweep).
7. **New `artifacts/api-server/src/lib/ca-hold-window-scan.test.ts`** — unit
   tests for the verdict/scan-line derivation and the DB write, mocking
   `graphFetchForTenant` the same way `msp-ca-policy-promotion.test.ts` /
   `ca-policy-impact.test.ts` already do (real evaluator code path, synthetic
   Graph response — not a display fixture).

**Not changed:** `portal-runbook-wire.ts` / `runbooks.tsx` (already correct),
`admin-testbed.ts` (a QA seed endpoint, not a production path — out of
scope), hold-window *creation* itself (separate gap, filed as a finding).

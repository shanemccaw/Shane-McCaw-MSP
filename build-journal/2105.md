  **Audit first** (verified against the real #2104 commit `964e3cb65`, not this prompt's
  description): Phase 1's real schema is `chat_pinned_questions(id, chat_id -> bt_chats.id,
  question_text, created_at, resolved_at)` with a partial unique index `(chat_id, question_text)
  WHERE resolved_at IS NULL`. Its real API is `BuildQueuePostgresClient.CreatePinnedQuestionAsync
  (int chatId, string questionText)` (returns false — not an error — on a redundant open dup),
  `GetOpenPinnedQuestionsAsync`, `ResolvePinnedQuestionAsync`. The bridge Phase 1 reused is
  `FloatingChatBridgeScript` (#2059/#2072): SEND = insert (`BuildInsertScript`) + submit
  (`SubmitScript`, which arms the #2072 correlation gate `__bcFloatyBeginWait`) + verify
  (`VerifySubmitScript`); RECEIVE = a ~1.2s poll that scrapes the last assistant turn to markdown
  and posts `BT_FLOATY_RESPONSE` only when the text changes. `BoardChat.Id` (the real `bt_chats.id`
  FK) is populated only by the direct-Postgres board path.

  **Real "turn completed" signal (audit item 2):** there was NO explicit turn-complete event in
  the existing bridge — `BT_FLOATY_RESPONSE` just fires repeatedly as the streaming text changes.
  The honest signal is the *settle edge*: the last turn's markdown stops changing. Added a new,
  purely-additive `BT_FLOATY_TURN_IDLE` message to `FloatingChatBridgeScript.CaptureScript` that
  fires **once** per settled turn (markdown stable for `IDLE_STABLE_MS = 2500ms`), placed after
  the #2072 wait-gate so a stale pre-send turn never fires it mid-probe. This is a real change→
  stable edge event on the existing poll, not a new polling loop, and every existing consumer
  ignores the new type.

  **Detection flow:** on `BT_FLOATY_TURN_IDLE` (`FloatingChatWindow.OnBridgeMessage`): if a probe
  is in flight for that tab, THIS idle is the probe's own answer → routed to a per-tab
  `TaskCompletionSource` (parsed), never re-probed (the loop-breaker); otherwise it's a genuine
  settled turn → `MaybeProbeForPinnedQuestionsAsync` sends `PinnedQuestionDetector.ProbePrompt`
  via the unchanged insert+submit+verify bridge, awaits the settled answer (90s bound), parses it,
  and persists each distinct question as its own row through new
  `LeftSidebar.CreatePinnedQuestionsFromDetectionAsync` → `CreatePinnedQuestionAsync`. A 10-minute
  per-chat cooldown (counted even on a failed send) stops every genuine turn drawing a probe.
  Gated on new setting `PinnedQuestionDetectionEnabled` — **default OFF** because it sends real
  messages into real conversations (consuming Claude usage, visible in the transcript); flip it in
  `%AppData%\BuildConsole\settings.json` (settings.json-only, same precedent as
  `EnforceWorktreeIsolation`).

  **Prose-to-distinct-questions parsing (audit item 3 — the real judgment call):** rather than
  regex-guess free prose, the probe asks the agent to answer in a strict format (one `Q: <text>`
  line per question, or the single token `NONE`). `PinnedQuestionDetector.ParseQuestions` uses that
  as the PRIMARY path (split on `Q:` lines, clean markdown/bullets/quotes, dedupe case-insensitively,
  never bundle). Only when the agent ignores the format does it fall back — first an explicit
  "none" check (guarded to require no `?` present), then structured list items containing `?`, then
  a last-resort sentence split keeping interrogatives.

  **Verified** the parser against 10 representative inputs via a throwaway console harness (deleted
  after; tree left clean): strict NONE→0, strict two `Q:`→2 split, bullet-prefixed `Q:`→cleaned,
  prose "no"→0, numbered-list questions→2, inline single→1, free-prose two→2 (sentence split),
  markdown-dup→1 (collapsed), empty→0, plain chatter→0. All correct.

  **Known limitations (documented honestly, not overstated):** (1) reliability of the primary path
  depends on the agent honouring the `Q:`/`NONE` format; the heuristic fallback is best-effort and
  imperfect — e.g. the free-prose sentence split keeps lead-in words ("Also, who should approve
  refunds?") and an inline single question captures its lead-in clause. (2) The probe is invasive:
  it posts a real message into the real conversation and consumes a turn/context — inherent to the
  issue's chosen "ask the chat" design; the cooldown + off-by-default mitigate spam. (3) Detection
  runs only for chats currently open as floaty tabs (that's where the live #2059 bridge exists); it
  does not spin up hidden browsers for every chat in the tree. (4) The agent may re-raise an
  already-resolved question; the DB partial-unique index dedupes identical open text but not a
  reworded restatement. (5) A genuinely new question raised within the 10-min cooldown is missed
  until the window elapses.

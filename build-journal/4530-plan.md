# Plan: #4530 — Graph pack `expectStatus` strict-gate rollout

**Posted:** 2026-09-17T23:35:35Z

## Problem Description

#4516 made `success_criteria.expectStatus` affect the Graph pack write path for the
first time, but only as a *widen* — a template's declared `expectStatus` is unioned
into the default `[200,201,204]` accept class (`graphAcceptedStatusCodes()`,
`artifacts/api-server/src/lib/workflow-executor.ts:732`). That fixed a real live bug
(`microrem.deactivate-ownerless-team`'s 202 was previously always "failed") but left
the issue's real ask open: a **strict** gate, where a write only counts as successful
if the actual returned status exactly equals the template's declared `expectStatus`,
dropping the shared default class for templates that declare one. #4516 deferred this
because 105/124 declared rows had no real execution history to check it against, and
most are destructive Graph writes not safe to fire live just to validate metadata.

## Root Cause Analysis

This isn't a bug — the widen-only fix is correct and non-regressive by construction.
The open question is purely a **rollout-safety** one: does the live data actually
support flipping to strict matching, and if not yet, what closes that gap without
firing destructive writes just to test metadata?

Live evidence gathered this session, queried directly against local Postgres
(same tenant/audit data #4516 checked, now with 7 more days of real traffic):

```sql
select count(*) as total_declared,
  count(*) filter (where exists (
    select 1 from baseline_action_template_audit_log bal
    where bal.template_id = bat.template_id
  )) as have_history
from baseline_action_templates bat
where bat.success_criteria ? 'expectStatus';
```
`total_declared = 124`, `have_history = 26` (up from #4516's 19 — real production
traffic is accumulating, as #4516's fallback plan anticipated).

The regression-relevant check — does any template have a real execution where the
returned status fell inside the *default* `[200,201,204]` class (i.e. a strict gate
would have called it a failure) but did **not** equal its own declared `expectStatus`:

```sql
select bat.template_id, bat.success_criteria->>'expectStatus' as expect_status,
  (bal.after_snapshot->>'status')::int as observed_status, bal.action, bal.created_at
from baseline_action_templates bat
join baseline_action_template_audit_log bal on bal.template_id = bat.template_id
where bat.success_criteria ? 'expectStatus'
  and (bal.after_snapshot->>'status')::int in (200,201,204)
  and (bal.after_snapshot->>'status')::int <> (bat.success_criteria->>'expectStatus')::int;
```
**0 rows.** Across all 26 templates with any real history, every observed status that
fell inside the default success class matched that template's own declared
`expectStatus` exactly. Every non-matching observed status (403, 400, 404, 500 — see
full breakdown below) was already outside the default class, i.e. already correctly
reported as a failure under both the old hard-coded scheme and today's widen-only
scheme — a strict gate changes nothing for those rows either.

Full per-template breakdown (`build-journal/` — not re-pasted here in full, see the
`Verification Plan` section for the exact query to reproduce):

| expect_status | audit rows (templates) |
|---|---|
| 204 | 51 declared / a handful with history |
| 200 | 41 declared |
| 201 | 31 declared |
| 202 | 1 declared (`microrem.deactivate-ownerless-team`, the #4516 fix) |

**So: for the 26/124 templates (21%) with real execution history, a strict gate is
safe today — zero observed conflicts.** For the remaining 98/124 (79%), there is
still no real evidence either way, and most of those are destructive writes
(delete-user, disable-user-signin, disable-per-user-mfa, create-ca-*-policy, etc.)
that this project's own conventions (production-change gate, "never invent data")
correctly forbid firing live just to accumulate metadata evidence.

## User Review Required

124 rows is NOT safely landable unattended this session**, for the same reason #4516
deferred it — 98 rows have zero real observed evidence, many are destructive, and

money/entitlement decision, but it is a real behavior-change risk to write paths Shane
actively runs against a real tenant, and I'm not going to narrow acceptance criteria
for 98 unverified rows (many destructive) on the strength of a 26-row sample, however
clean that sample is.

**What Shane can safely decide without further building:**
- Whether to promote the **21 templates with real history AND a clean 1:1 match**
  (excluding the 5 templates whose only observed statuses were errors, e.g.
  `quickstart-v1.disable-security-defaults` which has only ever returned 403 — a
  strict gate can't be validated for a template that has never once succeeded) to a
  strict per-template override list, once that's built (see below) — or wait longer
  for more data.
- Whether the shadow-instrumentation approach below is sufficient, or whether he'd
  rather manually confirm a batch of the 98 via Launch Control's own UI runs (the
  issue's third option) to accelerate coverage.

## Proposed Changes (this session)

Land the **safe, buildable** piece of the issue's second proposed option: instrument
the current widen-only path to make every write's expectStatus-vs-actual outcome
queryable, without changing pass/fail semantics for anyone. Concretely:

1. `graphAcceptedStatusCodes()` stays widen-only — zero behavior change to the accept
   class.
2. Extract the template's declared `expectStatus` (a small new export,
   `declaredExpectStatus()`) and, at the Graph pack write call site
   (`workflow-executor.ts` around the `graphWriteForTenant` call for the main
   template path), record two new fields on every audit log row that declares an
   `expectStatus`:
   - `expectStatus`: the declared value (verbatim, for easy querying without a join)
   - `expectStatusMatch`: `true`/`false` — whether the actual returned status equalled
     the declared value (only computed when the write was accepted as a success under
     today's widened class; irrelevant/omitted for already-failed writes)
3. When a write succeeds only because of the widened class (`expectStatusMatch ===
   false`), log a structured warning (`logger.child({ channel: "engine.workflow" })`)
   naming the template, endpoint, declared vs. actual status — visible in real time,
   not just queryable after the fact.
4. This directly builds the dataset the issue's second option describes ("let real
   production traffic build a real observed-status dataset over time"), in a durable,
   queryable form (the audit log, already the system of record) rather than only in
   logs. A future session (or Shane) can re-run the exact query in this plan at any
   time to see live coverage grow, with zero risk of narrowing anyone's acceptance
   criteria today.
5. No schema migration needed — `afterSnapshot` is an existing `jsonb` column;
   `expectStatus`/`expectStatusMatch` are just new keys within it, exactly like the
   existing `licenseFeature`/`errorType` keys.

**Explicitly not doing this session:** flipping `graphAcceptedStatusCodes()` (or
adding a second, strict-mode function used by default) to actually narrow the accept
class. That stays deferred until coverage broadens past today's 26/124, per the User
Review Required section above.

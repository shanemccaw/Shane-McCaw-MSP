  **New primitive — `Services/StartupGitHubCoordinator.cs`:** a static, thread-safe,
  proactive gate modeled on the existing `GitHubRateLimitCircuit` static-coordinator
  pattern. During a bounded cold-start window (first 120s of process uptime, anchored
  to `Process.StartTime`) it serializes registered startup GitHub operations through a
  single-permit `SemaphoreSlim` with a 750ms inter-op settle gap, so DIFFERENT
  subsystems don't overlap. Each op keeps its OWN internal bounded concurrency inside
  its slot. After the window it's a pure pass-through (steady-state manual refreshes
  never delayed). An `AsyncLocal<bool>` re-entrancy flag prevents self-deadlock if a
  gated op ever calls back in; a 60s max gate-wait means a hung op degrades to
  "uncoordinated call", never "frozen app". `RunAsync(label, work)` + a result-returning
  `RunAsync<T>` overload.

  **Wired the five real burst subsystems named in the issue through it:**
  - Home queue/board reconciliation — `MainWindow.RefreshHomeRollupAsync` force block
    (~500 `gh` open-issue numbers + board reconcile), one coordinated op.
  - In-Flight tile initial load — `BuildQueuePanel.RefreshInFlightIssuesAsync`
    (`gh issue list --label in-flight`, ~50).
  - Orphan-recovery board Status mirrors — `BoardStatusSync.Mirror` inner work (one
    board Status move per crashed build); all startup-time mirrors now serialize.
  - Blocked-by sweep — `LeftSidebar.EnrichBlockedStatusAsync` (~528 blocked_by REST
    calls, concurrency=6 preserved inside the slot); split into a thin wrapper +
    `EnrichBlockedStatusCoreAsync`.
  - Issue-title warm-up — `BuildQueuePanel.TriggerBackgroundIssueTitleQueries`, batched
    as ONE coordinated op during cold start (fetches still run 3-at-a-time inside).

  **Verified side effect (did NOT assume — CONFIRMED):** the "N issue(s) blocked
  remotely" whammy flood following the rate-limited sweep is an honest, temporary,
  self-correcting artifact, exactly as the issue hypothesized. Code-level proof:
  `GetConditionalAsync` calls `EnsureSuccessStatusCode()`, so the circuit's synthetic
  403 throws; `GetBlockedByAsync` only catches 404, so the 403 propagates into the
  sweep's per-issue `catch {}`, which leaves the seeded (false) value. A rate-limited
  sweep therefore records a false-empty `_knownBlockedIssueNumbers` baseline, and the
  next clean sweep flags the ENTIRE true blocked set as "newly blocked" → the flood.
  Real corroboration: only 12 open issues currently carry the `blocked` label vs the
  116 the whammy announced — an order-of-magnitude gap. Fix: added
  `GitHubRateLimitCircuit.IsOpen` (pure, side-effect-free read) and made the sweep skip
  itself while the circuit is open (without advancing its throttle, so it re-runs once
  the circuit closes) — belt-and-suspenders alongside the coordinator, which keeps the
  circuit from opening at all. #3005's gate-lift board-fetch → queue-recovery mechanism
  is untouched (only the sweep, not the board fetch, is gated).

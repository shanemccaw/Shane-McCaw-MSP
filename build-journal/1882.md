## Log
- 2026-08-30 ⏳ IN FLIGHT — Investigating StartupLoadingView / InitializeStartupOverlay / _startupConnectivity sequencing across the three failure modes in the issue body.
- 2026-08-30 ✅ DONE — Traced all three modes against a REAL cold-start log trace (`%AppData%\BuildConsole\logs`, ms timestamps). Root cause: the whole ~8s heavy MainWindow construction (WebView2 env warmup, queue watcher, panels, Home tab, focus mode) ran **synchronously on the UI thread before the window was ever shown**, and `InitializeStartupOverlay()` was the very LAST ctor line — so the user saw a frozen black window first, the overlay flashed at the tail, and `AllSettled` (10 network probes) dismissed it while WebView2/Home were still settling.
  - **Fix (`7d872eab7`):**
    - Deferred the heavy ctor tail into `RunDeferredStartupAsync()`, kicked off from `ContentRendered` (after the first frame paints) so the animated overlay appears FIRST. Chunked with `Dispatcher.Yield` at phase boundaries so the animation never freezes while init runs.
    - `StartupConnectivityService`: services moved from ctor → `Start(...)`; overlay rows/events wired the instant the window paints (`InitializeStartupOverlayShell`). Added an umbrella `KeyShell` "Application shell" row that stays non-terminal until `MarkShellReady()`, so `AllSettled`/dismiss means the app is genuinely ready, not just that probes returned. `finally`-block `MarkShellReady()` guarantees the overlay always dismisses.
  - **Verification (instrumented cold start, then reverted the temp logging):** thin ctor returns 08:20:58.745 → **ContentRendered / overlay PAINTED 08:21:01.109** → heavy WebView2 init begins 01.139 (30ms later) → deferred tail runs to `Application shell: ok (2022ms) — ready` 03.724. Overlay is on screen before the heavy work; init runs non-blocking after; dismiss gated on real readiness. `dotnet build …BuildConsole.csproj -c Release` clean (0/0). `git status` clean. Branch merged to origin/main.

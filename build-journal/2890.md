## What shipped

`TriggerBackgroundIssueTitleQueries()` was called from the periodic queue-refresh handler
(~line 821) and fired one **unawaited, unbounded** `FetchAndCacheIssueTitleAsync(num)` — i.e. one
`gh issue view` subprocess — per uncached issue number, all simultaneously, on **every** tick.
While the rate-limit circuit was open, every call was rejected, so `_issueTitleCache` never
populated, so the next tick re-fired the identical full burst — self-perpetuating.

Both fix requirements from the issue landed together:

1. **Bounded concurrency.** New `static SemaphoreSlim _titleFetchConcurrency` (limit
   `MaxConcurrentTitleFetches = 3`). `FetchAndCacheIssueTitleAsync` now `await`s the semaphore
   before the `gh` call and releases it in a `finally`, so no matter how many numbers are queued,
   at most 3 `gh issue view` subprocesses run at once — the calls stagger instead of bursting.
2. **Per-number retry cooldown.** New `static Dictionary<int, DateTime> _titleFetchCooldownUntil`
   with `TitleFetchRetryCooldown = 60s`. On a **transient** failure (the neither-Title-nor-NotFound
   branch, and the outer `catch`), the number is stamped with a "retry not before" time.
   `TriggerBackgroundIssueTitleQueries` skips any number still in cooldown, so a persistently-failing
   number is not re-attempted on the very next tick (bounded concurrency alone would still re-fire
   every failing number every tick, just slower). A successful fetch clears the cooldown; a hard
   `NotFound` still uses the existing `_unresolvableIssueNumbers` permanent skip (Git #1979).

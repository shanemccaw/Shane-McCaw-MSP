- 2026-09-12T01:54:28Z ✅ DONE — Shipped in `f58ae1e09`. Real changes, all in
  `desktop/BuildConsole/MainWindow.xaml.cs`:
  - `EnsureWebViewInitializedAsync` now wires `CoreWebView2.ProcessFailed` on every
    successful init (unsub-then-resub via a `ConditionalWeakTable<WebView2,
    EventHandler<...>>` so a forced re-init doesn't double-subscribe), gained a
    `forceReinit` escape-hatch param, and tracks every live WebView2 weakly in that same
    table so a whole-app recovery can enumerate them.
  - `RenderProcessExited` → `RecoverFromRenderProcessExitedAsync`: calls the SDK's own
    documented `CoreWebView2.Reload()` (confirmed against the WebView2 1.0.4129.50 SDK's
    own XML doc comments — this enum value's docs literally say "You can use the Reload
    method to try to recover from this failure"), logs the real reason/exit code, toasts
    `ToastEngine.Warning("Chat tab recovered", ...)` on success or
    `ToastEngine.Error("Chat tab crashed", ...)` if the reload itself throws.
  - `BrowserProcessExited` → `RecoverFromBrowserProcessExitedAsync` (the higher-priority
    branch per the issue): nulls `_sharedWv2EnvTask` so the next
    `GetSharedWebView2EnvironmentAsync()` call builds a genuinely fresh environment, then
    loops every tracked WebView2 through `EnsureWebViewInitializedAsync(wv,
    forceReinit: true)` and re-navigates each to its own last `Source`. Per-tab failures
    are caught individually and named in the log/toast rather than aborting the whole
    recovery loop.
  - Every `ProcessFailed` firing (any kind, not just the two recovered ones) is logged
    to `ActivityLog` under channel `webview2` with the real `kind`/`reason`/`exitCode`.
  - **Honest caveat, checked against the SDK's own doc comments (not guessed):** the
    `BrowserProcessExited` enum value's own XML doc says "The WebView automatically
    moves to the Closed state. The app has to recreate a new WebView to recover from
    this failure" — i.e. Microsoft's strictly-documented recovery path is a brand-new
    `WebView2` *control instance* swapped into the visual tree, not a forced re-init of
    the same instance. A full instance-swap would need per-call-site changes across four
    structurally different hosts (dynamic `TabItem.Content`, a `Panel.Children` bridge
    host, an XAML `x:Name` field, and a test-infra field) — out of proportion for this
    issue, and this issue's own body explicitly asked for the same-instance
    forceReinit + reload approach implemented here ("confirmed with Shane directly").
    Implemented exactly as specified, defensively: every reinit attempt is
    individually try/caught, so if a given tab's same-instance reinit doesn't fully
    recover in practice, that tab is named in the log/toast rather than silently
    dropped, and the crash itself is no longer silent — it is detected, logged, and at
    minimum attempted, which is the real gap this issue was filed to close.
  - **Verification:** `dotnet build BuildConsole.csproj -c Debug` — build succeeded, 0
    errors (pre-existing unrelated warnings only). No safe way exists to trigger a real
    WebView2 renderer/browser crash in this environment to observe live end-to-end
    recovery (no reachable `edge://crash`-equivalent affordance from a hosted WebView2
    control), so this was verified via code review against the actual WebView2 SDK XML
    doc comments for `CoreWebView2ProcessFailedKind`/`ProcessFailed` (see above), which
    is the SDK's own authoritative behavior description, not guesswork.
  - No fixture/hardcoded data — no test-manifest applicable (BuildConsole/WPF is out of
    scope for test manifests per CLAUDE.md).

  `mccawsoft2.onmicrosoft.com`. NOT the `-TenantId` domain-vs-GUID shape the issue
  guessed. The child logged the real exception:
  `AADSTS700027: The certificate used to sign the client assertion is not registered
  on application '9ea2e409-...'`. Verified with `az`: the app registration
  `9ea2e409-d1b9-422a-8451-02fa0b98d1c3` trusted only cert `BC8F5C26...`
  (`CN=ShaneMcCawMSP-MT-App-2026`), while the container signs with the Key Vault
  `mt-app-cert` PEM (`251BDCD5...`, `CN=ShaneMcCawMSP-MT-App`) — the exact thumbprint
  the committed `services/ps-execution/README.md` documents as the app-only cert.
  Only `mt-app-cert` exists in the vault; the platform holds the private key for
  `251BDCD5` only. A real cert trust-drift, not a formatting artifact (PEM is
  well-formed multi-line). Same shared app-only auth underlies the EXO path (#1482).
- 2026-08-29 ⏳ IN FLIGHT — Fix #1 APPLIED (Shane approved). Appended `251BDCD5`'s
  public cert to app `9ea2e409` keyCredentials (`az ad app credential reset
  --append`), keeping the existing `BC8F5C26`. Live re-run: `auth_failed` is GONE —
  the Teams session now establishes (~5.5s). Confirmed the cert fix works end to end.
- 2026-08-29 ⏳ IN FLIGHT — Root cause #2 surfaced (issue item #2). With auth working,
  `Get-CsOnlineUser` returns **"Access Denied."** The service principal
  (objectId `1c640fe8-1c23-4510-8235-9ee6938d8f8b`) has ZERO Entra directory role
  assignments; its only membership is the `PS-Execution-DLP-Access` security group
  (Purview/DLP path, not Teams). App-only `Get-CsOnlineUser` requires a Teams-capable
  directory role on the SP — Graph app permissions alone are insufficient. Remaining
  blocker: grant a Teams directory role (Global Reader = read-only, or Teams
  Communications Administrator) to the SP in the target tenant. This is a per-tenant
  grant needed in EVERY customer tenant for production, analogous to the existing DLP
  role-group provisioning — flagged as a follow-up. Awaiting decision on the role
  grant before the final live `ok:true` verification.
- 2026-08-29 ✅ DONE — Fix #2 APPLIED (Shane chose Global Reader). Granted the Global
  Reader Entra directory role (`roleTemplateId f2ef992c-3afb-46b9-b7cf-a126ee74c451`,
  read-only) to the SP `1c640fe8-...` in `mccawsoft2.onmicrosoft.com`. Live re-run of
  `get-cs-online-user`: **HTTP 200, `ok:true`** — Access Denied gone. Result body is
  `[]` because the container `PostFilter` (`EnterpriseVoiceEnabled -eq $true -and
  LineURI`) narrows to Teams-Phone-provisioned users, and the testbed has real users
  (10+) but ZERO Enterprise-Voice/MCOEV-licensed ones (verified via Graph
  `assignedPlans`). Per the no-fabrication rule this is recorded as a genuinely-empty
  real result, not faked data. Real Teams-session data was independently confirmed via
  `get-cs-teams-meeting-policy` (no filter) → real policy objects returned, HTTP 200.
  **The connect failure this issue is about is fully fixed and live-verified.**
  extracted_properties the check reads: `EnterpriseVoiceEnabled` (bool) + `LineURI`
  (string) — a populated `Get-CsOnlineUser` sample can't be observed in this testbed
  (no phone users) and must NOT be fabricated; capturing one needs a phone-provisioned
  tenant.

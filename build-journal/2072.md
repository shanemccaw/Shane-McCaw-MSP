# #2072 — Floating Chat Window: stale/mismatched response render (trust bug) + broken glyph rendering

- **Status:** ✅ DONE
- **Scope:** buildconsole
- **Started:** 2026-08-31
- **Commit(s):** a8e046e1f (IN FLIGHT bookend), 59a549be8 (fix) — both verified ancestors of origin/main

## Log
- 2026-08-31 ⏳ IN FLIGHT — Working #2072 against the CORRECTED diagnosis comment (which supersedes
  the original "attachments don't send" body). Real bug: Shane sent only "hi" via the floaty (#2059)
  and the rendered response was an answer to an UNRELATED prior turn already in the conversation, not a
  reply to "hi". Auditing `Services/FloatingChatBridgeScript.cs` (send: insertText+submit; receive:
  `.font-claude-message` / `[data-testid=assistant-message]` / `[role=article][aria-posinset]` last-turn
  scrape) and its host `FloatingChatWindow.xaml.cs` before any code change.

  Audit findings (root cause):
  1. RECEIVE-SIDE (trust-critical): `CaptureScript.poll()` posts whatever assistant turn is *last in the
     DOM* the first time it sees non-empty text (`lastSent === null`) — with no correlation to a message
     the user actually sent from the floaty. Opening an existing conversation therefore surfaces the
     pre-existing last reply as if it were "the response". If the send silently fails, or before the new
     turn streams, the pane keeps showing that stale turn — exactly the reported symptom.
  2. SEND-SIDE (contributing): `SubmitScript` returns `'sent'` immediately after `btn.click()` with no
     verification the composer cleared / a new turn started — a false-success path.
  3. GLYPH (secondary): the DOM→markdown walk recurses into unknown elements with no skip for
     `svg`/`button`/`[aria-hidden]`/`[role=button]`, so icon-font (PUA) glyphs from scraped UI controls
     leak into the markdown and render as tofu (□ □) after the text.

  Fix approach: arm a receive-side baseline gate at submit time so a stale pre-send turn is NEVER
  surfaced as the reply (only a genuinely NEW assistant turn is), verify the submit actually landed
  (composer cleared) instead of trusting the button click, clear the pane to an honest "Waiting for
  reply…" state on a confirmed send, skip non-content control subtrees during scrape, and sanitize
  never-legitimate codepoints (PUA / control / replacement chars) in MarkdownRenderer as defense in depth.
- 2026-08-31 ✅ DONE — Shipped the fix in commit 59a549be8 (rebased onto origin/main over the
  intervening #2063 refactor that extracted the shared `InsertAndSubmitAsync` helper; resolved so
  the confirm+gate logic lives in that shared helper and benefits BOTH the manual Send button and
  the programmatic `SendToActiveTabAsync`). Three files: `Services/FloatingChatBridgeScript.cs`
  (correlation gate `__bcFloatyBeginWait`/`__bcFloatyCancelWait` in CaptureScript; SubmitScript
  arms the gate and returns provisional 'submitted'; new VerifySubmitScript confirms the composer
  cleared; CancelWaitScript; `isSkippable` skips svg/button/[aria-hidden]/[role=button] during the
  DOM->markdown walk), `FloatingChatWindow.xaml.cs` (per-tab `AwaitingReply`; pane clears to an
  honest "waiting for the reply" state on a CONFIRMED send; `InsertAndSubmitAsync` now confirms via
  the composer-clear check instead of trusting the button click), `Services/MarkdownRenderer.cs`
  (`StripUnrenderableGlyphs` strips PUA/control/zero-width/replacement codepoints).

  ROOT CAUSE (both plausible mechanisms in the issue collapse to one design flaw): the receive-side
  capture posted whatever assistant turn was last in the DOM the first time it saw text
  (`lastSent === null`), with NO correlation to a message the user actually sent from the floaty.
  Opening an existing conversation surfaced its pre-existing last reply as if it were the answer;
  and the old send path reported a false 'sent' the instant it clicked Send, so a silently-failed
  submit left that stale reply on screen looking legitimate — exactly Shane's "sent 'hi', saw an
  answer to 'what's this referring to'". The fix makes the pane trustworthy at the moment that
  matters (the send): stale is dropped, only a genuinely NEW/changed assistant turn is surfaced,
  and an unconfirmed send shows an honest waiting/failed state rather than a stale answer.

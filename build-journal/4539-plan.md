# Plan — #4539: `governance:guest-staleness` has no guest filter

## Problem Description

`governance:guest-staleness` (endpoint `/users`, mapping
`[{sourceField: signInActivity, transform: countIfLastSignInOlderThan(90), targetField: staleGuestCount}]`)
has no `filter_params` and no `userType` scoping anywhere in its mapping.
`userType` is fetched (`properties: ["id","userType","signInActivity"]`) and
shown in evidence, but nothing in the check actually filters on it. As written
it counts every stale **user** on the tenant — guest or member — despite the
check's key, label ("Guest Account Staleness"), description ("Guest accounts
with no sign-in activity in 90+ days"), and severity rule
(`staleGuestCount > 0` → warning) all being guest-specific.

#4524 fixed this check's other, unrelated defect (missing `$select`, which
made `signInActivity` never evaluate at all) but explicitly left the
population-scope defect for this issue.

## Root Cause Analysis

Confirmed against the real local Postgres row
(`monitor_checks.key = 'governance:guest-staleness'`, id 42):

```
endpoint       /users
select_params  id,userType,signInActivity
filter_params  (empty)
mapping        [{"transform":"countIfLastSignInOlderThan(90)","sourceField":"signInActivity","targetField":"staleGuestCount","requireField":true}]
```

No filter is applied server-side, and the mapping has only one rule (no
second condition to intersect on `userType`), so the transform evaluates
`signInActivity` over the *entire* returned user set.

Two existing scoping patterns already exist in this catalog for the "guest"
population:

1. **Client-side count** — `governance:guest-count` uses
   `{"transform":"countEquals('Guest')","sourceField":"userType",...}` with no
   `filter_params`. This works because it has exactly one condition
   (`userType == 'Guest'`) to evaluate. `guest-staleness` already has its one
   condition slot occupied by `countIfLastSignInOlderThan(90)` on
   `signInActivity` — there's no `countWhere`-style compound predicate in use
   here that would let both conditions be expressed in one mapping rule
   without changing the check's evaluated shape.
2. **Server-side `$filter`** — `identity:break-glass-health` uses
   `filter_params = "startswith(userPrincipalName,'breakglass') or startswith(displayName,'Emergency Access')"`
   against the same `/users` endpoint, and `appgov:enterprise-app-registration-list`
   uses `filter_params` against `servicePrincipals`. `exchange:distribution-list-count`
   embeds an equivalent `$filter` directly in its endpoint URL. This is the
   pattern the issue itself points at ("same shape as
   `exchange:distribution-list-count`'s existing `$filter` usage").

Server-side `$filter` is the correct fix here: it scopes the Graph fetch
itself to guests, so `signInActivity` is only ever evaluated over guest
accounts — cheaper (no member accounts fetched at all) and requires no change
to the mapping/transform.

[`monitor-executor.ts`'s `graphFetchPaginated`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/1efb6059ca78a6f778286b95fd07574df0685e72/artifacts/api-server/src/lib/monitor-executor.ts#L2176-L2180)
already attaches `ConsistencyLevel: eventual` automatically whenever the built
URL contains `$filter=`, and
[`appendQueryParams`](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/1efb6059ca78a6f778286b95fd07574df0685e72/artifacts/api-server/src/lib/monitor-executor.ts#L656-L674)
already appends `filter_params` from the DB row onto the endpoint URL as
`$filter=...`. `userType eq 'Guest'` is a standard (non-advanced) Graph
filter — no code change is required, only the data fix.

## User Review Required

None. This is a missing population filter on an existing check, not a product
decision — same class of gap the standing "BUILD IT" rule already covers for
missing backend surface, applied here to a missing filter rather than a
missing column.

## Proposed Changes

- **New file:** `lib/db/migrations/manual/2026-09-17-guest-staleness-guest-filter-4539.sql`
  — additive, idempotent `UPDATE monitor_checks SET filter_params = 'userType eq ''Guest''' WHERE key = 'governance:guest-staleness'`,
  guarded by `filter_params IS DISTINCT FROM ...` so re-running is a no-op,
  plus the standard `simulator_migration_runs` self-marking insert (per
  CLAUDE.md's manual-migration convention). No Drizzle schema change — this
  edits existing row data in an existing column (`monitor_checks.filter_params`
  already exists and is already used by other checks), not a new column/table.
- No application code changes — `monitor-executor.ts`'s existing
  `appendQueryParams` / `ConsistencyLevel: eventual` handling already covers
  this shape correctly (see links above and precedent in
  `identity:break-glass-health`).

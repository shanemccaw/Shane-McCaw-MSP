## Real UX call this audit resolves (not left ambiguous)

Card-creation flow per type:
- **Communications Push / Training Session cards**: created **inline on the board** — the
  MSP operator fills the type-specific fields directly in the "add card" form, which creates
  the real underlying row (via the same insert logic as the existing standalone routes) *and*
  the linked `kanban_cards` row together. This is the only viable flow because neither entity
  has any existing standalone browse/pick UI to link from.
- **Automation Registry cards**: **link to an existing entry only** — no inline create. MSP
  operators cannot write `automation_registry` (admin/MyArchitect-only by design, per the
  schema's own comment), so a kanban card can only reference an entry that already exists.
  This required a new **read-only** MSP-operator-scoped list endpoint (nothing in the admin
  tier changes) so the board's "link an automation" picker has something to query — filed as
  part of this build, not a separate finding, since it's squarely "the surface needs an
  endpoint that doesn't exist yet, build it."

## Design decisions

- `kanban_cards.type`: nullable `text`, CHECK'd to the 3 real values + NULL (NULL = existing
  plain task cards, zero backfill needed).
- Three nullable linking columns (`communications_push_id`, `training_session_id`,
  `automation_registry_id`), each a **real FK** (all four tables live in the same Postgres
  schema — this is not the tenants.id "successor id-space" case `customer_id` uses elsewhere),
  `ON DELETE CASCADE` (matches the repo's own existing convention for
  `kanban_cards.bucket_id`/`communications_push_checkpoints.push_id` — a card representing a
  now-deleted entity should disappear with it). A CHECK constraint enforces exactly one linking
  column is set iff `type` says so.
- Deleting a *card* never deletes the underlying tracked entity (no reverse cascade) — the
  entity is the real record; the card is just its board representation.

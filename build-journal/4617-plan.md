# #4617 — Real creation path for `portal_hold_windows`

## Problem Description

`git grep -n "portalHoldWindowsTable).values"` returns exactly one hit:
`artifacts/api-server/src/routes/admin-testbed.ts:979`, inside the admin-only
`POST /admin/testbed/seed-runbooks` QA fixture. No route, workflow node, or
engine anywhere in the real product creates a `portal_hold_windows` row. Live
on the local dev DB before this build: `select count(*) from portal_hold_windows`
= 0. #4550 (already shipped) rescans and writes a real verdict onto a hold
window that already exists, but nothing makes one exist in the first place —
the whole hold-window / Runbooks-gating half of #1489's Remediation Tracking
module has no live entry point.

## Root Cause Analysis

`portal_hold_windows` was built schema-first (waitDays/startedAt/gatesStepPosition/
policyId, per #1940/#4550) and read-first (the customer Runbooks page,
`portal-runbook-wire.ts`, and the MSP extend/close/release routes,
`msp-runbooks.ts`/`portal-runbooks.ts`) — but the one thing that actually
*raises* a window was only ever built as QA seed data (`admin-testbed.ts`), and
never generalized into a real trigger.

## User Review Required

Two real candidate triggers exist in the codebase for "a wait-then-decide gate
that should become a `portal_hold_windows` row." I investigated both, chose
one, and am explicitly flagging why the other is **not** built here rather than
silently skipping it:

1. **Conditional Access report-only writes (#4518/#4522/#4550).** Every CA
   policy write through the shared executor (`runBaselineTemplateAgainstTenant`,
   `workflow-executor.ts:1405`) defaults to `state:
   "enabledForReportingButNotEnforced"` (`ca-enforcement-mode.ts`) unless a pack
   run explicitly chose "immediate." This looked like the obvious trigger going
   in — it is the one the #4617 issue body itself cites as precedent (the
   fixture's own `hold-ca01` example) — **but I did not wire it**, because
   Shane's own recorded decision on #4518
   (`gh issue view 4518 --json comments`, 2026-09-17) explicitly says promotion
   to enforced is **never** time-gated: "explicit promotion... not automatic
   timed promotion, Option C." `portal_hold_windows` is inherently a
   *time*-gated mechanism (`waitDays`, `startedAt`, a `due`/`closing` state
   machine derived purely from elapsed days — `portal-hold-windows.ts`).
   Raising one off a CA report-only write would bolt a "wait N days, then
   decide" clock onto a workflow Shane already decided is impact-gated, not
   time-gated, and there is no real day count anywhere in the CA code to use
   for `waitDays` — inventing one would be inventing exactly the Option-C
   mechanism he rejected. This is the kind of product conflict the dispatch
   says to stop for, so I stopped and did not build it.

2. **The real (non-QA) SharePoint site-fix runbook catalogue**
   (`portal-oversharing-sites.ts`'s `RUNBOOK_CATALOGUE`, created via the real,
   already-shipped `POST /portal/oversharing/runbooks/:sopKind`). Of its three
   SOPs, exactly one — `convert` ("Convert to Private") — has an actual,
   already-shipped, customer-facing wait commitment written into its own step
   copy: step 4 reads *"If no admin responds within 30 days, convert the site
   to Private automatically."* 30 days is a real number already promised to
   customers today, with zero enforcement behind it. This is what I built.

   The other two SOPs — `reduceAdmins` ("Allow time for admins to remove
   themselves voluntarily") and `manageGuests` ("Wait for admin response") —
   describe the same *shape* of wait-then-decide gate but name **no concrete
   day count** anywhere in code or in the portal's own copy
   (`grep -rn "30 days\|14 day" artifacts/portal/src` finds nothing for either).
   Inventing a number for either would be inventing a customer-facing
   timing promise that does not exist in the product today — a real product
   decision, not an implementation detail. Per the dispatch's own instruction
   ("stop only for a real product decision... a conflict with a decision
   already recorded on an issue"), I did not guess a number for these two, and
   filed the gap as its own Ask-Shane-routed sibling of #1489 instead of
   building it (see below).

## Proposed Changes

- **`lib/db/src/schema/msp.ts`** — no change; `portal_hold_windows` already has
  every column needed (`runbookId`/`runId` nullable, everything else already
  present per #4550). No migration required.

- **New: `artifacts/api-server/src/lib/portal-runbook-hold-triggers.ts`**
  ([permalink base](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/main/artifacts/api-server/src/lib/))
  — a small, real catalogue (`RUNBOOK_HOLD_TRIGGERS: Record<string,
  RunbookHoldTrigger>`) keyed by `runbookKey`, today holding exactly one entry:
  `oversharing-convert-to-private` → `{ triggerStepPosition: 1, holdKey:
  "oversharing-convert-notice", title, gates, gatesStepPosition: 4, pillar:
  "governance", waitDays: 30, why, scanSource, scanCadence: "manual", scanLine
  }`. `triggerStepPosition` is step 1 ("Notify all site admins...") because
  that notification is what starts the 30-day clock the step-4 copy refers to.

- **`artifacts/api-server/src/lib/portal-runbook-wire.ts`** — add
  `maybeRaiseHoldWindowForStep(opts: { runbook, run, position, checked, now
  })`, colocated with the existing `maybeAdvanceCycle` (same file, same
  calling convention: called from both step-tick routes right after a
  successful check). Looks up `RUNBOOK_HOLD_TRIGGERS[runbook.runbookKey]`; if
  none, or `position !== trigger.triggerStepPosition`, or `!checked`, no-op.
  Otherwise inserts a real `portal_hold_windows` row (`runbookId: runbook.id`,
  `runId: run.id`, `customerId: runbook.customerId`, `startedAt: now`,
  `scanVerdict: "watch"`, plus the trigger's fields) with
  `.onConflictDoNothing({ target: [portalHoldWindowsTable.customerId,
  portalHoldWindowsTable.holdKey] })` against the existing unique index — so
  re-ticking/re-running the step is a real no-op, not a duplicate or a reset
  clock.

- **`artifacts/api-server/src/routes/portal-runbooks.ts`** (PUT
  `/portal/runbooks/:runbookId/steps/:position`, ~line 221) and
  **`artifacts/api-server/src/routes/msp-runbooks.ts`** (its mirror route,
  ~line 195) — call `await maybeRaiseHoldWindowForStep({ runbook, run,
  position, checked, now })` alongside the existing `maybeAdvanceCycle` call,
  same `if (checked)` branch.

- **No fixture/hardcoded display data added** — this is a real DB write fired
  by a real user action (ticking a real step on a real, already-shipped
  runbook), read back through the existing real `GET /portal/runbooks` →
  `loadRunbooksForCustomer` → `toWireHold` path. Nothing new is rendered from
  a constant.

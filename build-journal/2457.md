  **What shipped.** The `ROLE_ORDER` ladder as data: each of the seven rungs is a
  platform-scoped `is_system` role in **both** role tables (the customer-side rules genuinely
  branch on MSP tier, and a customer-system evaluation cannot see MSP-system roles), and each
  `requireRole(X)` floor is a capability `ladder.<x>` whose allow set is every rung at or
  above X — computed in SQL by joining the ladder to itself on `idx >= idx`, which *is*
  `roleIndex(held) >= roleIndex(required)`, enumerated instead of evaluated. Each capability
  column became a role with one capability and one member set, granted from the real `users`
  rows rather than a list of ids. The `role = 'admin'` → PlatformAdmin promotion is carried
  across deliberately, which is what #1696 asks for. Plus `lib/db/src/rbac/legacy-ladder.ts`,
  the citable transcription of what those rules are today, which #2458 also needs.

  **Three capability columns, not two.** The issue body names `can_manage_team` and
  `can_approve_purchases`; the database also carries `can_approve_changes` (#1496, enforced
  live in `portal-change-control.ts`). Carrying two of three forward would have been exactly
  the gap the issue's own contract forbids. They are also read **asymmetrically**, and the
  transcription keeps that rather than tidying it: `can_approve_purchases` only grants on the
  MSPOperator branch (`msp-v1.ts:337-351`), so it is seeded for MSPOperators only — a column
  that grants nothing today must not start granting here; `customer:team.manage` exempts three
  role *names*, so a ServiceAccount passes flagless, while `changes.approve` names a different
  three and a ServiceAccount does not.

  **Verification, honestly.** `pnpm --filter @workspace/db run check-rbac-parity` — 888

  **The one deliberate divergence.** `denyIfCannotManageTeam` (`portal-team.ts:40-54`) tests

  `buildUserPayload` really can sign. It fails open. The new model denies that principal.

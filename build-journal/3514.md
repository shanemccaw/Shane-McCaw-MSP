- 2026-09-10T13:42:52Z ⏳ IN FLIGHT — Investigating BuildQueuePanel.xaml.cs: Queued filter + summary counts (In queue/Up next) report 0 while an UP NEXT item (#3471, believed queued) is visibly present under All. - 2026-09-10T13:49:01Z ✅ DONE — Root cause found and fixed. The issue body's hypothesis (summary computed from a stale/separate snapshot) was DISPROVEN: `ComputeQueueStatusCounts` and `ApplyFilter` both read the same `_lastItems` field, populated together in `RefreshAsync`, and both were CORRECT. Live DB proof: `bt_build_queue` has 0 rows with status `queued` right now and 103 `canceled`; #3471 = queue id 2161, status `canceled`. So "In queue: 0 · Up next: 0" was the truth.

  The real bug was the opposite — a per-row RENDER mislabel. The status-pill if/else chain, the mini-map dot (`CreateGraphNodeDot`), and `GhostStatusLabel` all ended in a catch-all `else` that rendered "⏳ UP NEXT" for ANY status not explicitly enumerated. `canceled` was never enumerated (nor was any future/unknown status), so a canceled build showed "UP NEXT" under the "All" view — making it look like a genuine queued/up-next item the Queued filter and summary were wrongly hiding, when they were both correct.

  Fix (commit 684c75048, one file — `desktop/BuildConsole/Controls/BuildQueuePanel.xaml.cs`): added an explicit `canceled` branch (🚫 CANCELED, muted gray, distinct from failed's red) to all three render paths, and gated the "⏳ UP NEXT"/"🔒 BLOCKED" branch so it is reachable ONLY for a genuinely `queued` row (IsGenuinelyBlocked itself already returns false for any non-queued status). Any other/unexpected status now renders its real status string verbatim rather than masquerading as a claim candidate — closing the root fallthrough, not just the `canceled` symptom.

  Verification: `dotnet build BuildConsole.csproj -c Debug` → Build succeeded, 0 warnings, 0 errors. Live DB queried directly via DATABASE_URL to confirm #3471's real status (`canceled`) and that 0 queued rows exist (so the summary was already correct). Branch confirmed merged into origin/main (verify-branch-merged.mjs exit 0). Working tree clean. No separate finding filed — this was a single bug (three co-located sites of the same fallthrough), all fixed in scope; the issue-body stale-snapshot theory was investigated and ruled out rather than being a second defect.

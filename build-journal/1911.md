### The purge — wider than #1900 reported

#1900 found the plaintext in 3 rows of `wf_run_node_outputs`. Searching for the real
values rather than the key name found **11 rows across 4 columns**:

| Column | Rows |
|---|---|
| `wf_runs.payload` | 3 |
| `wf_run_node_outputs.output` | 3 |
| `wf_run_node_outputs.input` | 3 — nested under `steps.start.*`, so the top-level `delete` missed it |
| `wf_node_output_samples.sample` | 2 — the sample guard named the gate node, but the leak came through `start` |

`lib/db/migrations/manual/1911-purge-plaintext-generated-credentials.sql` — recursive,
key-scoped to `generatedPassword`, then `VACUUM FULL` on the three tables so the
pre-`UPDATE` tuples are actually reclaimed (an `UPDATE` alone leaves them in the heap).
Deliberately **not** a blanket `/password|secret/i` strip: the same tables legitimately
carry `passwordExpirationDays`, `passwordProtectionPolicyExists`,
`passwordValidityPeriodInDays_*` and similar real scan results.

**Verified:** zero occurrences of the generator's `Bg9!` prefix remain anywhere in
`wf_runs`, `wf_run_node_outputs`, `wf_run_node_logs` or `wf_node_output_samples`.

### The redaction — lands independently of the Key Vault work

`redactForPersistence` in `workflow-executor.ts`: recursive, applied to `input` **and**
`output` at every `wf_run_node_outputs` insert and to the output-sample capture. Redacts
both by key name and **by value** — the value pass is what covers error payloads, since
an SDK error can echo the request body that carried the password, and every affected run
was a failure. `wf_runs.error_message` and the executor's error log go through the same
scrub. The gate's `redactedPayload` is deep-redacted before it reaches `wf_runs.payload`.

Only non-empty **string** values at a named sensitive key are replaced, so
`"secretText": null` and `passwordExpirationDays: 90` survive intact.

### The Key Vault store

`artifacts/api-server/src/lib/generated-secret-store.ts` — store / read / bind / purge
plus an orphan finder. `GENERATED_SECRET_VAULT_URL` is a separate env var from
`AZURE_KEY_VAULT_URL` so aiming this at the production vault is explicit, and names are
dev-scoped by default (`GENERATED_SECRET_NAME_PREFIX`, default `genc-dev`). Non-guessable
names, TTL expiry, tags carrying run + tenant. Purge is delete **and** purge — soft-delete
alone would keep a "purged on acknowledgement" secret recoverable for the vault's 90-day
retention, which is the opposite of what the reveal page promises the customer.

The orchestrator stores the credential and fires the run with a payload carrying only a
**reference**; the executor rehydrates it into memory at run start. The database never
holds the value at any point. Fail-closed: no store configured means the run is refused,
never a fallback that writes the credential to the database.

Orphan cleanup at three levels — eager purge when the run never starts, on the executor's
terminal paths (unless a delivery is still pending), and a `purge_orphaned_generated_secrets`
Workflow Engine node as the backstop. All three of #1900's runs died before the gate, so
that is the normal case, not the edge.

### The reveal path

`break_glass_pending_secrets.secret_ref` (additive migration) is what the reveal reads,
falling back to the gate's encrypted copy for older rows. **The gate encryption is
untouched** — this moved where the plaintext lives, it did not weaken the gate.
Acknowledgement purges both copies. Admin-override stores its replacement in the vault and
purges the superseded one (the terminal sweep would never see it, since the run is still live).

## Other generated credentials on the write path

Grepped rather than assumed. Six generators exist; exactly **one** mints a credential
written to a customer tenant:

- `generateStrongPassword` (`routes/break-glass-verification.ts`) — **in scope**, two call
  sites, both now routed through the store.
- The `Temp-…!9` reset passwords in `routes/msp-settings.ts` and `routes/portal-team.ts` —
  bcrypt-hashed into `users.password_hash`, returned once, never persisted in plaintext.
- `generateSixDigitCode` in `lib/purchase-account-flow.ts` and
  `routes/public-assessment-account.ts` — bcrypt-hashed verification codes.
- `generateWebhookSecret` in `lib/webhook-delivery.ts` — referenced only by its own test,
  so it mints nothing in production today.

Separately, `secretText` (what Graph returns on `POST /applications/{id}/addPassword`) was
added to the redaction key set: today's packs only ever read it back as `null`, but a pack
that minted an app secret would leak it exactly the way #1900's password leaked.

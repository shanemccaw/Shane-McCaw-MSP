### What changed in substance, not just spelling

- A route gate names a **capability row key** (`"ladder.msp-admin"`) instead of a rung in a total
  order. Who clears it is now an `UPDATE`, not a redeploy.
- `ROLE_ORDER` / `roleIndex()` — #1696's *"this is not RBAC, it is a privilege ladder"* — are gone
  from the request path **and** from the source. The ordering survives only as data in
  `msp_feature_role_mapping`, plus one transcription in the shim.
- The 403 body is byte-identical; the rung is recovered from the key purely to build it.
- `admin-panel`'s hand-written `DirectoryGroupRole` union — a second, unchecked copy of the same
  seven strings — is now an alias of `LegacyRole`.

### The two capability columns

Dropped from the Drizzle schema. The DDL is
`lib/db/migrations/manual/2026-09-10-drop-capability-columns-2460.sql` and is **deliberately not
run** — CLAUDE.md sends dropping a column to Shane. Every reader is already gone, so the columns
are inert in every environment and the DROP can run on any schedule. Recorded on **#1630**. The
file opens with two `RAISE EXCEPTION` guards that refuse to run unless #2457's roles exist *and*
every column-carrying user already holds the matching role row, and carries a rollback that
rebuilds both columns from those rows.

`can_approve_changes` (#1496) stays — #2460's contract names two columns, and widening scope on a
security path is not this issue's call.

### One deliberate behaviour change, stated not hidden

Four notification-recipient queries used `mspRole = 'MSPAdmin' OR can_approve_purchases`, which
honoured the column for *any* role — while the authorization rule it stood in for only honoured it
on the MSPOperator branch. So it was possible to be paged about an approval you could not perform.
Recipients are now exactly the `msp:purchases.approve` holders. Zero users carry the column in the
live database, so no notification actually moves.

## Findings filed

- **#3498** — nothing maintains `msp_user_roles` / `customer_user_roles` on user create or
  `msp_role` change. Only #2457's one-time seed and the AdminV2 CRUD write them, so a user created
  since holds no rung role and a re-roled user still holds their old one. Load-bearing: it is why
  `rbac-capability.ts` resolves the rung from the JWT claim and only the `cap.*` grants from live
  rows, rather than doing the obvious `loadRbacContext`. Parented under #1696.
- **#3500** — `admin-active-directory-delete.test.ts:425` asserts a `customer_alert_settings`
  UPDATE that #3105 moved into the database. Parented under #1096.

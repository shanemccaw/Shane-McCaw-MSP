- 2026-09-04T02:55:00Z ✅ DONE — Root cause: `extractM365DscResources` (scripts/config-state/parse-m365dsc.mjs) trusted
  `settings.json`'s own `resourceName` field unconditionally. For `MSFT_EXOAtpProtectionPolicyRule` that field
  held the literal, un-templated placeholder string `"ResourceName"` instead of a real value, which silently
  corrupted `resource_key`/`display_name`/`m365dsc_resource`, and (via prefix-match) `workload`/`surface` too.
  Fixed by deriving the resource name from the resource's own directory (`DscResources/MSFT_<Name>/` —
  Microsoft365DSC's structural, authoritative identity) instead, falling back to settings.json only if the
  directory name is unusable, and warning on any disagreement so future drift is visible instead of silent.
  Verified with `SELECT split_part(resource_key,':',2) ... WHERE resource_key LIKE 'm365dsc:%'` across all 481
  m365dsc-origin `config_resources` rows that this was the ONLY row with this pollution class — a single-row
  data fix, not a bulk repair. Verified the parser fix end-to-end against a scratch fixture reproducing the
  exact defect (placeholder resolved correctly to `EXOAtpProtectionPolicyRule` / `ExchangeOnline`, warning
  printed, unaffected sibling resource untouched) — no re-download of the ~500MB DSC tarball was needed or done.
  Manual migration `lib/db/migrations/manual/2026-09-04-fix-exoatpprotectionpolicyrule-resource-name-2007.sql`
  ran locally against `DATABASE_URL`, correcting the existing row's `resource_key`, `display_name`,
  `m365dsc_resource`, `workload`, `surface`; every other column (properties, permissions,
  `verification_status`, notes) was already correct and untouched. `verify-branch-merged.mjs` confirms
  1097ee55a is on `origin/main`. `git status --porcelain` clean.

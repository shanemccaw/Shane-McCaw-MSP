## What was actually happening (live evidence)
- **Not data loss, not an exclusive hold.** `exclusive-build-set.json` = `{"ExclusiveSet": null}`; `priority-build-sets.json` empty. `bt_build_queue` id sequence is contiguous (2150→2154) — the ~68 were **never inserted**, not inserted-then-deleted.
- **The queue was filling correctly the whole time.** `BatterUpClearOut` grew 2 → 26 rows (25 queued + 1 running) during the session as the #2815 circuit permitted each closed-window refresh.
- **The "reversion" was a display artifact.** While the #2815 rate-limit circuit is OPEN, `BatterUpQueueService.ResolveBuildCommentsAsync` returns nothing, so `RefreshAsync` rebuilt every board item as `HasBuildComment=false` → "no BUILD: comment yet, needs dispatch" — even items whose BUILD comment was real. At 75-item scale the circuit flaps open ~every minute (log 00:52:33 RESET → 00:52:34 TRIPPED), so the lane appeared to keep reverting. Confirmed in activity-2026-09-10.log at 00:35:43 / 00:53:11.
- Of the 66 open Batter Up items all already had a queue row: 26 fresh (BatterUpClearOut), 18 done, 13 canceled/failed, 8 running/verifying, 1 superseded. The Build Queue **panel** shows only active rows → read as "~7".

## Leads
1. Exclusive hold — RULED OUT.
2. Per-pass cap — RULED OUT as cause; "arrives later" is real but circuit-driven, not a cap.
3. Scale-specific — CONFIRMED as the #2815 circuit saturation, NOT batch-insert/dup/pool corruption.

## Fix (abcfc277f) — scoped to the false reversion
- `BatterUpQueueService.RefreshAsync` / `AiBatterUpQueueService.RefreshAsync`: bail fast when `GitHubRateLimitCircuit.IsOpen` (throw recognized message) instead of rendering false negatives.
- `BatterUpPanel` / `AiBatterUpPanel`: on transient circuit-open, keep last-known rows + "GitHub cooling down (#2815)" header, don't blank/flap. Only blank on first load or a real failure.
- Build clean (0 warnings, 0 errors). Verified queue filling + processing live.

- 2026-08-30 ✅ DONE — Shipped exactly the independently-useful half this issue asked for;

  **Schema.** `config_resource_property_divergence` (`lib/db/src/schema/config-state.ts`),
  additive migration `2026-08-30-config-property-divergence-1846.sql`, run clean against local
  `DATABASE_URL` and logged on #1630. Deliberately keyed on the stable `resource_key`, with NO
  hard FK to `config_resources.id` — that id is deleted/reinserted fresh on every
  `build-resource-model.mjs` run, and a cascading FK (this schema's usual pattern) would have
  wiped this table on every rebuild, exactly the #1895 bug class this issue exists not to repeat.
  `config_resource_id` is kept as a denormalised best-effort pointer only.

  **Detection.** `scripts/config-state/detect-property-divergence.mjs` re-derives the divergence
  from whatever is currently in `config_resource_samples` (newest OK sample per resource) joined
  against `graph_entity_types`/`graph_entity_properties`, classifying each into the two real
  cases: `version_gap` (declared in the other Graph version) vs `undeclared_anywhere` (declared
  in neither v1.0 nor beta). Wired into `verify-sample.mjs` so a later live sample surfaces new
  undeclared properties automatically. Upserts on `(resource_key, property_name)`, so a re-run
  updates `observation_count`/`last_observed_at` rather than duplicating rows — confirmed by
  running it twice in a row.

  **Docs.** `scripts/config-state/render-property-divergence-doc.mjs` regenerates a clearly
  marked generated section (`<!-- BEGIN/END: generated by ... -->`) in
  `docs/graph-resource-model.md`, placed after #1794's original "Finding" section (left
  untouched, per the issue's instruction) and before the "Running it" reference tail. Confirmed
  idempotent — re-running it in place replaces only the marked section, no duplication.

## Design decisions (latitude the issue gave)
- **Capability:** `customer:marketplace.browse-full` (customer system, category `marketplace`), not `customer.paid`. The catalog convention is `<surface>.<verb>`, and a capability names an authority over a surface, not an account state. Payment is the *grant condition*, not the thing granted, and a customer org narrowing it for its own roles (hide the upsell catalog from engineers) should read sensibly. Grant: the platform mapping allows Customer, ServiceAccount, MSPOperator, MSPAdmin and PlatformAdmin, i.e. every rung except the pre-payment Free rung. So a prospect gains it the moment `promoteMspUserToCustomer` moves them Free -> Customer, with no grant call to forget. Shared helper: `artifacts/api-server/src/lib/marketplace-catalog-scope.ts`. Marketplace answers 503 when the model is unreadable; search narrows only its marketplace source and logs an error.
- **Behaviour change, stated:** the old branch was `role === "Assessment" ? narrow : full`, so **Free** used to get the full catalog. Folding Assessment into Free makes Free the narrow tier. The live DB had 0 Free users before the migration, so nobody's view moved.
- **Capability keys stay immutable:** `ladder.customer-user` keeps its key (capabilities.ts: "Immutable once shipped"; 40+ gates and the mapping row name it), and only its label/description follow the rename. `ladder.assessment` is retired: its ~50 gates now ask `ladder.free`, which admits exactly the same set after the merge. The mapping row is deleted and the catalog row flagged inactive, per syncCapabilityCatalog's rule.
- **Role UUIDs kept:** the platform CustomerUser role is renamed in place in both systems, so every mapping reference and any AdminV2 edit survives. The Assessment role is deleted; #2455's purge trigger strips its id from every allow/deny array, and every mapping that allowed Assessment also allows Free.
- **#3408 trigger:** `rbac_sync_user_roles()` is replaced (CREATE OR REPLACE) with the six-rung list, with the same rule otherwise. The UPDATE users statements go *through* the trigger, and a final convergence pass runs over every user.
- **Stale JWT claims:** `canonicalRoleValue()` / `RETIRED_ROLE_VALUES` in legacy-ladder.ts reads a pre-rename claim (15m access, 30m impersonation tokens) as the rung it became. Applied in requireAuth, effectiveLegacyRole, the msp-diagnostics SSE decoder and subscriptionGate.
- **Free inherits Assessment's `copilot-readiness` landing** (identity-presentation.ts). Otherwise every former Assessment user would have been moved to "dashboard".
- **users_role_scope_check:** declared in the Drizzle schema, absent locally (#3608). The migration lifts it before the rename and restores it with the new values only where it existed.
- **Not rewritten, deliberately:** `msp_audit_logs.actor_role` history (52 CustomerUser / 12 Assessment rows are what the actor WAS), and the two workflow definition NAMES (the seed's upsert key). The two weekly-rescan `wf_triggers.fan_out_query` values WERE rewritten, because the seed never updates an existing trigger.

  **Context — what this build actually was.** Queue build 2382's entire prompt was the word
  `Retry`, with no GitHub number and no session to resolve it against. Reconstructed from
  `bt_build_queue`: 2364 built #3698 (done, exit 0, session `53af9d01`), Shane replied "Retry"
  → row 2376 (`resume_session_id` = `53af9d01`, superseded, exit -2), retried again → row 2382
  with `resume_session_id` **NULL**. #3698 itself is CLOSED and labelled `complete`, so redoing
  its work was not the ask; the real, reproducible defect was the one that had just stranded
  this session. Filed it as **#3728** and fixed that.

  **What shipped:**
  - `Services/ResumeOnlyQueueRows.cs` (new) — single definition of the two title prefixes that
    mark a row whose prompt is a conversational message rather than a build prompt:
    `Reply → ` and `Continue: `. Both were bare interpolated literals at four creation sites
    (BuildQueuePanel ×2, BuildWatchWindow, GitDetailView ×2) with **nothing on the read side**
    — the drift that let Retry treat a reply as an ordinary build. All four now use the const.
  - Both Retry paths (`QuickRetryAsync`, the `🔄 Retry` context-menu item) resolve through a new
    `TryResolveRetryResumeSessionId`: an ordinary row still re-queues with `null` (a genuine
    start-over, unchanged); a resume-only row carries its own `ResumeSessionId` forward; a
    resume-only row with no session left **refuses** with a plain explanation rather than
    minting a second cold session fed the same fragment.
  - The menu item relabels to "Retry (re-send to the same session)" on a resume-only row, since
    "start over" is not what it does there.
  - `scripts/probes/retry-resume-session/` (new, kept diagnostic) — compiles the **real**
    classifier via `<Compile Include>` (not a copy) and replays real rows exported from the live
    queue. Dependency-free: reads a TSV, links no Postgres driver, never launches BuildConsole.

  **Measured against all 2,170 real `bt_build_queue` rows:**

  | | rows |
  |---|---|
  | ordinary → `null` (start over, **unchanged**) | 2084 |
  | resume-only with a session → carried forward | 83 |
  | resume-only with **no** session → Retry refused | 3 |

  96% of rows are untouched — the point of the fix is that an ordinary build's Retry still
  means start over. The 3 refused are exactly the damaged rows: `#462 "retry"` and
  `#480 "try again"` (both 2026-08, both ran to **done, exit 0** on a two-word prompt with no
  conversation — the same bug a month earlier, silently) and `#2382 "Retry"`, this build.

  **Side effect, in the right direction:** `QueueWatcherService`'s `isFreshDispatch` keys off
  `ResumeSessionId`. A retried reply previously looked like a fresh dispatch and logged a
  `build_dispatch_log` row for what was really a continuation; it no longer does — matching
  that code's own stated intent ("never a Reply/--resume continuation").

  **Honest gaps:**
  - `dotnet build`: 0 errors, and the 10 warnings are identical to the pre-change baseline
    (the CS0162 pair is upstream #3699's `BuildMatrixDisabled` const; the CS0067 trio is
    FocusModeBar). No new warnings in touched files.
  - **No live click-through.** Per the standing rule a session must not launch BuildConsole.exe

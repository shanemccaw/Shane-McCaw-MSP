# #4837 — plan

Posted: 2026-09-19T05:18:17Z

## Problem Description

`resolveDriftEvents` serves every `drift:*` dashboard metric. It reads `drift_collection_status` only when **no baseline snapshot exists**. When a baseline was captured on an earlier run and the *latest* collector run was recorded `not_comparable` / `error`, it ignores that verdict and returns `ok` with `events: []`, `zeroRows: true` — "genuinely clean". Live example (local dev DB, tenant `c4c814d4-3afe-441e-9145-62461d0a4fd3`): `ca-policy` has a baseline (2026-09-16) **and** status `not_comparable` / `gate_not_satisfied`, so the dashboard reports no drift for a domain the collector said it could not compare.

## Root Cause Analysis

The status lookup lives inside the `if (!baseline)` branch: [dashboard-resolvers.ts L742–L766](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e7ab261f94b600dda92b6032f1548b99e72b0a1/artifacts/api-server/src/lib/dashboard-resolvers.ts#L742-L766). `drift_collection_status` has a unique index on `(tenant_id, domain_key)` and the collector upserts it on every run, so the row is by construction the verdict on the **latest** run — the baseline is only meaningful when that run could be compared. #4578's [pillar-drift.ts](https://github.com/shanemccaw/Shane-McCaw-MSP/blob/4e7ab261f94b600dda92b6032f1548b99e72b0a1/artifacts/api-server/src/lib/pillar-drift.ts#L60-L64) already reads status first via `driftStateFromStatus`; the resolver was left untouched at the time.

## Proposed Changes

1. `dashboard-resolvers.ts` `resolveDriftEvents`: read `drift_collection_status` first, unconditionally. If `driftStateFromStatus(status)` (shared with pillar-drift.ts, so both surfaces classify identically) is not `tracked`, return `notAvailable("not_comparable" | "collection_error", <collector's real reason>)` — before touching the baseline or events. Then the existing baseline / no_data / events logic is unchanged. Update the doc comment to state status-first.
2. New `dashboard-resolvers-drift.test.ts`: baseline + `not_comparable` → not_available; baseline + `error` → collection_error; baseline + `tracked` → ok (unchanged); no baseline + no status → no_data; no baseline + `not_comparable` → still not_comparable.

No schema change, no fixture data. Other consumers reach this only through `resolveMetric` (`drift:*` sourceKeys) and already handle `not_available` (the no-baseline branch returned the same shapes before).
